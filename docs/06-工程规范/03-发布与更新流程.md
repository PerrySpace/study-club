# 06-3 部署与更新流程

> 本文档定义「代码从合并到线上生效」的标准流程与动作。
>
> 本项目**不绑定任何 CI/CD 服务**：部署单元就是 `deploy/` 下的 Docker Compose，
> 由 `scripts/` 里的脚本驱动 —— 本机、内网服务器、云主机是**同一套动作**。
> 想接 Jenkins / GitHub Actions 也可以，但那是**你的选择**，仓库默认不依赖它。
>
> 分支模型与提交信息规范见 [06-1 §五](./01-开发规范与前端架构.md#五git-与协作规范)；
> 环境变量清单见 [06-1 §六](./01-开发规范与前端架构.md#六环境与配置)。

## 一、部署拓扑

四个服务**各自独立编排**（`deploy/mongo` / `deploy/api` / `deploy/web` / `deploy/admin`
四份 compose），统一 `network_mode: host` —— 容器直接占用宿主端口，**不做端口映射**。

| 服务 | Compose | 默认端口 | 对外 |
| --- | --- | --- | --- |
| web（nginx：静态前端 + `/api/` 反代） | `deploy/web` | `WEB_PORT`（8090） | ✅ **唯一对外入口** |
| api（FastAPI / uvicorn） | `deploy/api` | `API_PORT`（8000） | ⛔ 只应由 web / admin 的 nginx 反代访问 |
| admin（nginx：单管理员内容后台） | `deploy/admin` | `ADMIN_PORT`（8081） | ⛔ 内部工具，**勿暴露公网** |
| mongo（MongoDB 7） | `deploy/mongo` | `MONGO_PORT`（27017） | ⛔ 只绑 `127.0.0.1`（默认无鉴权） |

> **端口为什么默认 8090 而不是 8080**：8080 是被其它服务占用概率最高的端口，
> 撞车时表现是「web 起不来」而不是报错。四个端口都由 `.env` 控制，改一处即可整体迁移。

**持久化**：MongoDB 数据在命名卷 `study-club-mongo-data` / `study-club-mongo-config`，
上传的素材在 `study-club-assets`。`down` **不删卷**。

### 1.1 为什么接口必须同源（`/api/` 反代）

前端是静态站，接口在另一个进程上。如果让浏览器**直连后端**，会撞上两堵墙，
而且**两堵都不是「配一下 CORS 就能过」的**：

1. **混合内容**：线上页面在 `https://`，而接口若是 `http://<ip>:8000`，浏览器会
   **直接拦掉请求** —— 发都没发出去。此时控制台会同时报 `Mixed Content` 与
   `CORS header missing` 两条，很容易一路去调后端 CORS 白名单，而真正的原因在第一句。
2. **白名单要跟着访问地址变**：局域网 IP / 域名 / localhost 各不相同，
   每加一个入口就得改 `.env` 的 `CORS_ORIGINS` 并重启 api。

因此：`VITE_API_BASE_URL=/api/v1`（**相对路径**）+ web / admin 容器的 nginx
`location ^~ /api/ → proxy_pass http://127.0.0.1:8000`。同源之后两堵墙一起消失，
而且**同一份构建产物在 IP、域名、localhost 下都能用 —— 换地址不需要重新构建**。

> 两个容易踩的细节：① 必须写 `^~`，否则 `location ~* \.(svg|png|...)$`
> 这类**正则** location 优先级更高，会把 `/api/v1/assets/xxx.svg` 抢走并在静态目录 404；
> ② 该 location 里**不要写 `add_header`**，一条就会让 server 级的安全响应头整层失效。

## 二、先判断「改了什么」，再选动作

更新会改变线上行为的只有两类东西：**镜像里的代码/构建期变量** 和 **MongoDB 里的数据**。
先对号入座，**不要一律全量重建**。

| 改动 | 动作 | 为什么 |
| --- | --- | --- |
| `apps/web/**` 前端代码 | `scripts/web/up.sh` | 重建 web 镜像（Vite 构建静态文件） |
| `apps/api/**` 后端代码 | `scripts/api/up.sh` | 重建 api 镜像并重启容器 |
| `apps/admin/**` 后台代码 | `scripts/admin/up.sh` | 重建 admin 镜像（**前提**：`.env` 已配 `ADMIN_PASSWORD_HASH`） |
| `packages/**` 内核 / 学科 / 令牌 | 用到的镜像都要重建 | 三个 app 都依赖 workspace 包，改 core 可能同时影响 web 与 api |
| `content/**` 内容 JSON（字库/古诗/单元/关卡） | `scripts/seed/seed.sh` | 内容真源是 **MongoDB**，`content/` 是**导入种子**；幂等 upsert，不会重复插入 |
| `.env` 的 `VITE_*`（如 `VITE_ENABLE_INVITE_REQUIRED`） | `scripts/web/up.sh` | **构建期**变量，打进静态产物；只改 `.env` 不重建**不生效** |
| `.env` 的其它键（`JWT_SECRET` / 端口 / `CORS_ORIGINS` …） | 改完 `scripts/api/up.sh`（或 `restart.sh`） | **运行期**变量，重启即生效，不必重建镜像 |
| 邀请码 | **不需要发版** | 后台「邀请码」页批量创建，或 `scripts/api/issue-invites.sh` |
| 管理员口令 | `scripts/api/hash-password.sh` → 填 `.env` → `scripts/api/restart.sh` | 哈希是运行期变量 |
| 拿不准 | `scripts/dev/up-all.sh` | 按 db → api → web 顺序全量重建，最稳但最慢 |

> ⚠️ **`VITE_*` 是构建期变量**，这是「代码改了、发布也成功了，页面上却毫无变化」最常见的原因。
> 判断方法：下载线上入口 JS，搜旧值是否还在。

## 三、首次部署

```bash
git clone <你的仓库地址> && cd study-club
cp .env.example .env            # 生成环境变量（端口 / 开关 / 密钥占位）
scripts/dev/bootstrap.sh        # 建目录、生成密钥、准备图标等（一步到位）
scripts/dev/up-all.sh           # db → api → web 依次起，并做健康检查
scripts/seed/seed.sh            # 导入初始化数据（按表/功能拆分）
scripts/dev/status.sh           # 查看容器状态与全部访问地址
```

首次部署后有**三件事**必须处理，否则等于没部署好：

1. **没有任何可用邀请码**。仓库里的 `scripts/seed/data/01_invites.json` 只是占位样本
   （`note` 已写明「此 code_hash 不对应任何明文码」），导入它谁都注册不了。
   跑一次 `scripts/api/issue-invites.sh` 现场签发，把明文码发给使用者。
   若想先免码体验，把 `.env` 的 `VITE_ENABLE_INVITE_REQUIRED` 改成 `false`
   **并重建 web 镜像**（前端是静态构建，改构建期开关必须重建）。
2. **管理后台要配口令才会启动**。后台是**单口令、无用户名**的设计：

   ```bash
   scripts/api/hash-password.sh     # 交互式输入口令 → 输出一行可直接粘贴的配置
   # 把那一行整行贴进 .env（⚠️ 含单引号，别去掉），然后：
   scripts/api/restart.sh
   scripts/admin/up.sh              # → http://localhost:8081/
   ```

   哈希必须用**单引号**包住：Argon2 哈希含大量 `$`，Compose 的 dotenv 解析
   未加引号的值时会做变量插值把哈希改坏，症状是「口令明明对，却一直 `40301`」。
3. **对外域名与 TLS**。web 监听 `WEB_PORT`，前面挂反向代理 / 隧道 / CDN 都行，
   但必须满足 §1.1 的同源条件；HTTPS 页面调 http 接口会被浏览器直接拦下。
   用 CDN 时注意 §八 对 `/sw.js` 的缓存要求。

## 四、日常更新（标准动作）

```bash
cd study-club
git pull                       # 或 git checkout <tag> —— 发布永远针对一个确定的提交
scripts/dev/up-all.sh          # 按依赖顺序重建并重启（或按 §二只跑单个脚本）
scripts/seed/seed.sh           # 若本次改了 content/**
scripts/dev/status.sh          # 确认容器 healthy 且端口正确
```

- **内容与代码可以分开更新**：只改 `content/**` 时不需要重建任何镜像，`seed.sh` 即可。
- **`scripts/dev/up-all.sh` 不改「单独构建」的设计**：它只是按依赖顺序依次调用
  `scripts/db/start.sh` → `scripts/api/up.sh` → `scripts/web/up.sh`，并等 api 健康后再起 web。
- **管理后台不在默认链路里**（内部工具，按需 `scripts/admin/up.sh`）。

## 五、发布后验证（必做）

```bash
# ① 同源接口：必须返回 JSON 信封，而不是 HTML
curl -s http://127.0.0.1:8090/api/v1/health
#    → {"code":0,"message":"ok",...}
#    ⚠️ 若返回 index.html，说明 /api/ 反代没生效（nginx 把接口当成了前端路由），
#       此时状态码仍是 200，只看状态码会漏掉

# ② 线上产物里的接口基址（应为相对路径，不应出现 http://<ip>:8000）
curl -s http://127.0.0.1:8090/ | grep -oE '/assets/index-[^"]+\.js'

# ③ 四个服务状态
scripts/dev/status.sh
```

再按 §二 对号入座走一遍业务：**注册 → 建档案 → 取题 → 答题 → 学情报告**，
这条链同时覆盖了身份、内容、学习记录三张表，比单看健康检查有效得多。

## 六、改配置

`.env` 是真源，**不在仓库里**（`.gitignore` 已忽略，只提交 `.env.example`）。

1. **只改运行期键**（`JWT_SECRET` / 端口 / `CORS_ORIGINS` …）→ 改完重启对应服务。
2. **改 `VITE_*`** → 必须**重建 web 镜像**（`scripts/web/up.sh`），否则线上仍是旧值。
3. **不要把密钥写进仓库**：仓库里只允许有 `.env.example`。
4. **`JWT_SECRET` 一变，所有人立刻被登出** —— 这是预期行为，不是 bug。
5. 数据库目前**默认无鉴权**，因此 mongo 只绑 `127.0.0.1`：比「绑全网段 + 配口令」简单，
   也不会出现「口令对了却连不上」。共享局域网或公网机器上**必须**保持这个绑定。

## 七、回滚

部署是**原地覆盖**（没有蓝绿、没有多版本并存），所以回滚 = 把代码退回上一版再发一次。

| 回滚对象 | 动作 |
| --- | --- |
| 代码（api / web / admin） | `git revert <坏提交>`（或 `git checkout <上一个 tag>`）→ 重跑 §四。前端产物带内容哈希，用户刷新即见效 |
| 内容（`content/**`） | revert 内容 JSON → `scripts/seed/seed.sh`（幂等 upsert 会把字段改回去） |
| 配置 | 改回 `.env` → 重启对应服务 |
| 管理员口令 | 重跑 `scripts/api/hash-password.sh` 并填回 `.env` |

⚠️ **数据不会跟着回滚**：MongoDB 数据在命名卷里，`down` 不删卷。
破坏性的数据结构变更**没有自动回滚路径**，动手前先备份：

```bash
scripts/db/backup.sh                    # 导出到 backups/（.gitignore 已忽略）
scripts/db/restore.sh backups/<文件>     # 需要时回灌
```

## 八、「发布成功但页面还是旧的」怎么查

前端是 PWA（有 Service Worker）。**判定顺序固定，别跳步**：

1. **先撇开 SW，直连源站比对** —— 这是区分「源站问题」与「浏览器缓存问题」的关键一枪：

   ```bash
   curl -s http://127.0.0.1:8090/ | md5sum     # 源站
   curl -s https://<你的域名>/ | md5sum         # 对外
   ```

   两者一致 ⇒ 服务端已发布，问题在客户端。
   > ⚠️ **没有页面服务跑在 8000**。8000 是 api（`GET /` 返回 **404**，
   > `GET /api/v1/health` 才 200）；页面服务 web 在 `WEB_PORT`（默认 8090），
   > 它把 `/api/` 反代到 `127.0.0.1:8000`。别按容器名猜端口。

2. **看入口 chunk 名**：`index.html` 里的 `src="/assets/index-XXXX.js"`。
   > ⚠️ **不能按 hash 判断「是不是同一次构建」**：不同机器/不同工具链构建出的产物
   > 存在字节级差异，同一份源码两边产物名不同。判版本要看**内容特征**（新路由、新文案），
   > 不看 hash。

3. 源站已是新版、浏览器仍是旧的 ⇒ 几乎一定是 **Service Worker 拿旧缓存应答了导航请求**。
   用**无痕窗口**打开最快验证（无 SW、无 CacheStorage）。清理：
   DevTools → Application → Service Workers → **Unregister** →
   Storage → **Clear site data** → 强刷。

**代码侧已有的加固**（`apps/web/vite.config.ts` 与 `src/platform/pwa.ts`）：

- SW 里导航请求（HTML）改为 **NetworkFirst** —— 在线时永远取源站最新 HTML，
  不再"由 SW 新旧决定页面新旧"；离线回落最近一次成功导航的缓存。
  为此**去掉了 `navigateFallback`**：它生成的 `NavigationRoute` 是 cache-first，
  且注册顺序在 `runtimeCaching` **之前**（见 `workbox-build/templates/sw-template.js`），
  会抢先把导航请求答掉，让 NetworkFirst 永远轮不到。
  > ⚠️ `vite-plugin-pwa` 的 `defaultWorkbox` **硬编码了 `navigateFallback: "index.html"`**
  > 并用 `Object.assign` 合并 —— 只删配置项会被补回来。必须显式写
  > `navigateFallback: undefined` 才真正关掉；否则预缓存清单里没有 `index.html` 时
  > `createHandlerBoundToURL` 会在 SW 启动即抛错，**直接废掉整个 SW**。
- 客户端**主动轮询更新**（`registration.update()`：注册后立即 + 每 20 分钟 + 回到前台），
  不再依赖浏览器对自动更新检查的 **24h 节流**。

**对外 CDN 的硬性要求**：`/sw.js` 必须保持 `no-cache`。
⚠️ **Cloudflare 的 Browser Cache TTL 会覆盖源站头** —— 源站明明返回 `Cache-Control: no-cache`，
CDN 却可能返回 `max-age=14400`，浏览器会直接用缓存里的旧 SW 脚本，更新链路被掐断。
处理：Caching → Cache Rules → 表达式 `http.request.uri.path eq "/sw.js"`
→ Browser Cache TTL 设为 **Respect Existing Headers**，然后 Purge。

**历史包袱**：上述加固只对**新装上的 SW** 生效。已经装着旧 SW 的浏览器，
其 SW 代码已固化、不会再变，必须**手动清理一次**（无痕 / Unregister / Clear site data）才会切过去。

## 九、部署红线

1. **密钥不进仓库**：仓库里只有 `.env.example`。管理员口令走 `.env` 或临时环境变量，绝不落库。
2. **管理后台不对公网开放**：只监听 `ADMIN_PORT`（默认 8081），需要时临时起、用完 `scripts/admin/down.sh`。
3. **发布永远针对一个确定的提交**：`git pull` 后先 `git log -1` 确认是你要发的那一版，
   不要发一个「本地未提交/未推送的工作区」。
4. **发布必跑验证**（§五）：健康检查只看 `/health`，接口级的 500 它看不见。
5. **判定「反代是否生效」要看响应体，不能只看状态码**：nginx 没有 `/api/` 前缀块时，
   `try_files ... /index.html` 会把接口请求当前端路由接住，返回 **200 + HTML**。
6. **数据库默认无鉴权**：mongo 必须绑 `127.0.0.1`，且**不要**把 27017 暴露到公网。
7. **`docker image prune` 前先确认归属**：共享机器上可能还有其它项目的镜像。
