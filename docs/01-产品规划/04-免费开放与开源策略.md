# 01-4 免费开放与开源策略

> 本文档说明项目当前的运营模式与许可策略：**现有全部功能免费开放、无广告、无内购，项目以开源方式对外发布**。**当前版本不提供任何付费、会员或升级能力**——支付、订单、权益、会员等级、增值包一律不做、不打包、不部署。
>
> 这些结论反向约束架构、内容与工程规范：已具备服务器资源、云端后台可实际部署；能力取舍一律优先免费方案，不引入任何「没它不行」的付费依赖。

## 一、免费开放的边界

> 项目的前置约束（六条前置约束、约束推导出的架构、能力分级：掩藏 / 可做且已部署 / 首选）见 [docs/README.md](../README.md) 第一节。
>
> 架构落地方案见 [02-3 存储与后端策略](../02-系统架构/03-存储与后端策略.md)。本文档只回答「免费边界在哪、付费与升级能力如何处置、许可与版权怎么算、成本多少」。

## 二、免费开放的具体承诺

### 2.1 「免费」的定义

| 维度 | 承诺 |
| --- | --- |
| 功能 | **全部功能免费**，不做功能分级，不做「高级版」 |
| 时间 | 不设试用期、不设次数限制 |
| 用户数 | 不设邀请码发放上限；准入可放量至免码开放 |
| 广告 | **无任何第三方广告、无开屏、无插屏** |
| 内购 | 无（儿童产品的广告与内购本身就是合规雷区） |
| 数据 | 学习数据仅存自建服务端；不售卖、不用于训练、不接第三方埋点 |

### 2.2 因此明确不做的事

支付、订单、退款、权益校验、会员等级、优惠券、分销、邀请返利、付费打卡、课程售卖——**免费模式下不提供**；相关契约与开关保留（`enablePayment`，默认关闭），不注册路由、不打包、不部署。

### 2.3 仍然必须做的事

免费不等于免责。以下仍然要做，只是实现方式变了：

| 事项 | 现方案 |
| --- | --- |
| 隐私说明 | 必须保留：说明数据存自建服务端、不接第三方埋点，并披露访问日志 |
| 家长可见性 | 保留家长视图；「时长自控」从合规要求变为体验功能，按档案设置实现 |
| 儿童友好 | 无广告、无外链、无社交、无诱导消费——本来就该做，免费模式下天然满足 |
| 数据可迁出 | 进度导出/导入必须做（见 [02-3 存储与后端策略](../02-系统架构/03-存储与后端策略.md) 第七章） |

### 2.4 成本清单

关键结论：**后端已经真正跑起来，且"轻"到几乎没有成本**。

| 项 | 方案 | 成本 | 备注 |
| --- | --- | --- | --- |
| **服务器** | ✅ 已有 | 已沉没成本 | 需求很低：1C1G 即可跑起内容服务与统计 |
| 域名 | 自备 | 约 ¥50/年 | 若服务器在境内则**必须备案**（见 7.1） |
| 静态托管 | Cloudflare Pages / GitHub Pages / **自托管 Nginx** | ¥0 | 三选一或组合 |
| 内容分发 | 仓库 JSON → 自托管 MongoDB → 接口下发 | ¥0 | 内容数据量小（数千条 JSON），无需 CDN 也能跑 |
| 数据库 | **MongoDB 自托管**（已有服务器） | ¥0 | 内容量小，单机足够；**不买云数据库** |
| 缓存 | 内容全量进内存 | ¥0 | 数千条数据无需 Redis |
| 对象存储 | **优先仓库内文件 / 服务端落盘** | ¥0 | 仅当素材体积明显拖慢加载时才考虑替代方案 |
| 语音处理 | 浏览器本地运行（F0 / VAD） | ¥0 | 无调用费、无密钥 |
| CI | GitHub Actions 免费额度 | ¥0 | 足够 |
| 统计 | **自建匿名统计** | ¥0 | 不接第三方埋点 SaaS |
| 监控 | 本地日志 + 自托管 | ¥0 | 不接付费 Sentry |
| 短信 / 推送 | 不做 | ¥0 | 不做实名账号，无此需求 |
| **合计** | — | **约 ¥0–50/年** | 服务器已有，其余全部走免费方案 |

> ⚠️ **唯一的真实约束**：服务器位置决定合规路径。部署在境内 → 必须 ICP 备案（个人主体可做非经营性备案）；部署在境外 → 免备案但国内访问慢。两条路径的取舍见 [02-3 存储与后端策略](../02-系统架构/03-存储与后端策略.md) 第九章。

### 2.5 付费与升级能力：本版本不做

**当前版本不提供任何形式的付费能力**——不做会员 / 订阅 / 买断 / 增值包 / 去广告 / 解锁关卡，代码侧只保留契约与开关（如 `enablePayment`，默认关闭），不注册路由、不打包、不部署。这一处置与第三章「企业主体能力」一致。

**若未来确需引入付费能力，必须同时满足下面四条硬约束，否则不得合并**：

| # | 原则 | 反例（不允许） |
| --- | --- | --- |
| ① | **可选** —— 缺它，核心学习流程照常走完 | 「不配语音评测 Key 就无法做跟读练习」 |
| ② | **可降级** —— 没有它时自动走免费替代方案 | 「评测服务不可用时页面报错」 |
| ③ | **默认关闭** —— 由能力开关控制，默认 `false` | 默认开启、未配置就崩溃 |
| ④ | **不破坏开源可运行** —— 贡献者克隆后不配任何密钥、不付任何费用，能完整跑通所有功能 | 「README 里写：请先申请 XX 服务的 Key」 |

> 一句话：**付费能力只能是「锦上添花」，永远不能是「没它不行」。** 这条原则同时保护了三件事——开源可运行性、成本可控性、以及"不做企业主体的事"这条底线（多数付费 API 的实名与结算也要求企业主体，需逐个核实）。

## 三、企业主体相关能力：不做、预留、隐藏

### 3.1 逐项处置

| 能力 | 为什么依赖企业主体 | 当前处置 | 预留形式 |
| --- | --- | --- | --- |
| 微信支付 / 支付宝 | 商户号必须企业或个体工商户 | ❌ 不做 | 仅保留 `orders` 集合设计，不进代码 |
| 微信登录（网页/App） | 开放平台账号需企业认证 | ❌ 不做 | `users` 集合 + `/auth/wechat` 契约保留 |
| 手机号短信登录 | 短信服务需企业实名 | ❌ 不做 | 同上的 `/auth/otp` 契约保留 |
| 微信小程序 | **见下方 3.2** | ❌ **整体后置** | 契约与开关保留（`enableMiniprogram`） |
| App 上架 | 应用商店需企业开发者账号 | ❌ 不做 | 契约与开关保留（`enableNativeApp`） |
| ICP 备案 | 大陆服务器托管需要 | ⏸️ 按需（个人主体即可办非经营性备案） | 部署方案保留 |
| 教育类目资质 | 微信平台按类目要求资质 | ❌ 不做 | 内容合规清单保留 |
| 云端内容管理后台 | 需要服务器（不需企业主体） | ✅ **可做且可部署**：自托管「单管理员」后台 | 单管理员简易鉴权后台（见 [05-1](../05-管理后台/01-内容管理与用户管理体系.md)） |
| **邀请码身份与准入** | **不需要企业主体**（无手机号/微信） | ✅ **可做且可部署**：邀请码 + 密码，或 Ed25519 离线签名 | 见 [02-5](../02-系统架构/05-邀请码身份与准入体系.md) |
| 云同步（账号级） | 需要账号识别用户 | ✅ **可用邀请码身份 / 云端家庭档案替代** | 云端家庭档案同步 + 恢复码（见 [02-3 存储与后端策略](../02-系统架构/03-存储与后端策略.md) 第七章） |

> ⚠️ **重要区分**：**服务器本身不需要企业主体**，只有「账号体系（手机号/微信登录）」与「支付」才需要。所以：
>
> - ✅ **可以部署**：内容管理后台（单管理员密码）、匿名内容接口、云端家庭档案同步、自建统计
> - ⛔ **不能部署**：需要手机号/微信登录的账号体系、支付与订单、短信、小程序、App 分发
>
> 这条区分是本策略最容易被误解的地方——「不做企业主体的事」不等于「不能有服务器」。

### 3.2 ⚠️ 微信小程序不能「先用个人主体试水」

这条必须单独强调，因为它会让人做出**不可逆**的错误决策。核实到的官方规则：

1. **个人主体禁止申请教育类目**。微信的服务类目准入中，教育类目明确不对个人主体开放；个人主体小程序只能做图文展示、作品分享、简易工具、免费资讯。
2. **个人主体不能开通微信支付商户号**，也就无法承载任何经营行为；变相收款会被下架、封号。
3. **2026 年小程序全量强制备案**，未备案无法提交平台审核、不能发布。
4. **最致命的一条：小程序注册主体选定后不可变更**。前期注册个人小程序，后续要开通支付或切换类目，**只能重新用营业执照注册一个全新小程序**，原名称、访问数据、用户全部无法保留。

**结论**：现在注册个人主体小程序不但没用，还会浪费掉唯一的免费注册位与一个可用的名称。**小程序整体后置到「具备主体之后」**，在此之前不做任何投入。

> 顺带说明：这**不影响**本项目的多端布局设计。平台抽象层（`packages/core`）与小程序的契约、开关仍然保留——小程序一旦启动，会直接复用 `packages/core`。只是现在不写、不注册、不备案。

## 四、开源策略

### 4.1 建议：尽早开源，不要等到「做完」

**结论：尽早开源**——等到全部做完再开源，代价是内容生产（最大的瓶颈）全程单打独斗。

**理由**：这个项目最稀缺的不是代码，是**内容产能**（见 [01-2 第七章](./02-产品定位与内容体系设计.md#七内容生产的组织建议)）。而内容恰恰是最适合众包的——一个字条的释义、组词、例句，是可以被拆成上百个独立小任务分发的。**开源的真正价值在于把内容生产从「1 个人做 3500 字」变成「100 个人各做 35 字」。**

### 4.2 开源范围

| 层 | 是否开源 | 说明 |
| --- | --- | --- |
| 前端代码 | ✅ | 学生端、内核、组件 |
| 内容数据 | ✅ | 字库、古诗、课程编排 JSON |
| 文档 | ✅ | 本套 `docs` 与 `website/` 文档站 |
| 构建与部署脚本 | ✅ | 静态站点与容器部署配置 |
| 设计资产 | ✅ | tokens、图标、配图（须为自有或可授权） |
| **云端后台代码** | ✅ | 可开源；**贡献者按 `deploy/` 一键起后端即可完整自托管** |
| 用户数据 | ❌ | 存服务端，不进代码仓库 |
| 运营与统计数据 | ❌ | 不存在 |

### 4.3 许可证选择

**必须区分两类许可**，不能一个 LICENSE 了事：

#### 代码：建议 MIT（备选 Apache-2.0）

| 许可 | 特点 | 适合度 |
| --- | --- | --- |
| **MIT** | 最宽松、最短、最被理解，任何人可自由使用（含闭源商用） | ⭐ **推荐**，教育公益项目优先传播 |
| Apache-2.0 | 同样宽松，额外含**专利授权**条款 | 可选，若担心专利风险 |
| GPL-3.0 / AGPL-3.0 | copyleft，衍生作品必须同样开源；AGPL 还管到网络服务 | ⚠️ 与「让更多人用起来」的目标相悖 |
| 非商业许可（PolyForm NC 等） | 禁止商用 | ❌ **不是开源许可**，且会阻碍学校、教育机构等正当使用 |

**推荐 MIT**：这个项目的目标是让更多孩子用上，许可越宽松越好。

#### 内容：建议 CC BY-SA 4.0

| 许可 | 特点 | 适合度 |
| --- | --- | --- |
| CC0 / 公共领域 | 完全放弃权利 | 过于激进，内容被拿去闭源包装成付费产品的可能性高 |
| CC BY 4.0 | 署名即可自由使用，含商用 | 可选，最宽松 |
| **CC BY-SA 4.0** | 署名 + 相同方式共享（衍生内容必须同样开放） | ⭐ **推荐**，既让所有人可用，又防止内容被闭源独占 |
| CC BY-NC 4.0 | 禁止商用 | ⚠️ 「商用」定义模糊，会误伤学校与教育机构 |

> **注意**：Creative Commons 官方**不建议**将 CC 许可用于代码，所以本仓库会是「代码 MIT + 内容 CC BY-SA 4.0」的双许可结构，须在 `README` 顶部用显著位置说明，并在 `licenses/` 目录下分别放置两份许可全文。

### 4.4 开源前必须完成的四件事

一旦公开发布，**Git 历史会永久留存**，被 fork 的内容无法撤回。所以必须在第一次推送公开仓库之前做完：

| # | 事项 | 方法 |
| --- | --- | --- |
| 1 | **密钥清洁** | 全历史扫描（gitleaks / trufflehog）；确认 `.env` 从未入库；配置 CI 拦截 |
| 2 | **依赖许可扫描** | 逐个核对 npm / pip 依赖许可，产出 `THIRD_PARTY_NOTICES.md`；剔除与 MIT 不兼容的依赖 |
| 3 | **内容来源溯源** | 每一个数据文件标注来源与许可（详见第五章）；**来源不明的数据一律先删除再重建** |
| 4 | **个人信息清洁** | 清除提交历史中的真实姓名、手机号、邮箱、本机路径、内网 IP |

> 一次性数据生成脚本（含本机绝对路径与数据生成方式的）**不得进入公开仓库**，公开前统一清理，见 [06-2 发布与更新流程](../06-工程规范/02-发布与更新流程.md)。

## 五、内容版权：开源化的第一红线

这是本策略中**风险最高、最容易被忽略**的一环。免费开放不等于可以随意用别人的内容——**免费分发同样构成侵权**。

### 5.1 风险分级

| 级别 | 内容类型 | 判定 |
| --- | --- | --- |
| 🟢 低 | 古诗原文（唐宋及以前）、公版古籍正文 | 作者已故远超 50 年，进入公共领域，可自由使用 |
| 🟢 低 | 自编释义、自编写例句、自编题目 | 自有版权，可自由授权 |
| 🟡 中 | 拼音数据、笔顺数据、词典数据 | **取决于来源**，必须逐个核对来源许可（见 5.2） |
| 🟡 中 | 开源 TTS 生成的语音 | 取决于**模型许可**，需核对是否允许再分发产物 |
| 🔴 高 | **教材课文顺序、课文标题、教材生字表** | 出版社享有汇编权与著作权，**必须移除** |
| 🔴 高 | 来源不明的自动填充字库 | 无法溯源 = 无法授权，**必须重建** |
| 🔴 高 | 网络抓取的释义、赏析、译文、练习题 | 默认有版权 |
| 🔴 高 | 商业字体文件、字帖字库 | 字体授权通常不含再分发 |
| 🔴 高 | 未授权配图、影视截图、表情包 | 同上 |

### 5.2 可用数据源白名单

以下是**已核实许可**、可安全用于开源分发的数据源。这是本项目的「合法地基」，优先使用：

| 用途 | 数据源 | 许可 | 注意事项 |
| --- | --- | --- | --- |
| **拼音** | [`mozillazg/pinyin-data`](https://github.com/mozillazg/pinyin-data) | **MIT** | 派生自 Unicode Unihan 数据库（Unicode 许可，宽松）。其 `kMandarin_8105.txt` 正是《通用规范汉字表》8105 字的最常用读音，**恰好匹配小学识字范围**。⭐ 首选 |
| **笔顺图形** | `hanzi-writer-data`（派生自 [`skishore/makemeahanzi`](https://github.com/skishore/makemeahanzi)） | **Arphic Public License**（图形） | 源头是 Arphic Technology 1999 年以 APL 释出的字体。APL 是 copyleft 型：**必须随数据分发 APL 全文（`ARPHICPL.TXT`）并署名 Arphic Technology** |
| 笔顺动画库 | [`chanind/hanzi-writer`](https://github.com/chanind/hanzi-writer) | **MIT**（代码） | 代码 MIT、数据 APL，注意区分 |
| **英文释义** | makemeahanzi `dictionary.txt` | **LGPL v3+** | 派生自 Unihan + CJKlib；LGPL 为文件级 copyleft，**只需保持该文件及其许可独立**，不污染 MIT 代码 |
| **古诗文** | [`chinese-poetry/chinese-poetry`](https://github.com/chinese-poetry/chinese-poetry) | **MIT** | 37 万+ 首（全唐诗 5.5 万、宋诗 26 万、宋词 2.1 万），另含诗经、论语、蒙学（三字经、百家姓、千字文）。有简体分支。**古诗模块的内容底座可直接用它** |
| 多音字/词语读音 | `mozillazg/phrase-pinyin-data` | MIT | 词语级拼音，用于组词注音 |

> ⚠️ **释义不要用 CC-CEDICT**：它是 **CC BY-SA 4.0**，share-alike 具有传导性，会要求衍生数据集也以 BY-SA 分发，对本项目的双许可结构是额外约束。短释义自编更好（也符合小学场景——学术词典释义对儿童过难）。

### 5.3 必须移除的高风险内容

下列高风险内容在内容重建时**已按此处置执行**，现状如下（来源登记见 `content/sources.json`）：

| 资产 | 处置 | 现状 |
| --- | --- | --- |
| 教材映射数据（单元顺序、课文标题、教材生字表） | ⛔ **移除或整体重编** | **已移除**：`content/sources.json` 的 `forbidden` 明确禁止；单元改为**自编**（`content/lessons/units.json`） |
| 历史遗留的自动填充字库 | ⛔ **全部重建** | **已重建**：现字库全部逐条自编（`content/characters/*`），无来源不明条目 |
| 自编字条 / 单元 / 关卡 / 古诗注译 / 识字短文 / 徽章 | ✅ 保留 | 自有版权，均为 CC BY-SA 4.0（逐项登记在 `content/sources.json` 的 `self_authored`） |

**替代方案**：用「**课标字表 + 自编单元**」替代教材映射。

- 字表主线：《义务教育语文课程标准》要求的识字量（小学累计约 3000 字，一、二年级 1600 字），配合 `通用规范汉字表` 一级字表（3500 字）
- 单元划分：按**主题**（自然、身体、家人、动物、数字）或**字频/难度**自编，不照搬教材目录
- 若确实想要「跟课本学」，改为**用户自定义单元**：家长自己勾选字组成单元——**把编排权交给用户，项目不提供教材映射数据**，彻底回避版权问题

### 5.4 署名与许可文件要求

分发型仓库必须包含：

```
licenses/
├── LICENSE-MIT                 # 代码
├── LICENSE-CC-BY-SA-4.0        # 内容
├── ARPHICPL.TXT                # Arphic Public License 全文（随笔顺数据分发，APL 强制要求）
├── LGPL-3.0.txt                # 随 dictionary.txt 分发
└── THIRD_PARTY_NOTICES.md      # 逐项列出：来源、许可、用途、署名
```

`THIRD_PARTY_NOTICES.md` 的每条至少包含：来源项目名、仓库地址、许可名称、使用范围、署名文本。

### 6.2 「clone 即跑」硬标准

任何贡献者克隆仓库后，必须能在**三条命令内跑起来**，且满足：

- ✅ 无需任何 API Key、无需注册任何第三方账号
- ✅ 无需任何付费服务
- ✅ **本地自足** —— 按 `deploy/` 的 compose 一键起 MongoDB 与 API，不依赖任何外部服务
- ✅ 首次安装依赖需联网，之后可在本机完整运行
- ❌ 不允许出现「请先配置你自己的某某服务」这类前置步骤

这条标准会持续约束技术选型——**任何需要密钥的能力都不能进主流程**。这也是本项目坚持把语音处理放在浏览器端、把云端评测降为可选增强的根本原因，而非单纯为了省钱。

### 6.3 内容贡献流程（比代码贡献更重要）

```
贡献者 → 填写 Issue 模板（或直接改 JSON）
      → 提交 PR，只改 content/ 下的 JSON
      → CI 自动校验：JSON Schema 通过、拼音与字库一致、无重复条目、
                    释义长度合规、古诗原文与数据集比对一致
      → 维护者人工复核（内容质量）
      → 合并，自动部署
```

**关键设计**：内容与代码**物理分离**（`content/` 独立目录），这样内容贡献者不需要懂 Vue，也不需要在本地跑起整个应用就能贡献——只需编辑 JSON 并通过 CI 校验。这是把内容产能打开的唯一可行方式。

### 6.4 维护者负担的现实评估

| 事项 | 期望 |
| --- | --- |
| Issue 响应 | 无法承诺 SLA，README 明确说明「个人业余维护」 |
| PR 审核 | 内容审核可下沉给可信贡献者（`content-reviewers` 团队） |
| 版本发布 | 无发布压力，持续部署 |
| 长期风险 | 若维护者退出，项目应仍可被 fork 继续——这就是为什么内容与代码分离、构建无密钥 |

## 七、合规成本为什么反而降低了

这是轻量化服务端 + 免费模式的一个**意外收益**，值得明确指出：

| 合规项 | 传统云端产品 | 本项目（免费 + 轻量服务端） |
| --- | --- | --- |
| 监护人同意 | 必须（收集儿童个人信息） | **简化为隐私说明**——仅收集昵称与年级，不上传实名信息 |
| 儿童个人信息出境 | 必须评估 | **极简**（仅昵称与年级；云档案端到端加密） |
| ICP 备案 | 必须 | **取决于服务器位置**：境外免备案；境内必须备案（**个人主体可做非经营性备案**，见 7.1） |
| 等保备案 | 视规模 | **不需要**（无实名账号、无支付；仅邀请码匿名身份下的最小信息） |
| 软著 | 建议（上架需要） | 可选（无上架行为） |
| 未成年人模式 | 平台强制 | 保留为体验功能（时长自控） |
| 内容审核留痕 | 必须 | 转为 **PR 审核记录**（Git 天然留痕，反而更好审计） |
| 广告/内购合规 | 高风险 | **不存在** |
| 网络安全等级保护（含实名） | 强制 | **不适用**——无实名账号、无支付、无用户生成内容 |

### 7.1 服务器位置与备案决策

**结论：起步用境外或静态托管（免备案）；有稳定用户量后再评估境内自托管 + 个人备案。** 三种部署路径的取舍与备案要点（含「ICP 备案属个人主体即可完成的非经营性备案」）见 [02-3 存储与后端策略](../02-系统架构/03-存储与后端策略.md) 第九章。

> ⚠️ **但有两项不能省**：① **隐私说明必须保留**并如实披露托管方与自建服务记录的访问日志（IP、UA）；② **许可证合规必须做**（署名、许可全文随分发），这是开源项目的法定义务，不是可选项。

## 八、成本与可持续性

### 8.1 可持续路径

| 路径 | 说明 | 触发条件 |
| --- | --- | --- |
| **自托管云端后台**（✅ 已部署） | 用已有服务器承载内容管理、匿名统计、邀请码校验、可选同步；月成本≈0 | **已具备** |
| 纯社区运营 | 靠贡献者补内容，维护者只做审核 | 默认 |
| 接受捐赠 | 覆盖域名、备案、少量素材采购（如真人配音） | 有一定用户量后；**不接受广告与付费墙** |

### 8.2 成本控制的三条硬纪律

| 纪律 | 原因 |
| --- | --- |
| **能静态化的就静态化** | 静态托管零成本、零运维、零备案；只有"必须动态"的功能才上服务器 |
| **业务数据一律服务端** | 学习数据、档案、进度、复习状态集中在 MongoDB，保证跨设备一致与口径统一；纯音处理（F0 / VAD）留在浏览器端 |
| **不引入"没它不行"的付费依赖** | 避免"某个付费服务挂了/停了 → 功能不可用"的单点依赖（见 [2.5](#25-付费与升级能力本版本不做)） |

### 8.3 最大的可持续性风险

**不是钱，是内容产能与维护者精力。**

- 代码是一次性投入，内容是需要长期维护的资产（错别字、读音争议、版本升级）
- 应对：① 内容与代码分离，降低贡献门槛；② 建立 `content-reviewers` 协作角色；③ **内容范围宁小勿大**——宁可 800 字做到零错误，不要 3500 字错漏百出，用户对错字的容忍度远低于对字数少的容忍度

| # | 事项 | 结论 |
| --- | --- | --- |

| 3 | 开源时机 | 尽早开源（首版可用即开源） |

| 9 | 云端后台 | 只做内容管理 + 匿名统计 + 邀请码校验 + 可选同步，不做实名账号与支付（见 [02-3 存储与后端策略](../02-系统架构/03-存储与后端策略.md) 第四、七章） |
