# 05-1 内容管理与用户管理体系

> 本文档定义**内容管理**与**身份管理**两套能力：内容以「内容即仓库（Git）」为主路径、以单管理员后台（`apps/admin`）为可视化补充；身份为「邀请码 + 自设密码」，单管理员、无多角色。
>
> 管理能力分两条路径：**内容管理**以「**内容即仓库**」（JSON + CI 校验 + PR 评审）为主路径，服务器上的**单管理员内容后台**（`apps/admin`，可部署）为可视化补充；**身份管理**采用**邀请码 + 自设密码**，不需要手机号 / 微信 / 企业主体。管理能力是 P0，**不依赖一个"云端多角色后台"**。详见 [02-3 存储与后端策略](../02-系统架构/03-存储与后端策略.md)、[02-5 邀请码身份与准入体系](../02-系统架构/05-邀请码身份与准入体系.md)。

---

## 一、内容管理为什么是 P0

内容管理让内容脱离研发独立迭代（项目定位与现状见 [01-1 项目概述与定位](../01-产品规划/01-项目概述与定位.md)）。原因是：

| 没有内容管理能力的后果 | 具体表现                    |
| ----------- | ----------------------- |
| 内容扩张成本极高    | 每加 100 个汉字都要研发改代码、测试、发版 |
| 内容无法审核      | 面向儿童的内容没有审核记录，合规风险      |
| 无法快速纠错      | 发现一个释义写错，要等下一个发版周期      |
| 教研无法参与      | 内容生产完全压在研发身上            |
| 素材管理混乱      | 音频、图片靠文件名和口头约定管理        |

**判定标准**：当「非研发人员能独立上架一个新字，且改错别字不需要发版」时，这一期才算完成。

### 1.1 内容管理的两种形态

| 形态                | 载体                                  | 门槛       | 成本  | 何时用                          |
| ----------------- | ----------------------------------- | -------- | --- | ---------------------------- |
| **① 内容即仓库**（主路径）  | `content/` 目录的 JSON + CI 校验 + PR 评审 | 会编辑文本即可  | ¥0  | **默认**；外部贡献者贡献内容的主通道         |
| **② 自托管内容后台**（增强） | 部署在自己服务器的单管理员 Web 后台                | 需服务器（已有） | ≈¥0 | **可部署**：内容量大后提升编辑效率；非技术成员参与时 |

> **两者共用同一份 JSON Schema 与数据模型**（[03-2 数据字典](../03-数据设计/02-数据字典.md)）。后台只是「可视化编辑器 + 快捷操作」，产出物仍是仓库里的 JSON（或同步写入 MongoDB 后可导出为 JSON）。**不引入第二套数据模型，是这套设计能保持简单的关键。**

### 1.2 形态 ① 内容即仓库的运作方式

```
贡献者 → 填 Issue 模板（或直接改 JSON）
      → 提交 PR，只改 content/ 下的 JSON
      → CI 自动校验（合并前）：
          · JSON Schema 通过
          · 拼音与字库一致（对照 pinyin-data）
          · 无重复条目（同一 char 只有一条）
          · 组词必含本字、释义长度合规
          · 古诗原文与 chinese-poetry 数据集比对一致
          · 数据来源已在 sources.json 登记
      → 维护者 / content-reviewer 人工复核（内容质量、适龄性）
      → 合并 → 自动部署
```

| 需要一个后台的功能 | Git 如何满足                 |
| --------- | ------------------------ |
| 版本历史与回滚   | `git log` / `git revert` |
| 审核工作流     | PR 的 Review + Approve    |
| 变更审计留痕    | 提交历史（含谁、何时、改了什么）         |
| 权限控制      | `CODEOWNERS` + 仓库权限      |
| 草稿与发布     | 分支 + Merge               |
| 导出与备份     | `git clone`              |

> **为什么这是对的**：Git 天然具备版本、评审、回滚、权限、审计五项能力——这些在自研后台上每一项都要单独开发与维护。**把内容放在 Git 里，等于白拿一套内容管理系统。**

### 1.3 形态 ② 自托管内容后台的边界

| 做                                       | 不做                               |
| --------------------------------------- | -------------------------------- |
| 内容的在线 CRUD、批量导入、质量检查                    | 多角色权限（**只做单管理员**）                |
| 邀请码的批量生成、用量查看、吊销                        | 用户画像与权益管理                        |
| 内容变更写入 `audit_logs` 或直接提交到仓库            | 面向外部用户的注册与登录                     |
| **站点运行配置**（注册准入 / 默认学习目标 / 玩法开关），改完立即生效 | 短信/微信登录、单点登录                     |
| 简单密码鉴权（或 Basic Auth + IP 白名单）           | 部署项（端口 / 密钥 / DB 地址）——那些在 `.env` |

> ⚠️ **纪律**：后台是**单人使用的工具**，不是「系统的管理端」。**任何为了"将来多人协作"而引入的复杂度，都会被维护成本反噬**——需要多人协作时，用 Git 的 PR 流程，那比重构后台便宜得多。

**站点运行配置的两个分组（不要混淆）**：

| 分组         | 生效范围                     | 内容                           |
| ---------- | ------------------------ | ---------------------------- |
| `defaults` | **新建档案时**写入初值，之后每个孩子可各自改 | 每日新学字数、每日复习字数、每日时长上限         |
| `gameplay` | **全体孩子**，客户端每次启动读取       | 阶段检测间隔、题型开关、跟读、阅读承接、字源图、朗读语速 |

`gameplay` 是**客户端玩法的唯一真源**——客户端不再自带一份写死的玩法表，改这里等于给所有孩子换一套玩法。字段表与三条纪律见 [01-5 §五](../01-产品规划/05-玩法与复习机制设计口径.md)。配置落 MongoDB 单文档、进程内读一次缓存，**改完无需重启**（见 [06-2 发布与更新流程](../06-工程规范/02-发布与更新流程.md)）。

## 二、后台角色与权限

后台为**单人使用**，只有「维护者本人」一个使用者，因此**不做多角色、不做 RBAC、不引入权限矩阵**——这是**本期范围决定**（单人维护下多角色是过度设计，**与企业主体无关**）；需要多人协作时用 Git 的 PR 流程（`CODEOWNERS` 授权内容目录、PR 标签区分分工）。

下表把两类「不启用」的能力放在一起（**都只保留契约与开关，默认关闭、不打包**），但原因不同——**多角色 RBAC 是范围取舍，其余是合规约束**：

| 能力 | 开关名 | 契约位置 | 状态 |
| --- | --- | --- | --- |
| 后台多角色 RBAC（六角色 + 权限矩阵 + `admin_roles` / `admin_users` 集合） | — | 03-1 / 03-2 不登记；04-1 §10 预留接口 | ⛔ **本期不做**（与企业主体无关） |
| 手机号 / 微信账号 | `enableAccountAuth` | 04-1 §10 预留接口 | ⛔ 需企业主体，不启用 |
| 支付与订阅 | `enablePayment` | 04-1 §10 预留接口 | ⛔ 需企业主体，不启用 |
| 微信小程序 | `enableMiniprogram` | 02-3 存储与后端策略 | ⛔ 需企业主体，不启用 |
| iOS / Android App | `enableNativeApp` | 02-3 存储与后端策略 | ⛔ 需企业主体，不启用 |

> 「掩藏」的准确含义与实现机制（能力开关、开关默认关且不可被远端打开）见 [02-3 存储与后端策略](../02-系统架构/03-存储与后端策略.md)。

## 三、内容管理（以字库为核心）

后台的内容能力由 `apps/api/app/repositories/content_registry.py` **数据驱动**：一套通用 CRUD（`/admin/content/{collection}`）覆盖全部内容类型，新增一类内容只需在注册表加一行，视图与控制器不改。字库只是其中**最重要的一类**，古诗 / 故事 / 单元 / 关卡 / 识字短文 / 徽章与之同构维护。

### 3.1 内容类型与相互关系

六类内容 + 素材，集合名与仓库文件以注册表的 `IMPORT_SOURCES` 为准：

| 内容类型 | 集合 | 仓库文件 | `_id` 规则 | 创建必填 |
| --- | --- | --- | --- | --- |
| 汉字 | `characters` | `content/characters/grade-{1..6}.json` | `ch_<码点 hex>` | `char` |
| 古诗 | `poems` | `content/poems/required-75.json` | `poem_<slug(title)>` | `title` |
| 单元（自编） | `curriculum_units` | `content/lessons/units.json` | `unit_<unit_code>` | `title`、`unit_code` |
| 关卡 | `lessons` | `content/lessons/lessons.json` | `lesson_<slug(title)>` | `title` |
| 识字短文（含儿歌） | `stories` | `content/stories/stories.json` | `story_<slug(title)>` | `title`、`text` |
| 徽章 | `badges` | `content/badges/badges.json` | `badge_<code>` | `code`、`title` |
| 素材 | `assets` | `content/assets/**` | `as_<sha1(storage_key)>` | — |

> ⚠️ **集合名与展示名不一致**：孩子端地图第三条线叫「识字短文」，对应的内容类型是
> `stories`（track key `story`，子类型 `story` 短文 / `rhyme` 儿歌）——别按名字去猜集合名。

**这些内容是相互关联的**——字库是底座，古诗 / 短文 / 单元 / 关卡都引用它：

| 引用方 | 引用字段 | 指向 | 作用 |
| --- | --- | --- | --- |
| 单元 | `character_ids` | `characters._id` | 按主题 / 难度把字编成单元 |
| 关卡 | `character_ids` / `poem_id` / `unit_id` | `characters` / `poems` / `units` | 一关 = 一组字 + 可选一首诗 + 所属单元 |
| 古诗 | `key_characters` / `unit_ref` | `characters` 字面 / 单元 | 诗内生字标注，可反向跳到字卡 |
| 识字短文 | `highlight_characters` / `unlock_after_lesson_ids` | `characters` 字面 / `lessons._id` | 高亮已学字、按关卡解锁 |

> ⚠️ 引用不到时导入**不会报错**（字段只是字符串 / 数组），但客户端会缺图或缺音——所以导入后要跑 [3.4 内容质量检查](#34-内容质量检查项) 兜底。**推荐导入顺序**：`characters` → `curriculum_units` → `lessons` → `stories` / `poems` → `badges`。

**通用功能清单**（各类型共用同一套页面与接口，差异由注册表声明）

| 功能 | 说明 | 优先级 |
| --- | --- | --- |
| 列表与筛选 | 按各类型 `filters` 声明的字段筛选（如汉字按年级 / 状态 / 难度 / 标签 / 是否有音频配图） | P0 |
| 搜索 | 按各类型 `searchable` 声明的字段搜索（如汉字按 字 / 拼音 / 释义 / 组词） | P0 |
| 单条编辑 | 字段表单 + 实时校验（表单与模板下载共用注册表的字段定义） | P0 |
| **批量导入** | 按集合的 JSON 导入（仓库 / 上传），幂等 upsert、支持预检 —— 见 [3.3](#33-批量导入设计提效关键) | P0 |
| 批量导出 | 按集合导出 JSON，便于线下校对与回灌仓库 | P0 |
| 批量操作 | 批量改状态、批量打标签、批量绑定素材 | P1 |
| 提交审核 | 草稿 → 待审 | P0 |
| 审核通过 / 驳回 | 待审 → 已上架 / 驳回（需填原因） | P0 |
| 质量检查 | 自动扫描缺失字段、异常数据、引用失配 | P1 |
| 版本历史与回滚 | 查看变更、回滚到历史版本 | P2 |


### 3.2 编辑表单设计要点

表单按字段分组，避免一屏塞满：

| 分组     | 字段                                         |
| ------ | ------------------------------------------ |
| **基础** | 汉字、拼音、声调、是否多音字、多音字读音表                      |
| **字形** | 部首、笔画数、结构、笔顺数据                             |
| **释义** | 释义、组词、例句、字源说明                              |
| **素材** | 配图、读音音频、笔顺文件                               |
| **分类** | 年级、学段、难度、标签、形近字、反义/近义                      |
| **字源** | **字源图（`glyph`）** —— 象形 emoji，作为「看图选字」的题干主图 |
| **流程** | 状态、版本、创建人、审核人                              |

> ⚠️ **字源图必须是字义联想**（水 → 💧、山 → ⛰️），不是任意装饰图。图不对义会把注意力从汉字上带走，等于白做一道题。需要更精细的配图时走「素材」绑定 `image_ref`，与 `glyph` 并存、客户端优先图片。口径见 [01-5 §5.3](../01-产品规划/05-玩法与复习机制设计口径.md)。

**实时校验规则**

| 校验项   | 规则                         | 提示                   |
| ----- | -------------------------- | -------------------- |
| 汉字    | 1 个字符，且为 CJK 汉字            | 红字提示                 |
| 拼音    | 合法拼音格式，含声调符号               | 格式错误提示               |
| 声调    | 0–4                        | —                    |
| 多音字   | `is_polyphone=true` 时读音表非空 | 阻断保存                 |
| 笔画数   | 1–64                       | —                    |
| 释义    | ≤ 40 字，不含生僻词               | 超长提示                 |
| 组词    | 3–5 个，每个必须含本字              | **关键校验**：组词不含本字是常见错误 |
| 例句    | 2–3 句                      | —                    |
| 配图/音频 | 上架前必须绑定                    | 上架时阻断                |

### 3.3 批量导入设计（提效关键）

这是内容运营用得最多的功能。**当前实现是一套「按集合的 JSON 导入」**——覆盖七类内容与素材，与「内容即仓库」共用同一份数据模型，因此「仓库里的 JSON」就是导入格式的唯一定义。

**三条导入路径**

| 路径 | 入口 | 说明 |
| --- | --- | --- |
| 仓库驱动（主路径） | 改 `content/**/*.json` → PR → CI 校验 → 合并 | 贡献者与内容团队的主通道；**JSON 格式本身就是模板** |
| 后台「从仓库导入」 | `POST /admin/content/import`，`source: "repo"` | 把容器内 `content/*.json` 灌进 MongoDB，**幂等 upsert，可随时重跑**（部署初始化、内容更新都走它） |
| 后台「上传导入」 | `POST /admin/content/import`，`source: "upload"` | 上传按集合分组的 JSON：`payload: { "characters": [...], "poems": [...] }`，并用 `collections` 指定只导哪些集合 |

**导入流程**

```
预检（GET /admin/content/import/preview：每个来源文件是否存在 / 多少条 / 库里已有多少条）
→ 选择集合（不选 = 全部）
→ dry_run=true 试跑（只统计、不落库）
→ 确认后正式导入（dry_run=false）
→ 幂等 upsert → 重算 manifest 并自动进一个小版本（content_version）
→ 返回报告：逐集合 total / created / updated + 总数
```

**报告与「部分成功」**

导入是**逐集合 upsert**，结果逐集合给 `total / created / updated`；`dry_run=true` 只回统计不落库，先用它确认再正式导入。**任何一步失败都要能看到是哪个集合、哪几行**——不允许「导了一半却不告知哪些没进去」。

**模板下载：按类型下发，不是固定列**

后台「下载模板」走 `GET /admin/content/{collection}/template`，返回**字段说明 + 一条可直接照抄的示例**，来源是注册表的 `field_docs` / `template_sample`，因此「页面展示的字段说明」与「后端真正校验的必填项」永远同一份来源。

| 类型 | 是否提供模板 | 说明 |
| --- | --- | --- |
| 汉字 / 古诗 | ✅ | 字段多、派生字段多，模板最有用 |
| 单元 / 关卡 / 识字短文 / 徽章 | — | 字段少，照 `content/*.json` 现有条目写即可 |

> 是否有模板由注册表里该类型有没有 `field_docs` 决定：没有字段说明的类型**不给按钮**，
> 避免下载到一个空模板。

**派生字段：导入时按正文重算，手改无效**

| 字段 | 所属 | 由什么派生 |
| --- | --- | --- |
| `pinyin_plain` | 汉字 | `pinyin` 去声调 |
| `word_count` | 识字短文 | 正文逐字 |
| `_id` | 各类型 | `id_source` 字段（如古诗用 `title`）或码点；**改来源字段等于换一条记录** |

> ⚠️ 手改派生字段是真实会踩的坑：`word_count` 与正文不一致，阅读难度估计就会失真。


### 3.4 内容质量检查项

自动扫描以下问题并生成报告：

| 检查项                      | 严重级别 |
| ------------------------ | ---- |
| 组词中不含本字                  | 🔴 高 |
| 拼音与汉字不匹配                 | 🔴 高 |
| 必填字段缺失                   | 🔴 高 |
| 已上架但无音频/配图               | 🟡 中 |
| 例句含超纲词汇                  | 🟡 中 |
| 释义过长（> 40 字）             | 🟢 低 |
| 重复汉字（同一 char 多条）         | 🔴 高 |
| 声调与拼音不符（如 `shuǐ` 标成 2 声） | 🔴 高 |
| 引用失配（如短文 `highlight_characters` 指向不存在的字） | 🔴 高 |

## 四、古诗管理

### 4.1 功能清单

| 功能    | 说明                          |
| ----- | --------------------------- |
| 古诗列表  | 按年级、主题、来源（课标必背 / 蒙学 / 拓展）筛选 |
| 新增/编辑 | 含逐句注音、逐句释义、赏析、背景            |
| 注音校验  | **自动校验注音字数与诗句字数是否一致**       |
| 重点字关联 | 关联到汉字主表，支持一键跳转              |
| 音频绑定  | 上传朗诵音频                      |
| 批量导入  | 支持批量导入                      |
| 发布管理  | 草稿/待审/上架                    |

### 4.2 注音校验（易错点）

古诗录入最易出错的地方是**注音字数与诗句字数不匹配**（多音字、标点处理不当）。编辑器应：

1. 用户输入诗句原文后，自动按字切分
2. 注音输入框按字数自动生成对应数量的输入位
3. 实时比对字数，不一致时高亮提示
4. 提供"按拼音自动填充"辅助（用拼音库），再由人工校正

## 五、素材管理

### 5.1 设计目标

素材必须是有版权授权、来源可溯源的配图、读音音频与笔顺数据，且要能**批量关联**到内容。

### 5.2 功能设计

| 功能       | 说明                                                     |
| -------- | ------------------------------------------------------ |
| 上传       | 支持批量上传，自动生成校验值与缩略图                                     |
| 命名规范     | 音频 `audio/char/{char}.mp3`，图片 `image/char/{char}.webp` |
| **自动匹配** | 上传时按文件名自动匹配汉字并建议绑定（如 `水.mp3` → 汉字「水」）                  |
| 批量绑定     | 选中多个素材，批量绑定到对应汉字/古诗                                    |
| 引用检查     | 删除前检查是否被引用，被引用则阻断                                      |
| 版权信息     | **上传时必须填写来源与授权类型**，可关联授权文件                             |
| 试听/预览    | 音频可试听，图片可预览                                            |
| 替换       | 替换素材时，所有引用方自动生效（因为内容表只存 `_ref`）                        |

### 5.3 素材-内容解耦的价值

内容表存 `image_ref` / `audio_ref` 而非 URL，带来的好处：

- 替换配音：上传新音频 → 绑定 → 全部关联汉字自动更新，**无需修改任何内容记录**
- CDN 切换：只改 `assets.url`，内容表不动
- 批量换图风格：按 `subtype` 批量替换

## 六、身份与账号管理（✅ 邀请码形态）

> 详细的身份模型与安全设计见 [02-5 邀请码身份与准入体系](../02-系统架构/05-邀请码身份与准入体系.md)。本节只讲「后台里要管什么」。

### 6.1 邀请码管理（核心）

| 功能    | 说明                                                         |
| ----- | ---------------------------------------------------------- |
| 批量生成  | 指定数量、批量名、有效期、`max_uses`，一次生成一批                             |
| 码的展示  | ⚠️ **完整码仅在生成时显示一次**，之后只保留 `code_hint`（如 `HANZI-4K9F-****`） |
| 用量查看  | 每个码已用次数、绑定账号数、最近使用时间                                       |
| 吊销    | 立即作废某个码（`status: revoked`），已注册账号不受影响                       |
| 批次管理  | 按批次统计（如「首轮内测」用了多少、激活率如何）                                   |
| 离线码签发 | 用私钥签发 Ed25519 签名码（用于未联网环境签发邀请码）                            |

### 6.2 匿名账号管理

| 功能     | 说明                                       | 注意                          |
| ------ | ---------------------------------------- | --------------------------- |
| 账号列表   | 列出 `accounts`（家庭昵称、创建时间、最近登入、状态）         | **没有手机号、邮箱、真实姓名可查**——这是设计使然 |
| 账号状态   | 禁用 / 启用（处理滥用）                            | 禁用后该账号无法登入、无法访问其云端档案        |
| 重置密码   | **不做自助重置**（无手机号无法验证身份）；仅支持用户用**恢复码**自行重置 | 不要提供「管理员代改密码」，那会绕过用户主权      |
| 云端数据删除 | 处理「注销并删除云端数据」请求                          | **必做**（合规要求）                |
| 邀请关系查看 | 该账号来自哪个邀请码                               | 用于排查滥用来源                    |

### 6.3 后台不做的事

后台**不做**用户画像与标签、用户权益管理；**不做**「重置学习进度」——进度属于孩子，改由导出 / 导入让用户自助；**不展示**逐题明细与答题原文——报告只给聚合值（见 §8.3）。

允许下钻的边界是**账号 → 聚合**这一层：看得到"这个账号下有几个档案、各认了多少字、掌握率多少、最近一周练了多少题"，看不到"哪个字答错了、错了几次"。前者是家长真正看得懂的，后者既无必要又是隐私风险。

### 6.4 隐私约束（重要）

| 约束           | 实现方式                                                              |
| ------------ | ----------------------------------------------------------------- |
| 服务端不存身份信息    | `accounts` 只有 `invite_code_hash` + `pin_hash` + 自拟 `display_name` |
| **不存明文码与密码** | 一律 `sha256` / `argon2id` 哈希                                       |
| 儿童数据默认不上云    | 云档案**默认关闭**；开启时**默认端到端加密**，服务端只见密文                                |
| 后台操作留痕       | 邀请码生成/吊销写入 `audit_logs`                                           |
| 无「客服查看用户」权限  | 因为没有可查看的个人信息——这本身就是最强的隐私保护                                        |

> **合规依据**：本项目**不收集儿童个人信息**，因此「儿童个人信息保护」的义务大幅简化。但**数据上云告知与删除权**（R-06）与**邀请码安全设计**（R-07）仍必须做，见 [01-3 2.7](../01-产品规划/03-功能清单与优先级路线图.md)。

        │  draft  │ 草稿（运营编辑中）
        └────┬────┘
             │ 提交审核
             ▼
    ┌─────────────────┐

         │       │
    驳回 │       │ 通过
         ▼       ▼
    ┌────────┐ ┌───────────┐

    └────────┘ └─────┬─────┘
                     │ 下架
                     ▼

               └──────────┘

### 7.2 审核要点清单

审核员需逐项确认（作为审核表单的勾选项）：

- [ ] 汉字本身正确，无错别字
- [ ] 拼音与声调准确
- [ ] 释义适合目标年级理解
- [ ] 组词均为常用词，且包含本字
- [ ] 例句通顺、价值观正确
- [ ] 配图与字义相符、画面适龄
- [ ] 音频读音标准、无明显噪音
- [ ] 不含任何广告或外部导流信息

> **留痕要求**：审核通过/驳回必须记录审核人、时间、意见，写入 `audit_logs` 并在内容文档上回写 `reviewed_by` / `reviewed_at`。

## 八、运营数据看板

### 8.1 核心指标

| 分类     | 指标                            | 说明     |
| ------ | ----------------------------- | ------ |
| **用户** | DAU / MAU、新增用户、留存率（次日/7日/30日） | 基础健康度  |
| **学习** | 人均日学习时长、人均日学习字数、连续学习天数分布      | 产品价值验证 |
| **效果** | 平均正确率、掌握率、错题订正率               | 学习效果   |
| **内容** | 内容覆盖率、各年级字库完成度、素材完备率          | 内容健康度  |
| **质量** | 内容待审量、审核时效、被驳回率               | 运营效率   |

### 8.2 内容健康度看板（运营最常用）

运营每天要看的是：**内容到底做到哪一步了**。

```
字库完成度
├── 一年级  480 / 500   [=========-] 96%   ✅ 可发布
├── 二年级  320 / 500   [======----] 64%   ⚠️ 进行中
├── 三年级  120 / 500   [==--------] 24%   🔴 严重不足
└── ...

素材完备率
├── 音频    920 / 3000  [===-------] 31%
├── 配图    610 / 3000  [==--------] 20%
└── 笔顺   1400 / 3000  [=====-----] 47%

古诗完成度
├── 课标必背  42 / 75   [=====-----] 56%
└── 拓展     0 / 50    [----------]  0%
```

这类看板能直接回答"现在能不能上线"、"下一步该补什么"。

### 8.3 账号级学习报告（聚合下钻）

在用户列表里点开某个账号，看到的是**聚合值**，不是逐题明细。字段与口径见 [01-5 §六](../01-产品规划/05-玩法与复习机制设计口径.md)，接口为 `GET /admin/users/{account_id}/report?days=7`。

| 分组     | 指标                                            |
| ------ | --------------------------------------------- |
| **进度** | **已认汉字 / 掌握汉字 / 掌握率** —— 三个数必须同时出现，尤其前两个要分列   |
| 状态分布   | 复习中 / 学习中 / 待清错题                              |
| 活跃度    | 连续学习天数、最近一次学习                                 |
| 覆盖量    | 完成关卡、古诗诵读、获得徽章                                |
| 质量     | 答题正确率                                         |
| 趋势     | 按天：柱高为**题量**、颜色为**正确率**（≥80% / 60–79% / <60%） |

> ⚠️ **"已认"与"掌握"必须分列**，这是整份报告里最有用的一处：家长据此能分辨"这字只是见过一面"和"这字已经稳了"，复习该往哪儿使劲才有依据。两者的判定规则见 [01-5 §三](../01-产品规划/05-玩法与复习机制设计口径.md)。

### 9.1 账号可编辑字段白名单

后台能改账号的字段**只有三个**：`display_name` / `avatar_key` / `access_tier`。
  
请求模型用 `extra="forbid"`，越权字段直接 422 而不是静默丢弃。

| 字段                   | 为什么不提供编辑                            |
| -------------------- | ----------------------------------- |
| `username` / `phone` | 是**登录标识**，各自带唯一索引；改动等于换账号，历史登录记录对不上 |
| `passcode_hash`      | 密码必须经 Argon2 重新计算，不能明文直传            |
| `invite_code_hash`   | 邀请码即登录凭据，改它等于换邀请码                   |
| `sync_key_salt`      | 端到端加密密钥盐，一改就再也解不开历史密文               |
| `role`               | 单管理员体系没有多角色（本章 §1.3），开放它等于凭空造 RBAC  |

**注销**是软删：释放邀请码占用、使所有会话失效，但**保留孩子档案与学习数据**——
  
注销的是「登录资格」不是「学习记录」，这是儿童数据最小化的底线。

### 9.2 内容维护页的模板下载

字库 / 短文 / 古诗三类内容都提供「下载模板」，返回**字段说明 + 一条可直接照抄的示例**。
  
模板由后端从 `content_registry` 的 `field_docs` 生成，因此**页面展示的字段说明
  
与后端真正校验的必填项永远是同一份来源**，不会文档改了校验没改。

模板把字段分为三类，**派生字段必须标出来**（`derived: true`）：

| 类别     | 例子                                                | 说明                |
| ------ | ------------------------------------------------- | ----------------- |
| 必填     | `char` / `title` / `text`                         | 缺了导入直接失败          |
| 选填     | `pinyin` / `appreciation`                         | 不填不影响导入，但影响客户端体验  |
| **派生** | `character_chars` / `word_count` / `pinyin_plain` | **导入时按正文重算，手改无效** |

> ⚠️ 派生字段不标出来是真实会踩的坑：运营手改 `character_chars` 后与正文不一致，
>   
> 覆盖率算错，客户端会把满篇生字的短文推给孩子。

## 十、技术实现建议

| 项           | 建议                                                                |
| ----------- | ----------------------------------------------------------------- |
| **形态 ① 工具** | Node 脚本 + `ajv`（JSON Schema 校验），可被 CI 直接调用；编辑器用纯前端（Vite 单页）读写本地文件 |
| 前端框架（形态 ②）  | Vue 3 + Element Plus（后台无需定制视觉，追求效率），**部署在与主应用相同或独立的路径下**          |
| 表格          | 支持列配置、行内编辑、虚拟滚动（字库有 3000+ 行）                                      |
| **表单**      | ⭐ **用同一份 JSON Schema 驱动表单生成**——与 CI 校验共用，**保证校验规则只有一处定义**         |
| 富文本         | 故事编辑用轻量富文本（避免引入过重编辑器）                                             |
| 文件上传        | 分片上传 + 断点续传（音频文件较大）；优先提交到仓库而非对象存储                                 |
| **鉴权**      | ⭐ **单管理员密码（argon2id 哈希）+ 登录限流 + 可选 IP 白名单**。**不做 RBAC、不做多角色**     |
| 审计          | 邀请码生成/吊销、账号禁用、云端删除等写操作记录 `audit_logs`；内容变更走 Git 提交历史              |
| 导出          | 提供「导出全部内容为 JSON」一键下载，便于备份与导入还原                                    |

> ⚠️ **两个最容易做错的地方**：
>
> 1. **表单校验与 CI 校验各写一套** → 必然漂移（后台能存进去、CI 却报错）。**必须共用同一份 JSON Schema。**
> 2. **为了"将来多人用"而做 RBAC** → 维护成本高、收益低。**需要多人协作时用 Git 的 PR 流程。**
