# 02-4 本地优先与后端策略

> 本文档回答一个问题：**在「不做需要企业主体的能力、上线前全部免费开放、项目可能开源，但已有服务器且可部署云端后台」的条件下，系统该怎么搭？**
>
> 结论：**本地优先（Local-First）+ 内容即仓库（Content-as-Repo）+ 后端分层**——
> 学习数据与核心体验留在本地；**云端后台可以实际部署**，承担「内容管理、匿名统计、可选同步」这类**轻**职责；
> 需要企业主体的能力（账号、支付、小程序、App）**写代码但不启用**，由能力开关关闭。

---

## 一、约束推导

### 1.1 六条约束

六条前置约束的完整定义见 [docs/README.md 第一章](../README.md#一六条前置约束决定一切)。由此推出的架构是：**本地优先 + 内容即仓库 + 可部署的云端后台（非必需依赖）+ 企业能力掩藏**。

> ⚠️ **第 3、4、6 条必须一起读**：云端后台**要真实部署**，但它**不能成为开源主流程的必需依赖**——所以它存在的形式是「**默认可用、故障可降级、缺失不阻塞**」，而不是「没有它就打不开」。唯一真正的边界是**企业主体**：账号、支付、短信、小程序、App 上架仍然写代码但不启用。

### 1.2 关键区分：把三类事情分开

这是最容易搞混的地方——「不做企业主体的事」**不等于**「不能有服务器」。

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| **需要企业主体** | 支付、微信登录、手机号账号、小程序、App 上架、类目资质 | ⛔ **不启用**：代码 + 契约 + 开关，掩藏 |
| **不需要主体，但需要服务器或花钱** | 内容管理后台、匿名统计、云端家庭档案、云端语音评测、对象存储 | ✅ **可做**，优先免费方案；付费须满足四原则 |
| **既不需要服务器也不需要钱** | 本地存储、本地模型、静态内容、复习算法、F0 提取 | ⭐ **首选**，零成本零运维零合规负担 |

```
                    ┌──────────────────────────────────┐
                    │  判断顺序：能不能放本地？          │
                    └───────────────┬──────────────────┘
                                    │
                  ┌─────────────────┼─────────────────┐
                  ▼                 ▼                 ▼
              能 → 放本地       不能 → 需要服务器？   需要企业主体？
              （首选）              │                   │
                                  ▼                   ▼
                          有服务器 → 可做         ⛔ 掩藏 + 预留
                          （优先免费方案）
```

### 1.3 这个选择放弃了什么（诚实清单）

| 放弃 | 代价 | 缓解 |
| --- | --- | --- |
| 实名账号体系 | 无法用手机号/微信识别用户 | 用**邀请码身份 + 云端家庭档案**承载跨设备同步（见第六章） |
| 零后端 | 需自行运维云端后台 | 服务器已有；后端只做轻职责，单机部署，**故障时前端功能完整** |
| 云端音素级评测（默认） | 无精细发音反馈 | 本地声调判定为主路径；云端评测可选开启 |
| 全离线 | 首次访问依赖网络 | PWA 缓存 + 静态托管镜像 |

> **保住了什么**：用户数据仍以本地为主（隐私与合规优势不变）；**所有核心学习功能在无后端时完整可用**（这是开源可运行性的底线）；同时云端后台承担内容管理、匿名统计、邀请码校验与可选同步等轻职责。

## 二、架构总览

系统支持**三种部署形态**，同一套代码，靠配置切换（详见第七章）：

```
╔════════════════════════════════════════════════════════════════════╗
║  形态 A · 纯本地（默认 · 开源默认形态）                              ║
║  前端 ──► 静态托管（内容随仓库）  ·  无后端  ·  成本 ¥0               ║
╚════════════════════════════════════════════════════════════════════╝
╔════════════════════════════════════════════════════════════════════╗
║  形态 B · 云端后台（✅ 目标形态 · 部署到已有服务器）                   ║
║  前端 ──► 静态托管 + 云端后台（内容管理 / 匿名统计 / 邀请码校验 / 可选同步）║
║                                                     成本 ≈ ¥0（服务器已有）║
╚════════════════════════════════════════════════════════════════════╝
╔════════════════════════════════════════════════════════════════════╗
║  形态 C · 完整后端（⏸️ 仅企业主体能力 · 不在当前范围）                 ║

╚════════════════════════════════════════════════════════════════════╝
```

> **形态 B 是本项目的落地目标**：云端后台部署到已有服务器，但**前端在无后端时仍功能完整**——这两点同时成立，靠的是「后端只做增强、仓储层可切换」。

## 三、内容即仓库（Content-as-Repo）

### 3.1 为什么内容用文件而不是数据库

即使现在有服务器，内容管理**仍以仓库文件为主**，原因是它天然解决了好几个通常要自己开发的问题：

| 能力 | 云端后台 | 内容即仓库 |
| --- | --- | --- |
| 版本与回滚 | 需自己开发 | **Git 原生** |
| 变更审计 | 需自建日志 | **Git 原生全量留痕** |
| 多人协作与冲突 | 需自建锁/冲突处理 | **Git 原生** |
| 外部贡献 | 需注册与授权 | **提 PR 即可** |
| 内容可复现 | 数据在私有库 | **任何人可 fork** |
| 数据可迁移 | 需写导出接口 | **本来就是文件** |
| 成本 | 服务器 + 运维 | ¥0 |

> **结论**：Git 就是最好的内容管理后台。服务器上的自托管后台**是它的补充（可视化编辑与快捷操作），不是它的替代**。两者写同一份数据模型，后台可以直接读写 `content/` 文件或同步到 MongoDB。

### 3.2 内容包结构

```
content/                          # ⭐ 内容与代码物理分离
├── manifest.json                 # 内容包清单：版本、各文件哈希、条目数
├── characters/
│   ├── grade-1.json              # 一年级字表（300–500 条/文件）
│   ├── grade-2.json
│   └── ...
├── poems/
│   ├── required-75.json          # 课标必背 75 首
│   └── extended.json             # 扩展古诗（取自 chinese-poetry）
├── lessons/
│   ├── units.json                # 自编单元（按主题/难度，非教材目录）
│   └── lessons.json              # 关卡编排
├── assets-index.json             # 素材索引（相对路径，不存二进制）
├── schema/                       # JSON Schema（CI 校验 + 后台表单共用）
│   ├── character.schema.json
│   ├── poem.schema.json
│   └── lesson.schema.json
└── sources.json                  # ⭐ 数据来源与许可清单（见 01-4 第五章）
```

**字段规格与后端集合、前端类型三者同源**（单一事实来源在 [03-2 数据字典](../03-数据设计/02-数据字典.md)）。收益：内容文件可原样导入 MongoDB，无需转换；后台表单可由同一份 JSON Schema 自动生成。

### 3.3 内容分发四条路径

| 路径 | 机制 | 需要后端 | 用途 |
| --- | --- | --- | --- |
| **① 随包构建** | 内容 JSON 在构建时打进产物 | ❌ | **默认路径**，离线可用（开源默认形态） |
| **② 远端静态覆盖** | 启动时拉取静态托管的 `manifest.json`，比对版本/hash，有更新则下载并缓存 | ❌（仅静态托管） | 改错别字、补字条，**不发版就能更新** |
| **③ 轻后端接口** | 调自托管 `/content/*` 获取内容与增量 | ✅ 轻后端 | 内容规模变大、需要按用户下发不同内容（如自定义单元） |
| **④ 完整后端接口** | ⏸️ 与账号、个性化结合 | ✅ 完整后端 | 需企业主体，不在当前范围 |

**关键设计**：①②③ **必须产出同一份数据结构**，客户端用同一套解析逻辑，这样"没有后端"与"有后端"的体验完全一致。**②是成本最低的内容更新方式**，优先做。

```
启动 → 读本地缓存 manifest
     → 后台静默请求远端 manifest.json（静态托管，超时 3s）
     → 比对 content_version / checksum
     → 有更新：下载变更文件 → 写入 Cache Storage → 下次启动生效
     → 失败 or 超时：静默忽略，用本地内容（绝不阻塞启动）
```

> ⚠️ **兼容性硬约束**：内容包必须带 `min_app_version`。若远端内容要求更高的应用版本，**老客户端必须忽略该更新**，否则会出现「字段不认识 → 渲染崩溃」。

### 3.4 内容版本管理

| 字段 | 说明 |
| --- | --- |
| `content_version` | 内容包语义化版本，如 `1.3.0` |
| `min_app_version` | 使用此内容包所需的最低应用版本 |
| `checksum` | 各内容文件的哈希，用于增量比对 |
| `updated_at` | 内容更新时间 |

## 四、能力开关体系（前端「掩藏」的实现机制）

「企业能力掩藏」不是一句口号，需要一套明确机制。核心原则：**任何依赖企业主体的能力，代码里都存在、可被打开，但在当前构建与运行时不可见、不可达。**

### 4.1 三层开关

| 层 | 机制 | 时机 | 用途 |
| --- | --- | --- | --- |
| **① 构建期** | 环境变量 `VITE_ENABLE_*` + Vite `define` 常量 | 构建时静态求值，**死代码消除** | 彻底不打包付费/账号相关代码 |
| **② 运行期远端** | 远端配置 JSON（静态托管或轻后端） | 启动时拉取，默认全关 | **不发版**就能灰度开启某项能力 |
| **③ 用户级** | 本地设置 + 用户显式开启 | 用户主动操作 | 例如「实验性功能」开关 |

**默认值必须全部为 `false`**，开启必须显式。

### 4.2 能力开关清单

**这里是能力开关名的唯一定义处，所有文档的开关名以此为准。**

| 开关名 | 含义 | 默认 | 依赖 | 前端隐藏 / 降级方式 | 契约位置 |
| --- | --- | --- | --- | --- | --- |
| `enableInviteAuth` | 邀请码身份（注册/登入） | ✅ 开 | 无（离线签名为纯前端） | — | [02-5](./05-邀请码身份与准入体系.md) |
| `enableInviteRequired` | 是否强制凭码注册（准入放量控制） | ✅ 开 | 无 | 关闭即「免码开放」，免注册直接可用 | [02-5](./05-邀请码身份与准入体系.md) |
| `enableInviteOfflineVerify` | 邀请码离线签名校验 | ✅ 开 | 无（Ed25519 纯前端） | 关闭后仅走服务端校验（需后端） | [02-5](./05-邀请码身份与准入体系.md) |
| `enableCloudProfile` | 云端家庭档案与跨设备同步 | ❌ 关 | 轻后端 | 设置页可显式开启 | [02-5](./05-邀请码身份与准入体系.md) |
| `enableE2EEncryption` | 端到端加密同步 | ✅ 开 | 无（口令派生密钥） | 开启云档案时生效 | [02-5](./05-邀请码身份与准入体系.md) |
| `enableContentApi` | 后端内容接口 | ✅ 开 | 轻后端 | 自动探测，不可用则落静态内容 | [04-1](../04-接口设计/01-API接口定义.md) |
| `enableRemoteContent` | 远端静态内容覆盖 | ✅ 开 | 静态托管 | — | [04-1](../04-接口设计/01-API接口定义.md) |
| `enableStats` | 匿名统计上报 | ✅ 开 | 轻后端 | 不加载 SDK，仅上报聚合数据 | [04-1](../04-接口设计/01-API接口定义.md) |
| `enableCloudAssessment` | 云端语音评测 | ❌ 关 | 付费 API | **无 Key 时整块功能隐藏，绝不显示假分数** | [04-1](../04-接口设计/01-API接口定义.md) |
| `enableAccountAuth` | 手机号 / 微信账号 | ⛔ 关 | **企业主体** | 无入口、路由不注册 | [04-1 预留接口](../04-接口设计/01-API接口定义.md) |
| `enablePayment` | 支付与订阅 | ⛔ 关 | **企业主体** | 无入口、不打包支付 SDK | [04-1 预留接口](../04-接口设计/01-API接口定义.md) |
| `enableMiniprogram` | 微信小程序 | ⛔ 关 | **企业主体** | 不存在该构建产物 | [02-3 预留清单](./03-uni-app跨端方案与小程序适配.md) |
| `enableNativeApp` | iOS / Android App | ⛔ 关 | **企业主体** | 不存在该构建产物 | [02-3 预留清单](./03-uni-app跨端方案与小程序适配.md) |

> **注**：`enableInviteRequired` / `enableInviteOfflineVerify` 是 `enableInviteAuth` 的**子开关**（前者控制准入放量方式，后者控制邀请码校验方式），仅在 `enableInviteAuth=true` 时生效。
>
> 标 ⛔ 的四项（`enableAccountAuth` / `enablePayment` / `enableMiniprogram` / `enableNativeApp`）属**掩藏**（需企业主体），默认关且不打包；`enableCloudAssessment` 是唯一涉及付费的开关，须严格遵守 [01-4 2.5 四条原则](../01-产品规划/04-免费开放与开源策略.md#25-付费能力的四条使用原则)——可选、可降级、默认关闭、不破坏开源可运行。

### 4.3 前端「掩藏」的四道防线

以「微信账号登录入口」为例，一处隐藏不够，必须四道同时做：

| 防线 | 做法 |
| --- | --- |
| ① **路由不注册** | 路由表由开关生成，关闭时该路由**不存在**（不是隐藏，是不注册） |
| ② **组件不渲染** | 入口按钮、菜单项由开关包裹，关闭时不产出 DOM |
| ③ **调用即抛错** | 关闭时对应 API 方法抛 `FeatureDisabledError`，而非静默失败 |
| ④ **类型层保留** | TS 类型与接口契约**始终保留**，将来打开开关时编译期就能发现问题 |

### 4.4 ⛔ 严禁的伪隐藏

| 反模式 | 为什么不行 |
| --- | --- |
| 用 CSS `display:none` 隐藏按钮 | 代码仍在包内、仍可被调用，安全与合规上都等于没做 |
| 隐藏入口但接口可调 | 一旦接口可调，就等于能力已存在，合规审查不会认可 |
| 只在前端隐藏、服务端不鉴权 | 前端隐藏**不是**权限控制；有后端后必须服务端二次校验 |
| 删除代码而非开关关闭 | 将来打开时要重写。**「预留」要求代码在、开关关** |

> 一句话：**掩藏 = 不可打包 + 不可达 + 不可调，而不是看不见。**

### 4.5 兼容性硬约束

远端配置与远端内容**都可能比客户端新**：

```
远端内容要求 min_app_version > 当前版本 → 忽略该更新，用本地内容（不提示、不报错）
远端配置出现未知开关              → 忽略未知项，不抛错
远端请求失败 / 超时（建议 3s）      → 静默降级到本地，绝不阻塞启动
轻后端不可用                     → 自动落到「静态托管 + 随包内容」，功能完整
```

## 五、后端分层与云端后台形态

### 5.1 三类后端能力

| 类别 | 能力 | 当前 | 说明 |
| --- | --- | --- | --- |
| **可以做**（不需企业主体） | 内容管理后台（单管理员）、内容读取接口、匿名统计、**邀请码校验**、云端家庭档案、反馈收集、可选云端评测 | ✅ **形态 B · 部署** | 只依赖服务器与少量付费 |
| **必须掩藏**（需企业主体） | 实名账号登录、手机号/微信、支付与订单、小程序、App 分发、类目资质 | ⛔ 形态 C | 契约与骨架保留，开关关闭 |
| **不该做**（本地更合适） | 复习调度计算、学情报告生成、F0 提取、学习数据存储 | — | 放本地：零成本、离线可用、隐私更好 |

### 5.2 云端后台（形态 B）设计

| 模块 | 职责 | 技术 | 为什么需要后端 |
| --- | --- | --- | --- |
| **内容管理后台** | 内容 CRUD、批量导入、质量检查、发布 | FastAPI + MongoDB（或直接读写 `content/` 文件）+ 简易前端 | 可视化编辑比手写 JSON 高效，降低内容生产门槛 |
| **内容读取接口** | 按单元/年级下发内容，支持增量 | FastAPI + MongoDB | 内容量大后不必全量随包；支持按用户自定义单元下发 |
| **邀请码校验** | 校验邀请码是否有效、是否已达使用上限 | FastAPI + MongoDB（可退回离线签名模式） | 需要「撤销邀请码」时才有必要；纯本地时用 **Ed25519 离线签名**替代（见 [02-5](./05-邀请码身份与准入体系.md)） |
| **匿名统计** | 记录功能使用次数、内容完成度、错误率 | FastAPI + MongoDB（聚合写入） | 无用户账号也能知道"哪里卡住了" |
| **云端家庭档案**（可选） | 邀请码家庭档案 + 端到端加密的跨设备同步 | FastAPI + MongoDB | 缓解「换设备丢进度」，且不需要企业主体 |
| **反馈收集** | 用户提交问题与内容纠错 | FastAPI + MongoDB | 替代第三方工单系统 |
| **可选：云端评测代理** | 代理付费语音评测 API，保护 Key | FastAPI | Key 不落前端；**无 Key 时整块功能隐藏** |

**必须遵守的轻量化纪律**：

| 纪律 | 原因 |
| --- | --- |
| **单机部署（Docker Compose），不用 K8s、不用微服务** | 运维成本要低到"一个人能维护"；服务器已有，直接跑 |
| 不引入 Redis（内容量小，全量进内存） | 少一个组件少一份故障 |
| 不引入消息队列，统计异步写用后台任务 | 同上 |
| **后端不可用时前端功能完整** | 保证开源可运行性；也保证服务器故障不影响学习 |
| 最小权限：后台不做 RBAC 多角色，只做**单管理员鉴权** | 团队只有维护者一人，多角色是过度设计 |
| **一键部署脚本 + 环境变量模板** | `docker compose up` 即可跑起；密钥只走环境变量，不进仓库 |

### 5.3 适配器模式：将来接后端只改一处

```
              ┌──────────────────────────────┐
              │   业务代码（stores / 页面）    │
              │   只依赖接口，不关心谁实现      │
              └───────────────┬──────────────┘
                              │
                    ┌─────────▼─────────┐
                    │  IProgressRepo     │  ← 接口定义（packages/core）
                    └─────────┬─────────┘
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
    ┌─────────────────┐ ┌──────────────┐ ┌────────────────────┐
    │ LocalRepository │ │ SyncRepository│ │ HttpRepository     │
    │ IndexedDB ✅ 主   │ │ 云端家庭档案 ✅  │ │ 账号级同步 ⏸️ 掩藏   │
    └─────────────────┘ └──────────────┘ └────────────────────┘
```

**关键收益**：从「纯本地」到「轻同步」再到「账号云同步」，业务代码**一行不改**，只替换注入的适配器实现。这就是「后端分层」的实际含义——**不是留后门，是把切换成本压到一次注入**。

> ⚠️ **代价**：所有数据访问**必须**走仓储层，禁止在组件里直接调 `localStorage` 或打开 IndexedDB。这条要写进 lint 规则与 code review 清单（见 [06-1](../06-工程规范/01-开发规范与前端架构.md)）。

### 5.4 企业主体能力的预留意向

| 能力 | 预留物 | 启用前提 |
| --- | --- | --- |
| 实名账号登录 | `/auth/*` 契约、`users` 集合、`enableAccountAuth` 开关 | 企业主体 + 短信/微信资质 |
| 账号级云同步 | `HttpRepository` 完整实现、`sync_state` 字段、冲突合并策略 | 实名账号体系 |
| 支付与订阅 | `orders`/`subscriptions` 集合、`/billing/*` 契约 | 商户号 |
| 微信小程序 | `apps/mobile` 骨架、分包方案（[02-3](./03-uni-app跨端方案与小程序适配.md)） | 企业主体（**个人主体不能申请教育类目且主体不可变更**） |
| iOS/Android App | uni-app 工程结构 | 企业开发者账号 |

> **注意区分**：**邀请码身份（`accounts`）不属于此表**——它只需服务器，已随云端后台一起落地。此表只列**真正需要企业主体**的能力。

**不做的事**：不注册（含不注册个人主体小程序）、不申请、不提交审核；境内部署的 ICP 备案按需另议（见 7.1）。

## 六、本地数据与可迁移性

### 6.1 本地存储分层

| 层 | 技术 | 存什么 | 说明 |
| --- | --- | --- | --- |
| 结构化学习数据 | **IndexedDB** | 档案、学习记录、复习状态、错题、成就 | **主存储**，即使启用同步也以本地为准 |
| 静态资源缓存 | **Cache Storage** | 内容 JSON、音频、笔顺数据、应用外壳 | Service Worker 配套 |
| 轻量偏好 | localStorage | 主题、设置、开关状态 | **禁止放关键进度**（易被清理） |

### 6.2 数据可迁移性：三个层次

| 层次 | 机制 | 依赖 | 何时用 |
| --- | --- | --- | --- |
| **① 导出 / 导入文件** | 导出 `.json`（含 `schema_version`），可导入还原 | ❌ 无 | **必做（P0）**，唯一不依赖任何服务的方式 |
| **② 恢复码** | 短码 + 口令派生密钥，把进度加密存到轻后端 | 轻后端 | 换设备不愿传文件时用；可选 |
| **③ 云端家庭档案** | 邀请码家庭档案（`enableCloudProfile`）+ 端到端加密（`enableE2EEncryption`）：多端用同一码与口令访问，服务端只存密文 | 轻后端 | **✅ 当前可做（非掩藏）**，默认关闭、默认加密 |

> ⚠️ **核心原则**：**① 永远可用，②③ 只是便利**。不能出现「没有后端就导不出数据」的情况，这是开源可运行性与用户数据主权的底线。
>
> ⚠️ **必须明示用户**：界面要明确提示「进度保存在本设备浏览器中，清除浏览器数据会丢失，建议定期导出备份」。这不是免责声明，是真实风险告知。

### 6.3 为将来上云预留的字段

本地数据结构**先埋好这些字段**，将来接后端不用改表：

| 字段 | 用途 |
| --- | --- |
| `client_id` | 设备级唯一标识（本地生成，同步的幂等键） |
| `profile_id` | 档案级匿名标识（多档案同步的最小单位） |
| `occurred_at` | 事件发生时间（客户端时间，离线上报排序依据） |
| `created_at` | 写入时间 |
| `sync_state` | `local` / `pending` / `synced`（当前恒为 `local`） |
| `schema_version` | 数据版本，用于迁移 |

### 6.4 匿名统计的隐私边界（重要）

启用统计必须守住儿童产品的底线：

| 允许 | 禁止 |
| --- | --- |
| 功能使用次数、页面停留时长（聚合） | 任何个人身份信息（姓名、手机号、微信 ID） |
| 内容完成度、错题分布（按内容维度） | 儿童真实姓名、照片、精确位置 |
| 错误堆栈、设备类型与浏览器版本 | 录音原始数据、可识别个体的行为轨迹 |
| 匿名设备标识（随机生成，不与身份关联） | 将匿名数据与任何第三方数据源做关联 |

> **原则**：统计的目的是「知道哪里卡住了」，不是「知道谁在用」。**儿童数据不出设备**这条底线不变——统计只上报聚合后的行为计数，不上报学习内容明细。

## 七、阶段演进路径

```
形态 A ───────────► 形态 B ───────────► 形态 C
纯本地（开源默认）    云端后台（✅ 部署目标）  完整后端（⏸️ 仅企业主体能力）
```

| | **形态 A · 纯本地** | **形态 B · 云端后台** ✅ | **形态 C · 完整后端** |
| --- | --- | --- | --- |
| 触发条件 | 默认起点、开源默认形态 | **已有服务器 → 实际部署** | 具备企业主体，且决定上架 |
| 服务器 | 无 | 1 台轻量（1C1G 起） | 集群 |
| 数据 | IndexedDB | **仍以 IndexedDB 为主**，服务端只存内容与统计 | 上云 + 本地缓存 |
| 新增能力 | — | 内容管理后台、匿名统计、邀请码校验、可选云端家庭档案、反馈 | 实名账号、支付、小程序、App |
| 需要备案 | ❌ | 取决于服务器位置（见 7.1） | ✅ |
| 增量工作量 | — | **3–5 人月** | 约 15–20 人月（因地基已在 A/B 完成） |
| 需要改什么 | — | 新增内容接口与统计上报；**业务代码不改** | **换适配器注入 + 数据上行同步** |

> **重点**：形态 A → B → C 的迁移成本，取决于今天是否把「仓储层抽象 + 能力开关 + 字段预留」这三件事做好。做好了，是「换个实现」；没做，是「推倒重来」。这三件事在 [01-3 路线图](./../01-产品规划/03-功能清单与优先级路线图.md) 中列为 **P0**。

### 7.1 部署位置与备案决策

**有服务器不等于必须备案**，取决于部署在哪里。这是本方案里唯一需要外部流程的一环：

| 路径 | 备案 | 国内速度 | 合规复杂度 | 结论 |
| --- | --- | --- | --- | --- |
| **服务器在境外 + 静态托管** | ❌ 不需要 | 一般 | 最低 | ⭐ **起步推荐** |
| 服务器在境内（自托管） | ✅ **必须 ICP 备案** | 最好 | 中：**个人主体可做非经营性备案**，流程数周 | 有稳定用户量后再做 |
| 仅用海外静态托管（不用服务器） | ❌ 不需要 | 一般 | 最低 | 形态 A 即可满足 |

**关键提醒**：ICP 备案是**个人主体**就能完成的（非经营性备案），**不属于"需要企业主体的事"**。所以境内部署在合规上可行，只是引入数周等待与材料准备。

**推荐组合**：

```
起步（形态 A/B）
  静态托管：Cloudflare Pages（主）+ GitHub Pages（镜像）
  轻后端：境外服务器，不备案
  → 零外部流程，随时可上线

成熟后（形态 B+）
  若国内访问成为明显瓶颈：
  境内服务器 + 个人 ICP 备案 + 静态资源走 CDN
  → 速度最优，但需数周备案等待
```

> ⚠️ **PWA 是这一环的关键杠杆**：首次加载慢可以忍，之后全程离线可用——**这也是本项目坚持 PWA 的现实理由，不只是体验优化**。

## 八、风险与代价

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 换设备/清缓存丢进度 | 用户真实损失，口碑风险 | 导出/导入必做（不依赖后端）+ 界面显式提示 + 可选云端家庭档案 |
| 后端故障 | 若功能依赖后端则不可用 | **后端只做增强**：内容有本地兜底、统计失败静默忽略 |
| 后端运维成为负担 | 单人维护成本上升 | 单机部署、不引 Redis/MQ、组件数压到最少 |
| 内容更新依赖缓存刷新 | 用户长时间看到旧内容 | manifest 用 hash 比对（不依赖时间戳）；后台可强制版本号 |
| 付费服务停用/涨价 | 相关功能失效 | 四原则保证可降级（默认关闭、无它不影响主流程） |
| 匿名统计越界 | 儿童隐私风险 | 明确允许/禁止清单（6.4）；只上报聚合行为计数 |
| 国内访问不稳 | 首次加载慢 | 静态托管镜像 + PWA 缓存 + 后端可放境内（备案后） |
| 仓储层被绕过 | 将来接后端返工 | lint 规则禁止组件直连存储 API；code review 清单 |
| 掩藏不彻底 | 合规质疑 | 四道防线 + 严禁伪隐藏反模式（4.4）；CI 校验构建产物不含敏感代码 |
| 预备能力长期不启用而腐化 | 契约与实现脱节 | 契约用 TS 类型约束（编译期检查）；文档标注「未验证」 |
