# 02-1 系统总体架构与技术选型

> 本文档定义系统的分层结构、技术栈选择理由、部署形态与关键技术方案。
>
> **定位说明**：在「不做企业主体能力 + 全部免费开放 + 项目开源 + **可自托管**」的条件下（见 [01-1 项目概述与定位](../01-产品规划/01-项目概述与定位.md)），
> 系统采用**服务端权威 + 内容即仓库 + 单机自托管后端**架构。存储与后端职责的详细设计见 [02-3 存储与后端策略](./03-存储与后端策略.md)。

## 一、架构总览

### 1.1 分层结构

```
┌───────────────────────────────────────────────────────────────────┐
│                      用户设备（浏览器 / PWA）                       │
│  ┌─────────────────────────────────────────────────────────────┐ │
│  │  apps/web      Vue3 + Vite + Pinia                          │ │
│  │  手机 · iPad · 桌面   三档响应式 + PWA                       │ │
│  └───────────────────────────┬─────────────────────────────────┘ │
│  ┌───────────────────────────▼─────────────────────────────────┐ │
│  │  packages/core  ⭐ 零平台依赖 + 学科无关业务内核              │ │
│  │  算法 · stores · 类型 · 接口契约 · 能力开关 · 仓储接口         │ │
│  │  （只保留凭据与 UI 偏好，不持有业务数据）                      │ │
│  └───────────────────────────┬─────────────────────────────────┘ │

                               │ HTTPS  /api/v1/*（同源反代）

║  │  ① 内容读取接口            ② 邀请码校验与身份                 │ ║
║  │  ③ 儿童档案                ④ 学习与复习（服务端算）           │ ║
║  │  ⑤ 学情报告                ⑥ 匿名统计                       │ ║
║  │  ⑦ 可选：云端家庭档案（端到端加密）  ⑧ 素材托管               │ ║
║  └─────────────────────────────────────────────────────────────┘ ║
║  ┌─────────────────────────────────────────────────────────────┐ ║
║  │  apps/admin  单管理员内容后台（Vue3 + Element Plus，内部工具）  │ ║

║  需企业主体：手机号/微信账号 · 支付订阅 · 推送 · 小程序 · App     ║
║  本期不做（与企业主体无关）：多角色 RBAC 后台                     ║
╚═══════════════════════════════════════════════════════════════════╝
```

> **三条线要说清楚**：① 前端 + 云端后台 + 管理后台 = **已实现**；② 学习数据与内容全部以服务端 MongoDB 为唯一真源（详见 [02-3](./03-存储与后端策略.md)）；③ 掩藏层 = **需企业主体**的能力（手机号/微信账号、支付、推送、小程序、App），**代码与契约在、开关全关、不打包**；**多角色 RBAC 后台属「本期不做」的设计取舍**（单人维护下多角色是过度设计，**与企业主体无关**），同样只留契约与开关。

### 1.2 设计原则

| 原则 | 具体做法 |
| --- | --- |
| **服务端权威（Server-Authoritative）** | 学习数据、档案、进度、内容以服务端为唯一真源；浏览器只保留凭据与 UI 偏好 |
| **内容与代码分离** | 内容存放在独立的 `content/` 目录，以 JSON 分发；贡献者不需要懂前端 |
| **内容即仓库** | Git 承担内容管理职责（版本、评审、回滚、审计）；自托管后台是其可视化补充 |
| **仓储层抽象** | 业务只依赖接口与 API 客户端；数据访问统一走 `packages/core`，禁止组件直连存储 |
| **能力开关默认关闭** | 需企业主体的能力代码存在但不可达、不打包、不可调（见 [02-3 第六章](./03-存储与后端策略.md)） |
| **零密钥、零付费依赖（主流程）** | 需要 API Key 或付费服务的能力只能作为**可选增强**，且必须可降级、默认关闭 |
| **多端同源，内核复用** | 业务逻辑一律写在 `packages/core`（零平台依赖）；外壳只负责渲染与平台能力实现 |
| **单机可维护** | 组件数压到最少（FastAPI + MongoDB + nginx），不引 Redis / MQ / K8s / 微服务 |
| **契约先行** | 接口契约以 TS 类型表达；统一前缀 `/api/v1`，破坏性变更升 `/api/v2` |

### 1.3 多端形态与复用边界

**当前交付**：手机 / iPad / 桌面浏览器三档响应式（Web + PWA）。
**预留形态**：微信小程序 + iOS/Android App —— 属**掩藏能力**（`enableMiniprogram` / `enableNativeApp`），开关关闭、不打包、不可达，将来具备企业主体后激活（路径见 [02-4 4.1](../02-系统架构/04-架构演进与优化方向.md)）。

| 外壳 | 技术 | 覆盖端 | 状态 |
| --- | --- | --- | --- |
| `apps/web` | Vue3 + Vite（PWA） | 手机、iPad、桌面 | ✅ **当前唯一交付**，三档靠响应式区分，非三套代码 |
| `apps/admin` | Vue3 + Element Plus | 桌面 | ✅ 单管理员内容后台（内部工具） |
| 小程序 / App 外壳 | — | 微信小程序、iOS、Android | ⛔ **掩藏**：开关关闭，不构建 |

**复用边界（必须严守）**：

| 层 | 复用方式 |
| --- | --- |
| 算法、状态、类型、接口契约、能力开关 | ✅ 100% 复用（`packages/core`，零 DOM / 零平台 API） |
| 平台能力（录音、存储、通知） | ❌ 各端实现，通过接口注入（依赖倒置） |
| 视图层（页面与组件） | ❌ 各端重写（标签体系与布局能力不同） |

> ⚠️ **这是本架构最关键的一条纪律**：`packages/core` 中一旦出现 `window`、`document`、`uni.xxx`，复用率会从 95% 直接掉到 0。将来启用跨端时，退化为「重做一遍前端」。

### 1.4 学科无关红线（`packages/core` 的第二条边界）

产品后续可能从语文扩到**英语、数学**，因此 `packages/core` 不只是**零平台依赖**，还必须**与学科无关**。判据只有一句：

> **这段逻辑换成英语单词还成立吗？** 成立 → 放 `packages/core`；不成立 → 放学科包。

| 归属 | 内容 |
| --- | --- |
| ✅ `packages/core`（学科无关） | 仓储 / 开关 / 档案 / 统计框架、SRS 调度、题型框架、拼音比对骨架 |
| ❌ `packages/subject-hanzi`（学科专属） | 汉字笔顺判定、古诗文结构、语文专属题型与素材 |

- 学科走 **URL 路径** `/hanzi` `/english` `/math`，**不是子域**（理由见 5.5）。
- `packages/core` 中出现任何学科名（`hanzi` / `pinyin` / `poem`）即为越界，需 CI 检查拦截。
- 学科包必须登记进 [06-1 第一章的目录树](../06-工程规范/01-开发规范与前端架构.md)。

## 二、技术选型

### 2.1 前端：Vue 3 + TypeScript + Vite

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | Vue 3（Composition API） | 模板语法对内容型界面开发效率高 |
| 语言 | TypeScript | 数据模型复杂，类型约束能显著减少联调成本；**契约类型是前后端的共同载体** |
| 构建 | Vite | 生态成熟、开发体验好；构建期可静态消除未启用能力的代码 |
| 状态管理 | Pinia | 按领域拆分为多个 store |
| 路由 | Vue Router | 多视图导航、路由懒加载与权限守卫（路由由能力开关生成） |
| 学生端 UI | 自研组件 + 设计变量包 | 儿童产品需强视觉定制，通用组件库不合适 |
| 管理端 UI | Element Plus | 后台是内部工具，效率优先 |
| PWA | vite-plugin-pwa | 应用外壳离线缓存；也是国内访问不稳定的缓解手段 |
| 响应式 | CSS 媒体查询 + container query | 手机（<768px）/ 平板（768–1279px）/ 桌面（≥1280px）三档，见 [02-2](./02-多端适配与响应式设计规范.md) |

### 2.2 数据层：服务端唯一真源

**MongoDB 是业务数据与内容数据的唯一真源**；浏览器不持有业务数据，localStorage 只保留四类键（会话凭据 / 设备标识 / 当前档案 UI 偏好 / 登录记忆）。

| 层 | 载体 | 存什么 | 为什么 |
| --- | --- | --- | --- |
| 业务数据 | **MongoDB** | 账号、设备、儿童档案、学习记录、复习状态、错题、每日任务、徽章、同步对象 | 跨设备一致、多档案、报告可复算 |
| 内容数据 | **MongoDB** | 字库、古诗、单元、关卡、故事、短文、徽章定义、清单 | 由 `content/` JSON 导入，改内容不必发版 |
| 素材文件 | 磁盘 / 命名卷 + `assets` 集合 | 图片、音频、笔顺 JSON | 内容文档只存 `*_ref`，出参展开为 `*_url` |
| 浏览器 | localStorage（仅四类键） | 凭据、设备标识、UI 偏好、登录记忆 | 同步可读、不含业务数据 |

**设计要点**：所有数据访问走 `packages/core` 的仓储接口与 API 客户端，禁止组件内直接操作存储；接口统一前缀 `/api/v1`，响应信封 `{code, message, data|errors, request_id}`。详细设计见 [02-3 存储与后端策略](./03-存储与后端策略.md)。

### 2.3 内容分发：内容即仓库 ⭐

| 项 | 方案 | 理由 |
| --- | --- | --- |
| 内容形态 | 仓库内 JSON（`content/` 目录） | 可版本化、可 fork、可 diff，贡献者只需改 JSON |
| 内容校验 | JSON Schema + CI 脚本 | 拼音一致性、重复条目、古诗原文比对自动检查 |
| 内容导入 | `scripts/seed`（按表拆分）或管理后台导入 | upsert 幂等；改内容不必发版 |
| 内容下发 | `GET /content/bootstrap` 一次拉全量 + 子资源接口按需读取 | 口径统一；前端登录后即可用 |
| 内容版本 | `content_version` + `min_app_version` + `checksum` | 客户端忽略要求更高版本的内容，避免渲染崩溃 |
| 素材 | 服务端托管（`assets` 集合 + 落盘目录） | 内容文档只存引用，换素材不碰内容 |

> 详见 [02-3 第三章](./03-存储与后端策略.md)。

### 2.4 部署

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 编排 | **Docker Compose 分服务独立编排**（mongo / api / web / admin 四份） | 各服务可单独构建与重启，互不牵连 |
| 网络 | `network_mode: host` | 容器直接占用宿主端口，不做端口映射 |
| 前端托管 | nginx 托管构建产物 + `/api/` 同源反代 | 一次解决混合内容拦截与跨源白名单 |
| 运维脚本 | `scripts/`（db / api / web / admin / content / seed / dev / lib） | 一键起停、备份、种子导入 |
| 成本 | **约 ¥0/月** | 服务器自有 |

> 发布与更新流程见 [06-2 发布与更新流程](../06-工程规范/02-发布与更新流程.md)。

## 三、后端组件选型

### 3.1 后端：Python 3.12 + FastAPI

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | FastAPI | 异步性能好；Pydantic 做请求校验；**自动生成 OpenAPI 文档** |
| 运行 | Uvicorn（1–2 worker 足够） | 单机部署，无需集群编排 |
| 校验 | Pydantic v2 | 与 MongoDB 的松散结构互补，接口层强校验 |
| 异步驱动 | motor | 官方异步 MongoDB 驱动 |
| 定时任务 | 后台任务（不引入 Celery/Redis） | 统计聚合等在进程内完成 |

**职责边界**：内容读取、邀请码与身份、儿童档案、学习与复习、学情报告、匿名统计、反馈、可选云端档案、素材托管、单管理员后台。**不做**：支付、订单、实名校验、推送、社交、多角色 RBAC。

### 3.2 数据库：MongoDB 7（自托管单机）

**选型理由**：内容的数据形态与文档模型天然契合 ——

| 数据特征 | 关系型的痛点 | MongoDB 的优势 |
| --- | --- | --- |
| 汉字属性多态 | 多音字、变长组词数组需多表 JOIN | 原生嵌套数组与对象 |
| 古诗结构 | 诗句、注音、释义三个等长数组需强关联 | 内嵌数组天然对齐 |
| 课程编排 | 关卡嵌套层级深，递归查询麻烦 | 嵌套文档一次读取 |
| 迭代期 schema 变动 | 每次加字段都要 migration | 灵活 schema + 可选校验 |
| 学习记录高频写 | 单表写入压力大 | 写入性能好，易扩展 |

**关键收益**：**内容包 JSON 的字段设计与 MongoDB 集合设计保持一致**（单一事实来源在 [03-2 数据字典](../03-数据设计/02-数据字典.md)）。因此内容文件可**原样导入** MongoDB，无需转换；前端 TS 类型、内容包 schema、后端 Pydantic 模型三者同源，不会漂移。

**关键索引策略**：

| 集合 | 索引 | 用途 |
| --- | --- | --- |
| `characters` | `char`(unique)、`grade`、`tags`、`level` | 字卡查询、筛选 |
| `characters` | 文本索引 `meaning, words` | 后台搜索 |
| `learning_records` | `{child_id: 1, created_at: -1}` | 学情查询 |
| `char_review_states` | `{child_id: 1, next_review_at: 1}` | **复习调度核心索引** |
| `accounts` | `invite_code_hash`、`access_tier` | 邀请码身份查询 |
| `invites` | `code_hash`(unique)、`expires_at` | 邀请码校验 |

### 3.3 缓存：Redis（❌ 不采用）

| 用途 | 结论 |
| --- | --- |
| 会话与 Token 吊销 | ❌ 改用 JWT 短有效期 + `devices` 集合吊销，无需 Redis |
| 热点字库 / 古诗列表 | ❌ 内容量小（数千条），全量加载 |
| 接口限流 | ❌ 进程内滑窗（单机够用） |

> **为什么明确不用**：少一个组件就少一份运维与故障源。**单机 + 单进程足以承载当前负载。**

### 3.4 对象存储（⏸️ 仅按需）

| 资源 | 格式 | 说明 |
| --- | --- | --- |
| 汉字读音音频 | MP3 / AAC，单声道 | — |
| 古诗朗诵 | MP3 | — |
| 配图 | WebP，多尺寸 | — |
| 笔顺数据 | JSON | — |

> **优先方案**：素材由服务端托管（`ASSET_DIR` 落盘 + `assets` 元数据）。**仅当素材体积明显拖慢加载时**才启用对象存储 + CDN（`ASSET_BASE_URL` 已预留）。素材必须**可开源分发**（见 [01-4](../01-产品规划/04-免费开放与开源策略.md)）。

## 四、关键技术方案

### 4.1 复习调度（服务端）

- **计算时机**：提交答题结果时在服务端更新该字的复习状态。
- **每日任务生成**：服务端按到期复习字 + 新学字 + 错题重练生成。
- **算法实现**：SM-2 简化变体，维护 `ease_factor` / `interval` / `repetitions` / `next_review_at` / `last_result`。
- **口径**：**服务端算，客户端不算** —— 保证各端一致、报告可复算。
- 完整口径见 [01-5 玩法与复习机制设计口径](../01-产品规划/05-玩法与复习机制设计口径.md)。

### 4.2 语音评测（只做本地可做的层）

云端语音评测 API 按调用量计费，会让贡献者无法零成本运行项目。因此**只保留可离线做的层**：

| 层 | 能力 | 实现 | 状态 |
| --- | --- | --- | --- |
| ① 静音/开口检测 | 判断有没有开口 | VAD 或能量阈值 | ✅ 可做 |
| ② 声调判定 | **四声读对没有** | 前端提取 F0 基频，与四声模板比对 | ✅ **优先做** |
| ③ 音素级评分 | 声母韵母标准度 | 云端评测 API（按量计费） | ⏸️ 可选，默认关闭、无 Key 整块隐藏 |

> ⚠️ **产品表述**：通用 ASR 会把儿童不标准的发音自动纠错成正确字形，**不能**用于发音打分。本项目只输出「声调对不对」与「有没有开口」，**不展示任何发音分数**。

### 4.3 PWA

| 层 | 技术 | 说明 |
| --- | --- | --- |
| 应用外壳 | Service Worker 预缓存 | 沿用 `vite-plugin-pwa`（`autoUpdate`） |
| 静态资源 | Cache Storage | 内容与素材按需缓存；API 响应不入缓存 |
| 数据 | **服务端为真源** | 离线时以外壳缓存保证可打开；数据以服务端为准 |

### 4.4 能力开关与仓储抽象

| 机制 | 作用 |
| --- | --- |
| 能力开关（构建期静态求值 + 运行期） | 依赖企业主体的能力默认关闭，不打包、不可达、不可调 |
| 掩藏四道防线 | 路由不注册 / 组件不渲染 / 调用即抛错 / 类型保留 |
| 仓储接口 + 适配器 | 业务只依赖接口；数据访问统一走 `ApiRepository`（服务端） |
| 类型契约常驻 | 开关关闭时类型与契约**仍然保留**，将来打开时编译期就能发现问题 |

### 4.5 身份与准入：邀请码

身份走**邀请码 + 自设密码**（Argon2id 密码 / JWT 会话 / Ed25519 邀请码签名），避开手机号与微信，**不需要企业主体**。儿童不单独注册，作为「家庭档案」下的档案存在，不收集任何身份信息。

> 完整安全设计（威胁模型、限流锁定、哈希存储、端到端加密、恢复码、准入策略） → [02-5 邀请码身份与准入体系](./05-邀请码身份与准入体系.md)

### 4.6 隐私与合规设计（架构级）

**身份信息零收集**：儿童档案只存昵称与年级；语音在端侧处理；数据可导出可删除；云端档案**默认关闭、开启时默认端到端加密**，服务端无解密密钥。统计只上报聚合行为计数。

> 详见 [02-3 第八章](./03-存储与后端策略.md) 与 [02-5](./05-邀请码身份与准入体系.md)。

## 五、部署形态

### 5.1 单机 Docker Compose（当前形态）

```
┌──────────────────────────────────┐
│  服务器（1C1G 起）                 │
│  ┌────────────────────────────┐  │
│  │ nginx（web 容器，host 网络） │  │
│  │  ├── /       → 前端静态产物  │  │
│  │  └── /api/   → 127.0.0.1:8000│ │
│  └────────────────────────────┘  │
│  ┌──────────┐   ┌─────────────┐  │
│  │ FastAPI  │   │ MongoDB     │  │
│  │ (1–2 wkr)│   │ 内容+业务数据 │  │
│  └──────────┘   └─────────────┘  │
│  ┌────────────────────────────┐  │
│  │ apps/admin（内部工具，8081） │  │
│  └────────────────────────────┘  │
└──────────────────────────────────┘
```

| 项 | 要求 |
| --- | --- |
| 部署方式 | **Docker Compose 单机**，`docker compose up` 即起；密钥只走环境变量 |
| 规模 | 单机；**不引入 Redis、不引入消息队列、不做微服务** |
| 备份 | 每日 dump（内容 + 身份 + 统计），见 `scripts/db/backup.sh` |
| 位置 | 境外免备案；境内**须 ICP 备案**（个人主体可做非经营性备案） |

### 5.2 环境划分

| 环境 | 用途 | 当前是否需要 |
| --- | --- | --- |
| dev | 本地开发（`pnpm dev` / `scripts/web/dev.sh`） | ✅ |
| preview | 构建产物本地预览 | ✅ |
| prod | 自托管部署（四份 compose） | ✅ |
| test / staging | 联调、预发布 | ⏸️ 按需 |

### 5.3 部署入口与学科路由

- **唯一入口**：学科无关 + 品牌无关的域名，改名与扩科都不作废。
- **学科走路径**：`/hanzi` `/english` `/math`，**不是子域**（子域 = 不同源，跨科学情聚合与 PWA 安装都会被迫按学科各来一套）。
- **配套子域按需**：`api.`（后端）/ `admin.`（内容后台）/ `docs.`（文档站点）。

## 六、第三方服务决策

| 用途 | 决策 | 说明 |
| --- | --- | --- |
| 代码托管与 CI | ✅ GitHub | 免费额度充足 |
| 拼音 / 笔顺 / 古诗文数据 | ✅ 开源数据集（`pinyin-data` / `hanzi-writer-data` / `chinese-poetry`） | 必须署名并随分发许可全文，见 [01-4](./../01-产品规划/04-免费开放与开源策略.md) |
| 语音处理 | ✅ 端侧（F0 提取 / VAD） | 无调用费、无密钥 |
| 短信验证码 / 微信登录 / 支付 | ⛔ 不用 | 需企业主体；邀请码身份下不需要 |
| 服务端推送 | ⛔ 不用 | 改用 PWA 本地通知 |
| 数据埋点 SaaS | ⛔ 不用 | 改为自建匿名统计 |
| Redis / 消息队列 | ⛔ 不用 | 当前负载用不上，徒增运维与故障点 |
| 多角色 RBAC 后台 | ⛔ 本期不做 | 单人维护下多角色属过度设计，只做单管理员鉴权（**与企业主体无关**） |
| 云端发音评测 API | ⏸️ 可选 | 默认关闭，**无 Key 时整块功能隐藏** |
| 对象存储 + CDN | ⏸️ 可选 | 素材体积明显拖慢加载时才启用 |
| 服务器 / 域名 | ⏸️ 已有 / 按需 | 服务器自有，成本≈0 |

```
study-club/
├── apps/
│   ├── web/                  # ✅ 学生端 + 家长视图（Vue3 + Vite，手机/iPad/桌面）
│   ├── admin/                # ✅ 单管理员内容后台（Vue3 + Element Plus，内部工具）
│   └── api/                  # ✅ 云端后台（FastAPI + MongoDB）
│       └── app/              #    路由 / Pydantic 模型 / 集合定义 / 控制器 / 仓储 / 种子导入
├── packages/
│   ├── core/                 # ⭐ 零平台依赖 + 学科无关业务内核（多端共用）
│   │   ├── api/              #   HTTP 客户端（信封解包 / 注入 client 头与 Authorization）
│   │   ├── repositories/     #   ApiRepository（数据） / HttpSource（内容）
│   │   ├── stores/           #   Pinia 领域 store
│   │   ├── algorithms/       #   学科无关算法：SRS、关卡生成
│   │   ├── flags/            #   ⭐ 能力开关定义与默认值
│   │   ├── platform/         #   平台能力接口（只定义，不实现）
│   │   ├── types/            #   TS 类型
│   │   └── constants/        #   枚举、错误码
│   ├── subject-hanzi/        # 语文专属逻辑（拼音比对、题型生成、跟读判定）依赖 core
│   └── tokens/               # 设计变量（断点 / 触控热区 / 色彩 / 字体）
├── content/                  # ⭐ 内容即仓库（与代码分离，贡献者的主战场）
│   ├── manifest.json         #   内容包清单：版本、哈希、条目数
│   ├── characters/ poems/ lessons/ stories/ badges/
│   ├── sources.json          #   ⭐ 数据来源与许可清单
│   └── schema/               #   JSON Schema（CI 校验用）
├── deploy/                   # ✅ 分服务独立编排（mongo / api / web / admin 各一份 compose）
├── scripts/                  # ✅ 运维脚本（按用途与服务分目录）
└── docs/                     # 本套设计文档
```
