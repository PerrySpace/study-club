# 02-1 系统总体架构与技术选型

> 本文档定义系统的分层结构、技术栈选择理由、部署形态与关键技术方案。
>
> **定位说明**：在「不做企业主体能力 + 免费开放 + 可能开源 + **已有服务器**」的条件下（见 [01-4](../01-产品规划/04-免费开放与开源策略.md)），系统采用**本地优先 + 内容即仓库 + 云端后台（可部署）**架构。
>
> **关键区分**（容易混为一谈）：
>
> | 类型 | 例子 | 处理 |
> | --- | --- | --- |
> | **需企业主体** | 手机号/微信账号、支付、小程序、App 上架 | ⛔ **掩藏**：写代码、开关关闭、不打包、不部署 |
> | **只需服务器或少量付费** | **邀请码身份**、自托管内容后台、匿名统计、跨设备同步、云端语音评测 | ✅ **可做**：属当前范围（形态 B） |
> | **本地即可** | 本地存储、本地模型、复习算法、静态内容 | ⭐ **首选** |
>
> 详细机制见 [02-4 本地优先与后端策略](./04-本地优先与后端策略.md) 与 [02-5 邀请码身份与准入体系](./05-邀请码身份与准入体系.md)。

> **三条线要说清楚**：① 实线部分（前端 + 静态托管）= **必须**，开源默认形态；② **云端后台 = 部署目标**，会真实上线，但**缺失时前端功能完整**（这是开源可运行性与故障兜底的底线）；③ 掩藏层 = 需企业主体，**代码与契约在、开关全关**。

### 1.2 设计原则

| 原则 | 具体做法 |
| --- | --- |
| **本地优先（Local-First）** | 数据以用户设备为主存储，离线是全功能而非降级；**后端缺失时功能完整** |
| **内容与代码分离** | 内容存放在独立的 `content/` 目录，以 JSON 分发；贡献者不需要懂前端 |
| **内容即仓库** | Git 承担内容管理职责（版本、评审、回滚、审计）；自托管后台是其可视化补充 |
| **仓储层抽象** | 业务只依赖接口；本地实现 IndexedDB，同步实现可选，掩藏实现不出包。**升级形态只换注入** |
| **能力开关默认关闭** | 需企业主体的能力代码存在但不可达、不打包、不可调（见 [02-4 第四章](./04-本地优先与后端策略.md#四能力开关体系前端掩藏的实现机制)） |
| **零密钥、零付费依赖（主流程）** | 需要 API Key 或付费服务的能力只能作为**可选增强**，且必须可降级、默认关闭 |
| **多端同源，内核复用** | 业务逻辑一律写在 `packages/core`（零平台依赖）；外壳只负责渲染与平台能力实现 |
| **分层降级** | 云端后台不可用 → 落静态托管内容；远端不可用 → 落本地内容；**任何一层失败都不阻塞启动** |

### 1.3 多端形态与复用边界

**当前交付**：手机 / iPad / 桌面浏览器三档响应式（Web + PWA）。
**预留形态**：微信小程序 + iOS/Android App（当前不启动，原因见 [01-4 3.2](../01-产品规划/04-免费开放与开源策略.md#32--微信小程序不能先用个人主体试水)）。

| 外壳 | 技术 | 覆盖端 | 状态 |
| --- | --- | --- | --- |
| `apps/web` | Vue3 + Vite（PWA） | 手机、iPad、桌面 | ✅ **当前唯一交付**，三档靠响应式区分，非三套代码 |
| `apps/mobile` | **uni-app（Vue3 版）** | 微信小程序、iOS App、Android App | ⏸️ **预留**，目录与分包方案保留，不写不构建 |
| `apps/admin` | Vue3 + Element Plus | 桌面 | ✅ **可部署**：单管理员内容后台（内容管理主路径仍是仓库驱动，见 [05-1](../05-管理后台/01-内容管理与用户管理体系.md)） |

**复用边界（必须严守）**：

| 层 | 复用方式 |
| --- | --- |
| 算法、状态、类型、接口契约、能力开关 | ✅ 100% 复用（`packages/core`，零 DOM / 零平台 API） |
| 平台能力（录音、存储、通知） | ❌ 各端实现，通过接口注入（依赖倒置） |
| 视图层（页面与组件） | ❌ 各端重写（标签体系与布局能力不同） |

> ⚠️ **这是本架构最关键的一条纪律**：`packages/core` 中一旦出现 `window`、`document`、`uni.xxx`，复用率会从 95% 直接掉到 0，将来启用小程序时退化为「重做一遍前端」。需用 CI lint 规则强制约束。

**能力分档**（当前只有 Full 档实际交付）：

| 档位 | 端 | 能力 |
| --- | --- | --- |
| **Full** | Web / PWA（当前） | 全功能：本地语音模型、离线闭环、iPad 手写压感 |
| **Full**（预留） | iOS / Android App | 同上，另加原生通知与更好的录音质量 |
| **Lite**（预留） | 微信小程序 | 主包 ≤ 2MB 硬约束下保留核心闭环与声调检测，砍掉本地大模型 |

> **重要**：无实名账号体系，身份走邀请码；因此不存在「三端账号打通（unionid）」的需求。

- 终端形态、断点、降级规则 → [02-2 多端适配与响应式设计规范](./02-多端适配与响应式设计规范.md)
- uni-app 工程、小程序分包、App 上架（备查） → [02-3 uni-app 跨端方案与小程序适配](./03-uni-app跨端方案与小程序适配.md)
- 无后端如何运行、能力如何隐藏 → [02-4 本地优先与后端策略](./04-本地优先与后端策略.md)

### 1.4 学科无关红线（`packages/core` 的第二条边界）

产品后续可能从语文扩到**英语、数学**，因此 `packages/core` 不只是**零平台依赖**，还必须**与学科无关**。这是与「零平台依赖」并列的第二条硬边界，判据只有一句：

> **这段逻辑换成英语单词还成立吗？** 成立 → 放 `packages/core`；不成立 → 放学科包。

| 归属 | 内容 |
| --- | --- |
| ✅ `packages/core`（学科无关） | 仓储 / 开关 / 档案 / 统计框架、SRS 调度、题型框架、F0 提取、拼音比对骨架 |
| ❌ `packages/subject-hanzi`（学科专属） | 汉字笔顺判定、古诗文结构、语文专属题型与素材 |

- 学科走 **URL 路径** `/hanzi` `/english` `/math`，**不是子域**（理由见 5.5）。
- `packages/core` 中出现任何学科名（`hanzi` / `pinyin` / `poem`）即为越界，需 CI 检查拦截。
- `packages/subject-hanzi` 必须登记进 [06-1 第一章的目录树](../06-工程规范/01-开发规范与前端架构.md)。

## 二、当前运行层技术选型

### 2.1 前端：Vue 3 + TypeScript + Vite

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | Vue 3（Composition API） | 团队指定；模板语法对内容型界面开发效率高 |
| 语言 | TypeScript | 数据模型复杂，类型约束能显著减少联调成本；**契约类型是「本地/云端/掩藏」三层的共同载体** |
| 构建 | Vite | 现有原型已在用，生态成熟，开发体验好；构建期可静态消除未启用能力的代码 |
| 状态管理 | Pinia | 按领域拆分为多个 store |
| 路由 | Vue Router | 多视图导航、路由懒加载与权限守卫 |
| 学生端 UI | 自研组件 + 现有 CSS 资产复用 | 儿童产品需强视觉定制，通用组件库不合适 |
| PWA | vite-plugin-pwa | 离线能力是本地优先架构的天然结果，**也是国内访问不稳定的缓解手段** |
| 响应式 | CSS 媒体查询 + container query | 手机（<768px）/ 平板（768–1279px）/ 桌面（≥1280px）三档，见 [02-2](./02-多端适配与响应式设计规范.md) |
| 跨端外壳 | uni-app（Vue3 版） | ⏸️ **预留**，明确不用 uni-app x（见 [02-3](./03-uni-app跨端方案与小程序适配.md)） |

### 2.2 本地数据层：IndexedDB + Cache Storage ⭐

这是**承载运行时学习数据的主数据层**，服务端 MongoDB 仅作可选镜像。启用云同步后，它仍是主存储，服务端只作备份与跨设备中转。

| 层 | 技术 | 存什么 | 为什么 |
| --- | --- | --- | --- |
| 结构化学习数据 | **IndexedDB** | 档案、学习记录、复习状态、错题、成就 | 容量大、支持索引与事务；异步不阻塞 UI |
| 静态资源缓存 | **Cache Storage** | 内容 JSON、音频、笔顺数据、应用外壳 | Service Worker 原生配套，离线可用 |
| 轻量偏好 | localStorage | 主题、设置、开关状态 | 简单；**禁止放关键进度**（易被清理） |
| 本机身份 | IndexedDB | 认证模式、账户 ID、邀请码哈希、档案绑定 | 供 [02-5 邀请码身份](./05-邀请码身份与准入体系.md) 使用 |

**设计要点**：

| 要点 | 说明 |
| --- | --- |
| 禁止绕过仓储层 | 组件内不得直接操作 IndexedDB / localStorage，必须走 `LocalRepository` |
| 版本化 schema | 每条数据带 `schema_version`，升级时执行迁移，避免丢数据 |
| 为同步预埋字段 | `client_id`、`profile_id`、`occurred_at`、`created_at`、`sync_state` |
| 多档案 | 支持多个孩子档案并存与切换，档案间数据隔离 |
| 导出/导入 | **唯一不依赖任何服务的数据保险，P0 功能，永远可用** |
| 可选云同步 | 形态 B 下可用「邀请码家庭档案」跨设备同步；**默认关闭、默认端到端加密** |

> 索引设计、迁移机制与本地数据结构 → [03-1 集合设计](../03-数据设计/01-MongoDB集合设计.md)、[02-4 第六章](./04-本地优先与后端策略.md#六本地数据与可迁移性)

### 2.3 内容分发：内容即仓库 ⭐

| 项 | 方案 | 理由 |
| --- | --- | --- |
| 内容形态 | 仓库内 JSON（`content/` 目录） | 可版本化、可 fork、可 diff，贡献者只需改 JSON |
| 内容校验 | JSON Schema + CI 脚本 | 拼音一致性、重复条目、古诗原文比对自动检查 |
| 内容更新 | **远端静态 JSON 覆盖**（manifest + hash 比对） | 改错别字不必发版；**成本为零，无需后端** |
| 内容版本 | `content_version` + `min_app_version` | 老客户端必须忽略要求更高版本的内容，防止渲染崩溃 |
| 素材 | 仓库内文件或静态托管相对路径 | 不引入对象存储费用 |

> **关键收益**：内容更新不必发版、成本为零，改变了「无服务器如何更新内容」这个原本棘手的点。机制详见 [02-4 第三章](./04-本地优先与后端策略.md#三内容即仓库content-as-repo)。

### 2.4 静态托管与部署

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 主托管 | **Cloudflare Pages** | 国内可达性较好、免费额度充足、无需备案 |
| 镜像托管 | **GitHub Pages** | 面向开源受众；同一份 `dist` 部署两处 |
| 备选 | Vercel / Netlify | 偶发阻断，作为第三备选 |
| 域名 | 平台赠送域名起步；自备约 ¥50/年 | 可选 |
| CI/CD | GitHub Actions | 类型检查、lint、内容校验、密钥扫描、构建、双托管部署 |
| 成本 | **约 ¥0/月** | 见 [01-4 2.4 零成本清单](../01-产品规划/04-免费开放与开源策略.md#24-成本清单) |

> ⚠️ **唯一无法用代码解决的取舍**：国内访问 GitHub Pages 不稳定。方案是「双托管 + PWA 离线 + 首屏极致压缩」，详见 [02-4 7.1](./04-本地优先与后端策略.md#71-部署位置与备案决策)。**境内部署需备案，起步用免费静态托管。**

## 三、后端组件选型（分层：✅ 部署 / ⛔ 掩藏）

> 本节的技术选型**分为两层**：① **✅ 部署**（只需服务器，形态 B 即上线）；② **⛔ 掩藏**（需企业主体，保留设计）。
> **判断依据**：哪些设计一旦缺失，将来就要返工。

### 3.1 后端：Python 3.12 + FastAPI（✅ 部署 · 形态 B）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | FastAPI | 异步性能好；Pydantic 做请求校验；**自动生成 OpenAPI 文档**，前端可据此并行开发 |
| 运行 | Uvicorn（1–2 worker 足够） | 单机部署，无需 Gunicorn 集群编排 |
| 校验 | Pydantic v2 | 与 MongoDB 的松散结构互补，接口层强校验 |
| 定时任务 | APScheduler（内置） | 统计聚合、备份；**不引入 Celery/Redis** |

**为什么不用 Django**：本项目不需要 Django 的 Admin 和 ORM 全家桶；MongoDB 配 Django ORM 并不自然；FastAPI 的异步与自动文档更契合。

**职责边界（形态 B 只做这些）**：内容读取与后台管理、邀请码与匿名账号、匿名统计、可选云端档案、反馈收集。**不做**：支付、订单、实名校验、推送、社交。

**落地形态**：`apps/api/` 是**要部署的云端后台**（内容读取、邀请码校验、匿名统计、可选同步）；接口契约以 TS 类型形式存在于 `packages/core/api/contracts/`，**编译期即可校验**（这比文档更可靠）。**前端不依赖它也能跑**——未部署时自动落本地内容与本地功能。

### 3.2 数据库：MongoDB 7（✅ 部署 · 自托管单机）

#### 选型理由

学习内容的数据形态与文档模型天然契合：

| 数据特征 | 关系型的痛点 | MongoDB 的优势 |
| --- | --- | --- |
| 汉字属性多态 | 多音字、变长组词数组需多张表 JOIN | 原生嵌套数组与对象 |
| 古诗结构 | 诗句、注音、释义三个等长数组需强关联 | 内嵌数组天然对齐 |
| 课程编排 | 关卡嵌套层级深，递归查询麻烦 | 嵌套文档一次读取 |
| 迭代期 schema 变动 | 每次加字段都要 migration | 灵活 schema + 可选校验 |
| 学习记录高频写 | 单表写入压力大 | 易分片、写入性能好 |

#### 但当前更重要的是：内容文件本身就该是这套结构

**内容包 JSON 的字段设计与 MongoDB 集合设计保持一致**（单一事实来源在 [03-2 数据字典](../03-数据设计/02-数据字典.md)）。这样做的直接收益：

- 现在不需要数据库，JSON 文件即可承担内容分发
- 将来若有后端，**内容文件可原样导入 MongoDB，无需转换**
- 前端的 TS 类型、内容包 schema、后端 Pydantic 模型三者同源，不会漂移

#### MongoDB 的代价与应对（启用时再看）

| 短板 | 应对方案 |
| --- | --- |
| 事务能力弱于关系型 | 关键流程用**单文档原子操作**设计，避免跨文档事务 |
| 多表关联查询不便 | 适当冗余（如学习记录中冗余汉字快照），用聚合管道替代 JOIN |
| 无强 schema 约束 | MongoDB JSON Schema 校验器 + Pydantic 双重把关 |
| 报表统计能力弱 | 统计走**预聚合**（定时任务生成统计文档）或导出分析库 |

#### 关键索引策略（启用时使用）

| 集合 | 索引 | 用途 |
| --- | --- | --- |
| `characters` | `char` (unique)、`grade`、`tags`、`level` | 字卡查询、筛选 |
| `characters` | 文本索引 `meaning, words` | 后台搜索 |
| `learning_records` | `{child_id: 1, created_at: -1}` | 学情查询 |
| `char_review_states` | `{child_id: 1, next_review_at: 1}` | **复习调度核心索引** |
| `accounts` | `invite_code_hash`、`access_tier` | 邀请码身份查询 |
| `invites` | `code_hash` (unique)、`expires_at` | 邀请码校验 |

> ⛔ `users`（手机号/微信账号）为掩藏能力，**当前不建索引、不启用**。

### 3.3 缓存：Redis（❌ 不采用）

| 用途 | 原拟键名 | 结论 |
| --- | --- | --- |
| 会话与 Token 黑名单 | `session:{user_id}` | ❌ 改用 JWT 短有效期 + `devices` 集合吊销，无需 Redis |
| 热点字库 / 古诗列表 | `cache:chars:{grade}` | ❌ 内容量小（数千条），**全量进进程内存** |
| 接口限流 | `rate:{user_id}:{endpoint}` | ❌ 用进程内滑窗（单机够用） |
| 排行榜 | `rank:weekly` | ❌ 无社交榜需求 |

> **为什么明确不用**：少一个组件就少一份运维与故障源。**单机 + 单进程足以承载形态 B 的负载**。

### 3.4 对象存储（⏸️ 仅按需，可少量付费）

| 资源 | 格式 | 说明 |
| --- | --- | --- |
| 汉字读音音频 | MP3 / AAC，单声道 | 命名 `audio/char/{char}.mp3` |
| 古诗朗诵 | MP3，含配乐 | 命名 `audio/poem/{poem_id}.mp3` |
| 配图 | WebP，多尺寸 | 命名 `image/char/{char}_{size}.webp` |
| 笔顺数据 | JSON | `stroke/char/{char}.json` |

> **优先方案**：素材直接放仓库（注意体积，超限用 Git LFS 或静态托管）。**仅当音频体积明显拖慢加载时**才启用对象存储 + CDN——属于 [01-4 2.4 的可选付费项](../01-产品规划/04-免费开放与开源策略.md#24-成本清单)。
>
> ⚠️ **素材必须可开源分发**（授权与署名要求见 [01-4 第五章](../01-产品规划/04-免费开放与开源策略.md#五内容版权开源化的第一红线)）。

## 四、关键技术方案

### 4.1 语音评测方案（分层，本地优先）

这是识字产品的重要能力，也是**与「零成本、可开源」约束冲突最激烈的一处**——云端语音评测 API 按调用量计费，会让贡献者无法运行项目。因此**只保留本地可做的层**：

| 层 | 能力 | 实现 | 成本 | 状态 |
| --- | --- | --- | --- | --- |
| ① 静音/开口检测 | 判断有没有开口 | Silero VAD（约 2MB）或能量阈值（几百字节） | 免费 | ✅ P2 |
| ② 内容判定 | 读的是不是这个字 | 本地 ASR 小模型（20–60MB） | 免费 | ✅ P2，按端能力探测 |
| ③ **声调判定** | **四声读对没有** | 前端提取 F0 基频（约 0.4MB 模型或纯 JS 算法），与标准四声模板比对 | **免费** | ✅ **P1，优先做** |
| ④ 音素级评分 | 声母韵母标准度 | 云端语音评测 API（腾讯云/讯飞） | 按调用量 | ⛔ **R 级，明确不做** |

**实施建议**：

- **优先做第 ③ 层**。声调是中文识字的核心痛点，且几乎零成本：`fnaught`（106k 参数、428KB ONNX，实施前需复核许可）或纯 JS 的 YIN 算法即可实现，全程离线。
- 第 ④ 层**不做**。理由不是精度不够，而是**它会让项目无法开源**——需要密钥、按量计费，任何贡献者克隆下来都跑不起来。这也正好契合「428KB 模型 vs 189MB 模型」的取舍结论。

> ⚠️ **关键提醒（产品表述层面）**：通用 ASR（语音转文字）**不能**用于发音打分——ASR 会把儿童不标准的发音自动纠错成正确字形，导致「读错也判对」。所以本项目**只输出「声调对不对」与「有没有开口」，不展示任何发音分数**。UI 表述用「声调小助手」，不用「发音评分」。展示虚假分数既误导家长，也是合规风险。

**端能力差异**（第 ② 层受端约束最大）：

| 层 | Web / PWA（当前） | 微信小程序（预留） |
| --- | --- | --- |
| ③ 声调判定（纯 JS，几十 KB） | ✅ 可实时出曲线 | ✅ 录后分析（PCM 机型兼容性需真机验证） |
| ② 内容判定（本地 ASR 模型 20–60MB） | ✅ | ❌ **主包 ≤ 2MB，物理上装不下** |
| ② 内容判定（降级路径） | — | 退化为「只判有没有开口」（能量阈值 VAD） |

> **可见：只做声调判定，恰好是唯一在所有端都可用的方案。** 这是约束逼出来的正确选择，而非妥协。

### 4.2 复习调度方案

- **计算时机**：每次提交答题结果时，同步更新该字的复习状态（本地事务）
- **每日任务生成**：应用启动或进入首页时懒生成（**无服务端定时任务**）
- **算法实现**：SM-2 简化变体，**纯函数**，放在 `packages/core/algorithms`，四端共用、可单元测试
- **代价**：跨设备不一致（因为无云同步）→ 由导出/导入缓解

### 4.3 离线与本地优先（PWA）

| 层 | 技术 | 说明 |
| --- | --- | --- |
| 应用外壳 | Service Worker 预缓存 | 沿用现有 `vite-plugin-pwa` |
| 内容缓存 | Cache Storage + IndexedDB | 按需缓存已学字所属单元 |
| 远端内容更新 | 后台静默比对 manifest | **失败静默忽略，绝不阻塞启动**（超时 3s） |
| 离线数据 | 本地即为唯一存储 | **不存在「离线降级」**——离线是全功能状态 |
| 前瞻 | 离线队列 | 阶段 B 起用于统计上报 |

> ⚠️ 本地优先的代价是「换设备丢进度」，由导出/导入与可选云端档案缓解——这是最需要向用户如实告知的一点。

### 4.4 能力开关与仓储抽象

这是「后端可部署、前端掩藏」的落点，此处只列要点：

| 机制 | 作用 |
| --- | --- |
| 三层开关（构建期 / 远端 / 用户级） | 依赖企业主体的能力默认关闭，不打包、不可达、不可调 |
| 仓储接口 + 适配器 | 业务只依赖接口，本地实现 IndexedDB，云端实现（形态 B）可切换 |
| 类型契约常驻 | 开关关闭时类型与契约**仍然保留**，将来打开时编译期就能发现问题 |

> 完整机制（含开关清单、四道防线、严禁的伪隐藏反模式） → [02-4 第四、五章](./04-本地优先与后端策略.md#四能力开关体系前端掩藏的实现机制)

### 4.5 身份与准入：邀请码

身份走**邀请码 + 自设口令**（短码走服务端校验，长签名码用 Ed25519 离线验签），避开手机号与微信，**不需要企业主体**。儿童不单独注册，作为「家庭档案」下的档案存在，不收集任何身份信息。

> ⚠️ **硬约束**：「先不注册（纯本地）」必须永远可用，**不得出现「不注册就不能用」的强制墙**。
>
> 完整安全设计（威胁模型、限流锁定、哈希存储、端到端加密、恢复码、准入策略） → [02-5 邀请码身份与准入体系](./05-邀请码身份与准入体系.md)

### 4.6 隐私与合规设计（架构级）

本地优先让合规负担大幅下降：**身份信息零收集**、儿童档案只存昵称与年级、语音全部端侧处理、数据可导出可删除；云端档案**默认关闭、开启时默认端到端加密**。

> 完整合规清单（数据上云告知、数据出境评估、第三方许可义务） → [02-5 第八章](./05-邀请码身份与准入体系.md#八合规影响)；许可与内容版权红线 → [01-4](../01-产品规划/04-免费开放与开源策略.md)。

### 5.2 形态 B：云端后台（✅ 部署目标）


| 项 | 要求 |
| --- | --- |

| 组件数 | 尽量少（Nginx + FastAPI + MongoDB 三件） |
| 备份 | 每日 dump（内容 + 身份 + 统计），保留 7 天 |
| 可用性 | 允许偶尔不可用——**前端有本地兜底，后端挂了不影响学习** |
| 位置 | 境外免备案；境内**须 ICP 备案**（个人主体可做非经营性备案），见 [02-4 7.1](./04-本地优先与后端策略.md#71-部署位置与备案决策) |

### 5.3 形态 C：完整后端（⛔ 需企业主体，不在当前范围）

| 阶段 | 方案 | 触发条件 |
| --- | --- | --- |
| 起步 | Docker Compose 单机（含会话与缓存） | 具备企业主体 |
| 增长 | 云托管容器服务 / K8s | 用户 > 1 万，需弹性伸缩 |
| 规模化 | MongoDB 副本集 + 分片 | 数据量或 QPS 到达瓶颈 |

### 5.4 环境划分

| 环境 | 用途 | 当前是否需要 |
| --- | --- | --- |
| dev | 本地开发（`npm run dev`） | ✅ |
| preview | 构建产物本地预览（`npm run preview`） | ✅ |
| prod | 静态托管（双托管） | ✅ |
| prod-api | 云端后台（形态 B） | ✅ **部署目标** |
| test / staging | 联调、预发布 | ⏸️ 有完整后端时才需要 |

### 5.5 部署入口与学科路由

- **唯一入口 `study.example.com`**：名字**学科无关 + 品牌无关**，改名或扩科都不作废。
- **学科走路径**：`/hanzi` `/english` `/math`，**不是子域**。
- **关键理由一句话**：**子域 = 不同源 → IndexedDB 按源隔离，学情报告无法跨科聚合**（同源还有 PWA 只装一次、离线缓存只维护一套的收益）。
- **配套子域按需**：`api.`（云端后台）/ `admin.`（内容后台）/ `docs.`（文档站点）。
- **DNS 与证书**：通配符 DNS + 通配符证书一次覆盖全部子域。

## 六、第三方服务决策

> 本节是一份决策记录：哪些用、哪些明确不用、为什么。判定标准：**要么需要企业主体，要么会破坏开源可运行性**。成本与付费原则见 [01-4](../01-产品规划/04-免费开放与开源策略.md)。

| 用途 | 决策 | 说明 |
| --- | --- | --- |
| 代码托管与 CI | ✅ GitHub | 免费额度充足 |
| 静态托管 | ✅ Cloudflare Pages + GitHub Pages | 双托管 |
| 拼音 / 笔顺 / 古诗文数据 | ✅ 开源数据集（`pinyin-data` / `hanzi-writer-data` / `chinese-poetry`） | 必须署名并随分发许可全文，见 [01-4 5.2](../01-产品规划/04-免费开放与开源策略.md#52-可用数据源白名单) |
| 语音模型 | ✅ 本地运行（F0 提取 / VAD） | 无调用费、无密钥 |
| 短信验证码 / 微信登录 / 支付 | ⛔ 不用 | 需企业主体；邀请码身份下不需要 |
| 服务端推送 | ⛔ 不用 | 改用 **PWA 本地通知**（无需服务端） |
| 数据埋点 SaaS | ⛔ 不用 | 改为**自建匿名统计** |
| 错误监控 SaaS（Sentry 云版） | ⛔ 不用 | 付费 + 数据出境；改用**自托管或本地日志导出** |
| Redis / 消息队列 | ⛔ 不用 | 形态 B 用不上，徒增运维与故障点 |
| 多角色 RBAC 后台 | ⛔ 不用 | 需账号体系；当前只做**单管理员简易鉴权** |
| 音量级发音评测 API | ⏸️ 可选（可少量付费） | 默认关闭，**无 Key 时整块功能隐藏** |
| 对象存储 + CDN | ⏸️ 可选 | 音频体积明显拖慢加载时才启用；境内需备案 |
| 服务器 / 域名 | ⏸️ 已有 / 按需 | 服务器已有，成本≈0 |

> ⛔ 掩藏能力（手机号/微信账号、支付与订阅、小程序、App 分发、多角色后台、备案与类目资质）已写好契约与骨架，启用前提见 [01-3 5.3 预留池](../01-产品规划/03-功能清单与优先级路线图.md#53-预留池不属于当前排期)。**邀请码身份与云端后台不属于此列**——它们只需服务器，属于「✅ 部署」层。
