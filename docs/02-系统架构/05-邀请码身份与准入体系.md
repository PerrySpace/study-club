# 02-5 邀请码身份与准入体系

> 本文档定义 **用邀请码完成注册与登入** 的身份模型、安全设计与准入策略。
>
> **一句话结论**：邀请码是**唯一不需要企业主体、却能做到「注册登入 + 跨设备同步」**的身份方案。它把原本必须依赖手机号/微信的账号能力，换成了一套基于「邀请码 + 自设口令」的轻身份，从而绕开了短信资质、企业认证与用户实名，同时保留了数据可迁移的能力。

---

## 一、为什么用邀请码

### 1.1 它解决了三个原本棘手的问题

| 问题 | 原来的困境 | 邀请码方案的解法 |
| --- | --- | --- |
| **跨设备/换设备丢进度** | 无账号 → 进度只在设备上；云同步需要身份 | 邀请码即身份 → **同一码 + 口令可在任意设备恢复档案** |
| **增长不可控** | 完全开放 → 服务器压力、内容错误被放大、反馈噪音大 | 邀请制 → 小规模内测、精准收集反馈、渐进放量 |
| **账号需要企业主体** | 手机号短信需企业实名；微信登录需开放平台企业认证 | ⭐ **邀请码既不发短信、也不接微信** → **不需要企业主体** |

### 1.2 它避开了什么（这是核心价值）

| 原「标准账号」需要 | 邀请码方案 |
| --- | --- |
| 短信服务（企业实名 + 费用） | ❌ 不需要 |
| 微信开放平台（企业认证 + 300 元/年） | ❌ 不需要 |
| 用户手机号（个人信息，合规义务重） | ❌ 不收集 |
| 实名认证 | ❌ 不需要 |
| 用户协议签署（服务端留痕） | ❌ 不需要（无身份信息） |

> **关键判断**：邀请码的本质是**「一个共享密钥式的身份标识」**，不是「实名账号」。它把身份从「你是谁」变成「你持有哪个凭证」——这正是开源、免费、无主体场景下唯一可行的身份模型。

### 1.3 架构影响

邀请码方案在「本地优先」之上增加三项能力：**轻量身份、可选云端档案、可开关的准入控制**。它们**只需要服务器，不需要企业主体**，因此不属于掩藏层。

## 二、身份模型

### 2.1 先分清两个概念

这两件事经常被混为一谈，但它们的策略可以完全独立：

| 概念 | 回答的问题 | 可否独立开关 |
| --- | --- | --- |
| **准入（Access）** | 「你有没有资格进来？」 | ✅ 可开关（邀请制 / 完全开放 / 免码本地模式） |
| **身份（Identity）** | 「你是谁？你的档案是哪个？」 | ✅ 可开关（有码身份 / 纯本地无身份） |

**这一区分非常重要**：它让你可以在**不违背「免费开放给所有用户」承诺**的前提下使用邀请码——因为开放的是**准入策略**，而身份模型与是否收费、是否限制用户无关。

### 2.2 邀请码承担的三种角色

| 角色 | 说明 | 是否必需 |
| --- | --- | --- |
| **准入凭证** | 有码才能注册，用于控制放量节奏与质量 | ⏸️ 可关闭 |
| **身份凭证** | 码 + 口令 = 一个家庭档案的唯一标识，用于登入与跨设备恢复 | ✅ 核心 |
| **家庭凭证** | 同一码供家庭成员共用（多设备、多位家长），对应「一个家庭 = 一个档案空间」 | ✅ 核心 |

### 2.3 数据模型

**本地（IndexedDB）**：

```
local_identity            # 本机身份（未注册时为空）
├── auth_mode            # none（纯本地）| invite（邀请码身份）
├── account_id           # 服务端返回的匿名账号 ID
├── invite_code_hash     # 本地保存的是哈希，不存明文
├── display_name         # 家庭昵称（自拟，非实名）
├── profile_ids[]        # 本机绑定的孩子档案
├── last_login_at
└── recovery_code_set    # 是否已设置恢复码（布尔，不存码本身）
```

**服务端（MongoDB，形态 B/C）**：

```json
// accounts — 匿名账号（无手机号、无微信、无实名）
{
  "_id": ObjectId("..."),
  "invite_code_hash": "sha256:...",       // ⭐ 只存哈希，不存明文；兼作来源溯源
  "passcode_hash": "argon2id:...",        // ⭐ 口令哈希（加盐）
  "display_name": "小明家",
  "status": "active",
  "created_at": ISODate("..."),
  "last_login_at": ISODate("..."),
  "failed_attempts": 0,
  "locked_until": null
}

// invites — 邀请码（发放与用量）
{
  "_id": ObjectId("..."),
  "code_hash": "sha256:...",              // ⭐ 只存哈希
  "code_hint": "HANZI-4K9F-****",         // 便于后台辨认，不含完整码
  "batch_id": "internal-2026-10",         // 批次标识，便于整批作废
  "channel": "community",                 // 发放渠道
  "max_uses": 1,                          // ⭐ 恒为 1（见下方「一码一账号」说明）
  "used_count": 1,                        // 0（未激活）或 1（已激活）
  "bound_account_ids": [ObjectId("...")], // ⭐ 至多 1 个账号
  "expires_at": ISODate("..."),
  "revoked_at": null,                      // 非 null 即已作废（整批作废亦写此字段）
  "note": "首轮内测，语文老师群",
  "created_by": "admin",
  "created_at": ISODate("...")
}

// devices — 设备与会话（可选）
{
  "_id": ObjectId("..."),
  "account_id": ObjectId("..."),
  "client_id": "dev_xxx",                  // 本地生成的设备标识
  "client": "web",                         // web / miniprogram / app
  "platform": "ios",                       // ios / android / harmony / web
  "device_form": "phone",                  // phone / tablet / desktop
  "revoked": false,                        // 会话是否已吊销
  "last_active_at": ISODate("...")
}
```

> **隐私要点**：`accounts` 里**没有任何个人身份信息**——没有手机号、没有邮箱、没有真实姓名、没有微信 ID。`display_name` 由用户自拟（如「小明家」），可以随时修改且不校验真实性。这使「儿童个人信息保护」的负担维持在很低的水平（详见第八章）。

> ⭐ **「一码一账号」是确定的口径，`max_uses` 恒为 1。**
> 邀请码承担**身份凭证**角色（§2.2）——它就是账号的登录标识，登入时用「码 + 口令」
> 定位到唯一账号。因此 `accounts.invite_code_hash` 上有**唯一索引**
> （见 [03-1 §3.1](../03-数据设计/01-MongoDB集合设计.md)），一个码只可能激活一个账号；
> `used_count` 只有 0/1 两种取值，`bound_account_ids` 至多一个元素。
>
> **「家庭共享」= 全家人用同一个码 + 同一个口令进同一个档案空间**（§3.4），
> 而不是各自注册。若需要给孩子之外的人做数据隔离，**再发一个码**即可（§3.4）。
>
> ⚠️ 早先 `max_uses` 曾开放到 1000、后台也摆了一个「可用次数」控件，那是**与唯一索引冲突**的：
> 填 3 只会成功 1 个，第二次注册撞唯一索引后返回 500「服务内部错误」。
> 现已收口：请求模型限 `le=1`，后台改为只读说明，重复注册返回统一业务错误
> （`40103` 邀请码或口令不正确）而不是 5xx。

### 2.4 与「纯本地模式」共存

三种使用方式**必须同时可用**，由开关决定：

| 模式 | 触发条件 | 身份 | 数据在哪 | 用途 |
| --- | --- | --- | --- | --- |
| **纯本地** | 用户选择「先不注册」（部署方可置 `enableInviteAuth=false`） | 无 | 仅本机 | 开源默认形态；离线用户；不想注册的家长 |
| **邀请码身份** | `enableInviteAuth=true` 且用户完成注册 | 码 + 口令 | 本机为主 + 云端档案 | 需要跨设备、需要备份 |
| **免码开放** | `enableInviteRequired=false` | 自助生成的码 | 同上 | 放量期：不限制准入，但仍可注册以便同步 |

> ⚠️ **硬约束**：**「先不注册」必须永远可用**。任何时候都不能出现「不注册就不能用」的强制墙——那既违背免费开放承诺，也破坏开源可运行性（贡献者默认无后端）。

## 三、注册与登入流程

### 3.1 注册

```
① 输入邀请码
   → 校验（离线签名校验 或 服务端校验，见第六章）
   → 失败：提示「邀请码无效或已用尽」（不区分「不存在」与「已用尽」，防枚举）

② 设置口令（PIN）
   → 强度要求：≥ 6 位，非纯数字连续（家长易用与安全的折中）
   → 二次确认

③ 设置家庭昵称（可跳过，默认「我的家」）

④ 创建首个孩子档案（昵称 + 年级，不收真实姓名）

⑤ ⭐ 显示「恢复码」，要求用户抄下并确认
   → 恢复码仅显示一次，用于忘记口令时恢复

⑥ 完成 → 本机保存身份，后台静默建立云端档案
```

### 3.2 登入

```
① 输入邀请码 + 口令
   → 服务端校验（限流 + 失败计数 + 锁定策略）
   → 成功：返回匿名账号 ID + 档案摘要

② 本机已有数据？
   → 询问：合并 / 覆盖 / 保留本机
   → 合并策略：学习记录按 occurred_at 去重合并（追加型数据天然易合并），
                复习状态取"更晚一次"的结果

③ 拉取档案 → 进入应用
```

### 3.3 ⚠️ 找回机制（必须诚实设计）

**没有手机号，就无法用「验证码找回」**。这是邀请码方案的固有代价，必须正面处理：

| 情况 | 可用手段 | 说明 |
| --- | --- | --- |
| 忘记口令，但记得恢复码 | ✅ **恢复码重置口令** | 所以第 ⑤ 步必须强制确认抄写 |
| 忘记口令与恢复码 | ❌ 无法找回云端档案 | **但本机数据仍在**——可继续使用，或导出后重新注册 |
| 换设备，记得码与口令 | ✅ 直接登入 | 正常路径 |
| 云端档案丢失 | ✅ **本机导出文件可恢复** | 导出/导入是最后一道保险，永远可用 |

> ⚠️ **UI 必须明确告知**：注册时用醒目文案说明「忘记口令且丢失恢复码将无法找回云端备份，请妥善保存恢复码」。**不要用「找回密码」这类暗示可以找回的措辞**——那会误导用户，是真实的口碑风险。

### 3.4 多设备与多孩子

```
                      ┌──────────────────────────┐
                      │  account（邀请码 + 口令）  │
                      │  “一个家庭”                │
                      └────────────┬─────────────┘
                                   │ 1:N
        ┌──────────────┬───────────┼───────────┬──────────────┐
        ▼              ▼           ▼           ▼              ▼
   ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌──────────┐
   │ 孩子档案A │  │ 孩子档案B │  │ 手机设备 │  │ iPad设备 │  │ 家长设备  │
   └─────────┘  └─────────┘  └─────────┘  └─────────┘  └──────────┘
```

| 场景 | 设计 |
| --- | --- |
| 一人在手机与 iPad 用 | 同一码同一口令 → 两设备看到同一档案空间 |
| 家里多位家长各自设备 | 同一码同一口令（家庭共享码）→ 共享孩子档案 |
| 一部设备多个孩子 | 本机多档案切换（本地已有能力） |
| 家长想隔离自己的数据 | 支持「一码一账号」，即发放多个码 |

> **设计取舍**：**不做「邀请子账号」这类复杂模型**。家庭共享码 + 口令已覆盖绝大多数场景，而复杂度会直接吞噬维护者精力。若确有隔离需求，直接发第二个码即可。

## 四、安全设计

这是本方案**风险最高**的部分——邀请码天然比手机号弱。必须靠设计补齐。

### 4.1 威胁模型

| 威胁 | 后果 | 对策 |
| --- | --- | --- |
| 码被**枚举/爆破** | 他人进入系统、看到孩子的学习数据 | 码必须有足够熵（≥ 60 bit）+ 服务端限流 + 失败锁定 |
| 码在群里**被转发** | 超出预期放量 | `max_uses` 限制 + 用量可观测 + 可吊销 |
| 码**泄漏**但口令未知 | 无法登入（口令是第二因素） | 口令强制、独立哈希存储 |
| 口令**弱** | 被离线/在线爆破 | 服务端限流 + `argon2id` 加盐哈希 + 强度下限 |
| 服务端**读到儿童数据** | 合规与信任风险 | ⭐ **端到端加密同步**（见 4.5） |
| 码被用于**钓鱼** | 用户被骗输入码 | 码本身不含用户信息，泄漏后果有限；提示用户勿在非官方渠道输入 |

### 4.2 码的生成

| 项 | 设计 | 理由 |
| --- | --- | --- |
| 字符集 | Crockford Base32（去掉易混的 `I`/`O`/`U`/`L`） | 家长需要手抄、口述、手动输入 |
| 长度 | **12 位**（分 3 组：`XXXX-XXXX-XXXX`） | 60 bit 熵 → 暴力枚举不可行 |
| 生成方式 | 服务端 `secrets` 密码学随机 | 禁止自增、禁止时间戳派生 |
| 存储 | **只存哈希**（`sha256`） | 数据库泄漏也不能反推可用码 |
| 展示 | 仅创建时显示一次完整码 | 后台只保留 `code_hint`（如 `HANZI-4K9F-****`） |

> ⚠️ **为什么是 60 bit**：8 位 Base32（40 bit）在无限流时理论上可被离线枚举；12 位（60 bit）即使无限流也不可行。分层防御从码本身开始。

### 4.3 双因素：码 + 口令

| 因素 | 承担 | 强度 |
| --- | --- | --- |
| **邀请码** | 准入（是否被允许） | 高熵，但可能被共享/泄漏 |
| **自设口令** | 身份确认（是否是你） | 低熵，但只有本人知道 |

**两者缺一不可**：

- 只有码 → 群里转发一下就进不去（因为没有口令）
- 只有口令 → 无法定位到哪个账号
- 码 + 口令 → 即使码被转发，他人也不知道口令

### 4.4 服务端防护（必须实现）

| 防护 | 参数建议 |
| --- | --- |
| 登入限流 | 按 `client_id` + IP：10 次 / 10 分钟 |
| 失败锁定 | 连续 5 次失败 → 锁定 15 分钟（指数退避） |
| 时序安全 | 校验比较用恒定时间比较（防时序侧信道） |
| 错误信息 | 统一返回「邀请码或口令不正确」，**绝不区分**（防用户枚举） |
| 注册防滥用 | 同 IP 注册数限制；`max_uses` 硬上限 |
| 会话 | 短期 Access Token（JWT）+ 可吊销的长期 Refresh Token |
| 传输 | 强制 HTTPS/HSTS |
| 日志 | **不记录明文码与口令**；只记录账号 ID 与结果 |

### 4.5 ⭐ 端到端加密同步（推荐）

这是本方案最有价值的一个设计，因为它一举解决了「邀请码安全强度」与「儿童数据合规」两个问题：

```
用户口令 ──► KDF（Argon2id + 盐）──► 派生密钥
                                        │
                    客户端加密学习数据 ◄─┘
                            │
                            ▼
                  服务端只存密文（无法解密）
                            │
                            ▼
                  另一设备登入 → 下载密文 → 本地用同一口令解密
```

| 收益 | 说明 |
| --- | --- |
| 服务端**读不到儿童学习数据** | 合规负担大幅降低；即使服务器被入侵也不泄漏内容 |
| 口令既是认证因素也是解密密钥 | 无需额外设计密钥管理 |
| 信任成本低 | 开源项目最怕「你收集我孩子的数据」，此设计可直接回应 |

| 代价 | 应对 |
| --- | --- |
| 忘记口令 = 云端密文永久不可恢复 | 强制恢复码流程 + 本机导出兜底 + UI 明确警告 |
| 服务端无法对学习内容做分析 | 统计只做**聚合计数**（见 [02-4 6.4](./04-本地优先与后端策略.md#64-匿名统计的隐私边界重要)） |
| 密钥派生需注意性能 | 用 WebCrypto 原生 API；Argon2id 参数按低端机调优 |

> **默认建议**：**默认开启端到端加密**。若开启后家长反馈「忘记口令太麻烦」，再考虑提供「不加密同步」的可选开关（并在 UI 明确说明「服务端可读取」）。**先严后宽，而不是先宽后严。**

### 4.6 恢复码

| 项 | 设计 |
| --- | --- |
| 格式 | 一次性长码（如 24 位 Base32，120 bit），仅显示一次 |
| 作用 | 忘记口令时重置口令（并重新派生加密密钥） |
| 存储 | 服务端只存哈希 |
| 提示 | 强制用户抄写并二次确认；提供「下载为文件」也可 |
| 可重生成 | 是（生成新恢复码会失效旧的） |

## 五、准入策略

准入与身份**可独立开关**：准入用 `enableInviteRequired` 控制发放方式，身份用 `enableInviteAuth` 控制。

| 策略 | `enableInviteRequired` | 发放方式 |
| --- | --- | --- |
| 邀请制内测 | `true` | 维护者手工发放 |
| 自助领取 | `true` | 用户自助申请，审核后发放 |
| 免码开放 | `false` | 用户自助生成身份码（放量期默认） |
| 完全本地 | — | 无需码（`enableInviteAuth=false`） |

> **边界**：用邀请码控制**放量节奏**，不用它做收费门槛、不长期关闭公开入口、不用码绑定真实身份。**邀请制是阶段性放量手段，不是长期门槛**——到放量期必须进入「免码开放」，否则与「免费开放给所有用户」矛盾。**「先不注册」永远可用**，不得出现强制注册墙。
>
> 准入的阶段排期（F0–F2）见 [01-3 功能清单与优先级路线图](../01-产品规划/03-功能清单与优先级路线图.md)。

## 六、两种校验模式

这是保证「开源可运行」的关键设计——**邀请制不必依赖后端**。

### 6.1 ⭐ 离线签名邀请码（无需后端）

用「签名许可证」的思路：**部署者持私钥签发码，客户端用公钥本地校验**。

```
维护者（持私钥）                   用户客户端（含公钥）
     │                                    │
     │  签发：code = payload || sig       │
     │  payload = {tier, expires, nonce, │
     │             batch}                 │
     │  sig = Ed25519_sign(privkey, payload)
     │                                    │
     └──────────► 用户输入 code ──────────►│
                                          │ 公钥本地验签
                                          │ ✅ 通过 → 生成身份标识（离线）
                                          │ ❌ 失败 → 提示无效
```

| 项 | 设计 |
| --- | --- |
| 算法 | Ed25519（Node/浏览器 WebCrypto 均支持） |
| 公钥 | **随开源代码公开**（公开不影响安全） |
| 私钥 | 仅维护者持有，**不入库**（`.gitignore` + CI 密钥扫描保护） |
| 码长度 | 签名码较长（约 40–60 字符），**内测期可接受**；建议配合二维码/链接分发 |
| 适用 | 形态 A（无后端）：开源贡献者、离线部署、纯前端发布 |

> **这个设计的意义**：它让「邀请制」在**没有任何服务器**的情况下也能成立。开源项目默认形态因此可以既保持邀请制的质量把控，又不要求任何人配后端。

### 6.2 服务端校验（形态 B/C）

| 项 | 设计 |
| --- | --- |
| 接口 | `POST /auth/invite/verify`（仅校验）/ `POST /auth/invite/register` / `POST /auth/invite/login` |
| 优势 | 可吊销、可统计用量、可限制 `max_uses`、可远程作废 |
| 适用 | 形态 B（有服务器）——**推荐，因为可撤销** |

### 6.3 对比

| 维度 | 离线签名码 | 服务端校验 |
| --- | --- | --- |
| 需要后端 | ❌ 不需要 | ✅ 需要 |
| 可吊销 | ❌ 不可（只能靠有效期） | ✅ 可随时吊销 |
| 用量统计 | ❌ 不可 | ✅ 可 |
| 长度体验 | 长（40–60 字符） | 短（12 字符） |
| 与口令配合 | ✅ 仍可（口令与云同步需后端） | ✅ |
| 推荐用途 | 形态 A、离线分发 | 形态 B 主路径 |

**结论**：**两者都实现，由开关选择**。`enableInviteAuth=true` + `enableContentApi=false` → 走离线签名；有后端则优先服务端校验。

### 6.4 开源默认行为

| 场景 | 默认 |
| --- | --- |
| 贡献者克隆运行 | 免码开放（`enableInviteRequired=false`）→ **免注册直接可用**；如需纯本地可置 `enableInviteAuth=false` |
| 部署者自建 | 可开启邀请制（离线签名或服务端校验） |
| 隐私 | 默认不启用统计、不启用云同步 |

> ⚠️ 遵守 [01-4 2.5 的四条原则](../01-产品规划/04-免费开放与开源策略.md#25-付费能力的四条使用原则) 的同类精神：**任何"要不要注册/要不要上传"的决定权在部署者与用户，不在代码的默认值里。**

## 七、能力开关与降级

### 7.1 开关清单

> 开关名的**唯一定义处**是 [02-4 §4.2](./04-本地优先与后端策略.md#42-能力开关清单)，此处只列与本体系相关的开关。

| 开关 | 默认 | 依赖 | 说明 |
| --- | --- | --- | --- |
| `enableInviteAuth` | ✅ | 无（离线签名为纯前端） | 邀请码身份总开关 |
| `enableInviteRequired` | ❌ | 无 | 是否强制凭码注册（放量控制） |
| `enableInviteOfflineVerify` | ✅ | 无 | 离线签名校验（形态 A 也能邀请制） |
| `enableCloudProfile` | ❌ | 轻后端 | 云端家庭档案与跨设备同步 |
| `enableE2EEncryption` | ✅ | 无 | 同步数据端到端加密（开启 `enableCloudProfile` 时生效） |
| `enableAccountAuth` | ❌ | **企业主体** | 手机号/微信账号（掩藏） |

> **注**：`enableAccountAuth` **属掩藏层**（需企业主体）。邀请码身份（`enableInviteAuth`）与其云档案（`enableCloudProfile`）**不属于掩藏层**——它们不需要企业主体。

### 7.2 无后端时的降级行为

| 能力 | 无后端时 |
| --- | --- |
| 邀请码校验 | ✅ 走离线签名（若开启），否则跳过 |
| 注册/登入 | ⏸️ 不可用 → 自动退化为「纯本地模式」，**功能完整** |
| 跨设备同步 | ⏸️ 不可用 → 引导使用导出/导入文件 |
| 恢复码 | ⏸️ 不需要（无云端档案） |

> **硬要求**：后端不可用时，**必须自动进入纯本地模式且不报错、不阻塞**。身份是增强，不是必需。

### 7.3 数据主权始终在用户

| 保证 | 实现 |
| --- | --- |
| 随时可导出 | 导出功能**不依赖后端**，永远可用 |
| 可离线删除云端档案 | 提供「注销并删除云端数据」按钮（或直接在服务端撤回） |
| 可拒绝上传 | `enableCloudProfile=false` 时纯本地，零上传 |
| 可退出身份 | 退出登录后本机数据保留，可继续以纯本地使用 |

## 八、合规影响

### 8.1 仍然不需要企业主体

| 项 | 是否需要 |
| --- | --- |
| 短信服务 | ❌ 不需要（不发短信） |
| 微信开放平台 | ❌ 不需要 |
| 支付商户号 | ❌ 不需要 |
| 用户实名 | ❌ 不需要 |
| 应用商店开发者账号 | ❌ 不需要 |

### 8.2 儿童个人信息：负担仍然很轻

| 合规项 | 状态 | 说明 |
| --- | --- | --- |
| 收集个人身份信息 | ❌ 不收集 | 无手机号、无邮箱、无真实姓名、无微信 ID |
| 监护人同意 | ⚠️ **简化为隐私说明 + 明确告知** | 因为不收集身份信息；但**数据上云需明确告知并获得同意** |
| 儿童数据上云 | ⚠️ **有义务** | 启用云端档案后须：① 明示告知；② 提供删除；③ **端到端加密（推荐）** |
| 数据出境 | ⚠️ 需注意服务器位置 | 境外服务器同步儿童数据需评估；建议**默认关闭云档案**，用户显式开启 |
| 数据删除权 | ✅ 提供 | 「注销并删除云端数据」+ 本机清除 |

> ⚠️ **重要提醒**：启用邀请码云档案后，「数据不出设备」这一最强的合规卖点**不再完全成立**。必须做到：
>
> 1. **默认关闭云档案**（`enableCloudProfile=false`），由用户显式开启
> 2. 开启时用通俗语言告知上传的是什么、加密方式、如何删除
> 3. **默认启用端到端加密**，使服务端不可读
> 4. 若服务器在境外，需单独评估儿童数据出境的合规要求
>
> 这样即使上云，合规负担仍远低于「实名账号 + 明文存储」的传统方案。

> **部署注意**：默认采用**家庭共享码**（「一码一账号」仅在确需隔离时发放第二个码）；云档案默认关、默认端到端加密，把上传决定权交给用户；服务器位置决定是否备案——起步放境外，境内须 ICP 备案（个人主体可做非经营性备案），见 [02-4 7.1](./04-本地优先与后端策略.md#71-部署位置与备案决策)。
