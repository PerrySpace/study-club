# 02-2 多端适配与响应式设计规范

> 本文档定义产品覆盖的终端形态、各端的布局与交互差异、跨端代码复用边界、能力分级与降级规则，以及多端验收标准。
> 跨端工程实现（uni-app、小程序分包、App 打包）见 [02-3 uni-app 跨端方案与小程序适配](./03-uni-app跨端方案与小程序适配.md)。
>
> ⚠️ **当前范围（重要）**
> | | 端 | 状态 | 原因 |
> | --- | --- | --- | --- |
> | ✅ **当前交付** | 手机 / iPad / 桌面（Web + PWA） | **实际开发** | 零门槛、免主体、免审核、免备案（视服务器位置） |
> | ⏸️ **预留（本文档仍完整设计）** | 微信小程序、iOS / Android App | **不写、不构建、不注册** | **需要企业主体**；个人主体不能申请教育类目，且**小程序注册主体选定后不可变更**（见 [01-4 3.2](../01-产品规划/04-免费开放与开源策略.md#32--微信小程序不能先用个人主体试水)） |
> | ✅ **云端后台** | FastAPI + MongoDB（自托管） | **可部署** | 只需服务器，不需要企业主体 |
>
> **为什么预留端仍要设计**：多端的复用成本在**第一天**就被决定。`packages/core` 的边界、`packages/tokens` 的设计变量、视图层的选择器约束——**这些东西 Web 端写的时候不遵守，将来做小程序就是重做前端**。所以本文档的 iPad/桌面规范**现在就执行**，小程序/App 规范**作为约束保留**（约束当前写法，而非当前实现）。

## 一、目标端矩阵

### 1.1 端清单与定位

| 端 | 载体 | 定位 | 优先级 | 目标阶段 |
| --- | --- | --- | --- | --- |
| **手机浏览器** | Web（H5 + PWA） | 主力学场景；家长分享落地页（微信内置浏览器打开） | P0 | Phase 0 |
| **iPad** | Web（H5 + PWA） | **最佳学习体验端**：大屏 + 手写笔，家庭共用 | P0 | Phase 0 |
| **桌面浏览器** | Web（H5 + PWA） | 家长报告、教师看板、演示与大屏 | P1 | Phase 0 |
| **微信小程序** | uni-app 编译 | **低成本获客与裂变**；轻量学习闭环 | P1 | Phase 2 |
| **iOS App** | uni-app 编译 | 推送、离线、录音质量 | P1 | Phase 2 |
| **Android App** | uni-app 编译 | 同上 | P1 | Phase 2 |
| 鸿蒙 App | 待定（见 02-3 预留清单） | 远期覆盖 | P3 | 立项复核 |

### 1.2 三条硬结论

**结论一：手机 / iPad / 桌面三端共用一套 Web 代码，靠响应式区分。**
这三端的差异是"屏幕宽度 + 指针类型"，属于同一套渲染引擎（浏览器），没必要拆三份代码。iPad 不是"独立的端"，而是**断点更大、多了手写笔、多了横屏**的手机。

**结论二：小程序和 App 共用一套 uni-app 代码，与 Web 端并列。**
小程序不能运行 Web 构建产物（无 DOM、无 Service Worker、包体积 ≤ 20MB），所以它是真正意义上的第二个外壳。App 与小程序同为 uni-app 产物，可共享视图层。

**结论三：业务逻辑只写一遍，永不写在视图层。**
这是多端方案能不能成立的分水岭。见第二章。

## 二、总体策略：一套内核，三套外壳

### 2.1 分层结构

```
┌────────────────────────────────────────────────────────────────────────┐
│                          外壳层（UI，各自独立）                          │
│  ┌──────────────────┐  ┌──────────────────┐  ┌────────────────────┐  │
│  │ apps/web         │  │ apps/mobile      │  │ apps/admin         │  │
│  │ Vue3 + Vite      │  │ uni-app (Vue3)   │  │ Vue3 + Element Plus│  │
│  │ 手机/iPad/桌面    │  │ 小程序 + iOS/安卓 │  │ 仅桌面             │  │
│  └────────┬─────────┘  └────────┬─────────┘  └─────────┬──────────┘  │
└───────────┼──────────────────────┼──────────────────────┼─────────────┘
            │                      │                      │
            ▼                      ▼                      ▼
┌────────────────────────────────────────────────────────────────────────┐
│              内核层 packages/core（零 DOM 依赖，四端共用）                │
│  ┌────────────┬────────────┬────────────┬────────────┬─────────────┐  │
│  │ api 适配器  │ Pinia store │ 算法引擎    │ 类型与常量  │ 平台能力接口  │  │
│  │ HTTP 抽象   │ 领域状态    │ SRS/拼音/  │ TS 类型     │ Recorder    │  │
│  │            │            │ 题型/F0 提取│ 枚举        │ Storage/Push│  │
│  └────────────┴────────────┴────────────┴────────────┴─────────────┘  │
├────────────────────────────────────────────────────────────────────────┤
│             设计层 packages/tokens（CSS 变量 + 断点常量，跨端同源）        │
└────────────────────────────────────────────────────────────────────────┘
            │
            ▼
┌────────────────────────────────────────────────────────────────────────┐
│                服务层 Python + FastAPI + MongoDB（端无关）                │
└────────────────────────────────────────────────────────────────────────┘
```

**关键约束：`packages/core` 里不允许出现 `window`、`document`、`localStorage`、`uni.xxx`、`wx.xxx`。**
所有平台能力通过接口注入（依赖倒置），见第七章 7.3。

### 2.2 哪些能复用、哪些必须重写

| 层 | 内容 | Web → 小程序/App 复用率 | 说明 |
| --- | --- | --- | --- |
| 业务算法 | SRS 调度、拼音比对、题型生成、F0 转声调判定、错题归因 | **100%** | 纯函数，无平台依赖 |
| 数据与状态 | Pinia store、API 契约、TS 类型、枚举常量 | **95%** | Pinia 在 uni-app 受支持 |
| 接口层 | 请求封装、拦截器、Token 刷新、离线队列 | **80%** | 需换 HTTP 适配器（axios → uni.request） |
| 设计变量 | 色板、间距、圆角、断点、动效时长 | **90%** | 需注意 rpx/px 单位换算 |
| 视图层 | 页面、组件、布局 | **20–30%** | 标签体系与布局能力不同，**必然重写** |
| 平台能力 | 录音、存储、推送、分享 | **0%** | 必须各端实现 |

> **复用的本质**：可复用的是"算"和"存"，不可复用的是"画"和"调"。把业务逻辑写进组件里，就等于放弃多端。

### 2.3 复用率预期

| 端 | 相对 Web 端的前端工作量 | 前提 |
| --- | --- | --- |
| iPad / 桌面 | **+15%**（响应式与布局增量） | Web 端从第一天就按响应式写 |
| 小程序 + App（同工程） | **+55%**（视图层重写 + 平台能力 + 分包调优） | core 边界严格守住 |

> ⚠️ **如果 Web 端先把布局写死成手机尺寸、再把逻辑塞进组件**，那么到小程序阶段复用率会从 55% 掉到 15%，等于重做一遍。**多端的成本早在 Phase 0 就决定了。**

## 三、响应式体系（Web 端）

### 3.1 断点定义

断点按**真实设备视口宽度**划分为**三档**，不按设备名：

| 档位 | 视口宽度 | 覆盖设备（CSS 视口实测） | 布局形态 |
| --- | --- | --- | --- |
| **手机** | `< 768px` | 手机竖屏与横屏（竖屏单列，横屏加宽） | 单列 |
| **iPad / 平板** | `768–1279px` | iPad mini 744、iPad 10 代 810、iPad Air 820、iPad Pro 11" 834、iPad Pro 12.9" 竖屏 1024、iPad 横屏 1080 | **双列**（窄边栏） |
| **桌面** | `≥ 1280px` | 桌面 / 笔记本 / 大屏显示器 | **三列**（完整侧边栏） |

**实现方式**：CSS 媒体查询 + `matchMedia` 的 `useBreakpoint()` 组合式函数（JS 需要感知断点做条件渲染时用）。

```css
/* styles/tokens.css —— 断点常量（供 CSS 使用） */
@media (min-width: 768px)  { /* iPad */ }
@media (min-width: 1280px) { /* 桌面 */ }
```

```ts
// packages/core/constants/breakpoints.ts —— 供 JS 使用，必须与 CSS 保持同一份数值
export const BREAKPOINTS = { phone: 0, tablet: 768, desktop: 1280 } as const;
export const DEVICE_FORM = { phone: 'phone', tablet: 'tablet', desktop: 'desktop' } as const;
```

> **规则**：断点数值只允许存在两份（CSS 变量 + TS 常量），且必须同步修改。**不允许在组件里写魔法数字** `if (window.innerWidth > 900)`。

### 3.2 三档布局形态

| | 手机 | iPad / 平板 | 桌面 |
| --- | --- | --- | --- |
| 导航 | 底部 Tab Bar（4–5 项） | 左侧窄边栏（图标 + 文字） | 左侧完整侧边栏 |
| 学习地图 | 纵向卷轴，一期显示 3–4 关 | 横向双列网格，一期显示 8–12 关 | 横向三列 + 关卡详情侧栏 |
| 字卡学习 | 满屏单字，上下滑动切换 | **左侧字卡 + 右侧释义/组词/笔顺并排** | 同 iPad，右侧再加第三个辅助面板 |
| 答题 | 选项纵向堆叠，大按钮（矮屏切 2×2，见 §3.6） | 选项 2×2 网格 | 题目居中，选项横排 |
| 学情报告 | 卡片纵向滚动 | 图表 2 列并排 | 图表 + 明细表并排 |
| 古诗 | 单栏竖排/横排切换 | 左诗文右注释，**大屏保留竖排版式** | 同 iPad + 背景插画全屏 |

**布局实现建议**：用 CSS Grid 定义"外壳"，用 container query 让内部组件自适应容器宽度，而不是让每个组件都去猜屏幕宽度。

```css
/* 三档外壳：一份 DOM，媒体查询控制列数 */
.app-shell {
  display: grid;
  grid-template-areas: "main" "nav";
  grid-template-rows: 1fr auto;        /* 手机：内容 + 底部导航 */
  min-height: 100dvh;
}
@media (min-width: 768px) {
  .app-shell {
    grid-template-areas: "nav main";
    grid-template-columns: 88px 1fr;   /* 平板：窄边栏 */
    grid-template-rows: 1fr;
  }
}
@media (min-width: 1280px) {
  .app-shell { grid-template-columns: 240px 1fr; }  /* 桌面：完整边栏 */
}
```

### 3.3 触摸、指针与热区

| 项 | 规则 | 理由 |
| --- | --- | --- |
| 最小可点击热区 | **56×56px**（主操作 ≥ 64px） | 儿童手指定位精度低于成人；高于 Apple 44px / Material 48dp 的下限 |
| 相邻可点击元素间距 | ≥ 12px | 防误触（儿童误触率显著更高） |
| `hover` 效果 | 必须包在 `@media (hover: hover)` 内 | 触屏设备 `:hover` 会"粘住"上一次点击态 |
| 触摸反馈 | 用 `:active` + 缩放/变色，≤ 100ms | 无 hover 提示时，即时反馈是唯一确认手段 |
| 手势 | 滑动切字卡、下拉刷新、双指缩放字卡 | 但**每个手势都要有等价按钮**（认知能力与发现性考虑）。⛔ 页面级缩放是反过来的要求：见「文本选中 / 缩放」两行 |
| 文本选中 | **全应用默认 `user-select: none`**，只有 `.selectable`（报告页、释义、弹窗正文）与输入控件开回来 | 防长按弹菜单打断学习；「默认关、按需开」能杜绝漏加——漏开的代价只是某段文字选不中 |
| 缩放 | **整体关闭**：`viewport` 写 `user-scalable=no, maximum-scale=1, minimum-scale=1`，CSS 用 `touch-action`，Safari 用 `gesturestart` 事件 | 孩子双指/双击把页面放大后退不回来，整个布局会一直歪着；见下方「为什么光靠 viewport 不够」 |
| 长按 / 拖拽 | `-webkit-touch-callout: none` + `-webkit-user-drag: none` + `selectstart/dragstart/contextmenu` 守卫 | 长按弹「拷贝/查询」浮层、拖字卡留半透明残影，都会让界面失控 |

**为什么光靠 viewport 不够**（这条是实测出来的，别只配 meta 就以为完事）：

| 手段 | 覆盖 | 覆盖不到 |
| --- | --- | --- |
| `viewport` 的 `user-scalable=no` | Android Chrome；桌面浏览器 | **iOS Safari 10+ 起直接忽略**（无障碍考虑） |
| `touch-action: manipulation` | 挡「双击放大」；iOS Safari 也认 | 仍然**允许捏合缩放** |
| `touch-action: pan-x pan-y` | 挡捏合 + 双击（Chrome/Android/桌面） | iOS Safari **不解析双值语法**，整条声明被丢弃 |
| `gesturestart/change/end` + `preventDefault()` | iOS Safari 的捏合 | 其他内核不发这些事件（但它们已被上面的 CSS 挡住） |
| `wheel + ctrlKey` 拦截 | 桌面触控板捏合 / Ctrl+滚轮 | 浏览器自身 Ctrl +/− 快捷键（UI 层拦不住，已知且可接受） |

落地位置：CSS 在 `apps/web/src/styles/base.css`（`touch-action` 用 `@supports (touch-action: pan-x pan-y)` 分档，见文件内注释），事件守卫在 `apps/web/src/platform/dom-guard.ts`，由 `main.ts` 在首屏渲染**之前**安装。

```html
<!-- 正确的 viewport：含安全区与禁止缩放（三档缩放都要锁，缺一档安卓上仍可能被顶开） -->
<meta name="viewport"
      content="width=device-width, initial-scale=1, maximum-scale=1, minimum-scale=1,
               viewport-fit=cover, user-scalable=no" />
```

### 3.4 安全区与视口

| 问题 | 正确做法 | 错误做法 |
| --- | --- | --- |
| 底部导航被 iPhone Home 指示条遮挡 | `padding-bottom: env(safe-area-inset-bottom)` | 固定 `padding-bottom: 16px` |
| 刘海 / 灵动岛遮挡顶部标题 | `padding-top: env(safe-area-inset-top)` | — |
| 移动端地址栏导致 `100vh` 溢出 | **`100dvh`**（动态视口高度） | `height: 100vh` |
| 键盘弹出遮挡输入框 | `VisualViewport` API 监听 + 滚动到可视区 | 靠 `scrollIntoView` 硬猜 |
| iPad 横屏左右安全区 | `env(safe-area-inset-left/right)` | — |

> ⚠️ `100vh` 是移动端最经典的坑：地址栏收起/展开会改变实际可视高度，用 `100vh` 做全屏会导致底部内容被裁掉。**全项目统一用 `100dvh`，并在 `@supports` 中为老浏览器降级为 `100vh`。**

### 3.5 字号、密度与流体缩放

儿童产品的字号不能按成人 H5 的 14px 来，也不能在大屏上无限放大。

| 元素 | 手机 | iPad | 桌面 | 实现 |
| --- | --- | --- | --- | --- |
| 正文 | 18px | 20px | 18px | `clamp(18px, 1.2vw + 14px, 22px)` |
| 字卡主字 | 120–160px | 200–280px | 160–200px | 视口比例 + 上限约束 |
| 按钮文字 | 18px | 20px | 18px | 同上 |
| 辅助文字（拼音/释义） | ≥ 16px | ≥ 18px | ≥ 16px | **绝对下限 16px** |

> 学习页（§3.6）在矮屏上会把「字卡主字」「聚焦大字」逐档收小，
> 最低到 88px 左右 —— 那是为了把**操作按钮留在屏幕内**付出的代价，
> 是刻意的取舍，不是漏了 `clamp`。收紧的只有「大标题」那一号，
> 正文 18px 的下限不动。

```css
:root {
  /* 流体字号：小屏不过小、大屏不过大 */
  --font-body: clamp(18px, 1.1vw + 14.5px, 22px);
  --font-card-glyph: clamp(120px, 26vw, 240px);
  /* 内容最大宽度：防止大屏上字卡被拉成巨型方块 */
  --content-max: 880px;
  /* 触控热区 */
  --tap-min: 56px;
  --tap-primary: 64px;
}
```

**大屏约束原则**：内容区最大宽度 `--content-max`（880px）居中；超出的宽度用于**增加信息密度（多栏）**，而不是**拉大单个元素**。大屏上把一个字卡放大到 600px 是设计事故。

### 3.6 学习页：全部操作控制在一屏内

**规则（硬性）**：识字闯关 / 古诗 / 故事这三条**学习中**的页面，当前这一步的
全部操作必须在一个屏幕内可达 —— 页面本身不滚动，主操作按钮永远可见。

**为什么**：这三页原来是「长文档」形态，进度、引导、内容、按钮从上到下排成一条，
整页跟着内容一起长高。手机上一旦内容多，主操作（下一步 / 下一题 / 我念完啦）
就被顶到屏幕外。而 6 岁孩子**不会主动尝试滚动**：看不见的按钮等于不存在的按钮，
流程就卡在「他明明答对了，却停在这一题」，而报障记录里只会写「点不动」。

**结构契约**（三条线共用 `apps/web/src/styles/learn-screen.css`）：

| 区域 | 类名 | 职责 | 是否滚动 |
| --- | --- | --- | --- |
| 整页 | `.learn-page` | 视口内的一列，自身**不滚动** | ❌ |
| 顶部 | `.learn-page__head` | 进度 / 步骤指示 / 标题 | ❌ 常驻 |
| 内容 | `.learn-page__body` | 本步的核心内容 | ✅ **唯一**滚动区 |
| 底部 | `.learn-page__foot` | 本步的主操作 | ❌ 常驻 |

外壳层开启方式：路由 `meta: { oneScreen: true }` → `AppShell` 加 `.app-shell--one`
（`height: 100dvh` + `overflow: hidden`，内容区变成 flex 容器）。
⛔ 只给学习中的页面加；列表页（首页 / 地图 / 报告 / 设置）本来就该能往下翻。

**四条实现纪律**（每条都对应一次踩坑）：

1. **主操作 `__foot`、内容 `__body`，不要颠倒**。把按钮放进滚动区，等于把
   「能否继续」交给滚动位置决定。
2. **不要用 `position: fixed` 做底部操作条**。它会盖住内容与安全区，而且失去了
   「内容区自己让位」的关系；flex 分配高度才是对的。
3. **`height` 不能写成 `min-height`**。只保证「不低于一屏」时，内容一多页仍会变高，
   `__body` 拿不到有限高度，`min-height: 0` 的收缩无从谈起，`__foot` 照样被顶走。
4. **自适应尺寸能用 CSS 就别用 JS**。本页唯一必须用 JS 的是手写板的米字格边长
   （canvas 尺寸是内联像素值，媒体查询改不动它），走 `useViewportHeight()`
   → `platform/viewport.ts`。

**矮屏分档**（横屏手机 / 小屏手机 / 小笔记本）：

| 阈值 | 处理 |
| --- | --- |
| `max-height: 820px` | 字卡主字收一档（`--font-card-glyph`） |
| `max-height: 760px` | 页内间距收一档；**4 个选项由纵向堆叠切成 2×2** |
| `max-height: 700px` | 字卡主字再收一档；聚焦大字 / 米字格提示字 / 跟读题大字收档 |

```css
/* 一屏骨架（节选，完整见 styles/learn-screen.css） */
.app-shell--one { height: 100dvh; overflow: hidden; }
.app-shell--one .app-shell__main {
  display: flex; flex-direction: column; min-height: 0; overflow: hidden;
}
.learn-page { flex: 1 1 auto; min-height: 0; display: flex; flex-direction: column; }
.learn-page__head, .learn-page__foot { flex: none; }
.learn-page__body { flex: 1 1 auto; min-height: 0; overflow-y: auto; }
```

⚠️ **矮屏别用 `min(x, ydvh)` 塞进 clamp**：含 `dvh` 的表达式在旧内核
（Safari < 15.4 / Chrome < 108）整条无效，而 `font-size` 一旦无效就退回**继承值**
（18px）—— 字卡主字会缩成正文大小，比「字大了点」严重得多。用高度媒体查询分档，
在所有内核上都有确定结果。

### 3.7 横竖屏

| 端 | 策略 |
| --- | --- |
| 手机 | 默认锁竖屏体验；字卡学习与古诗页**允许横屏**（横屏时字卡左、内容右） |
| iPad | **双方向都支持**，横屏为推荐学习姿态（配合键盘/手写笔放置） |
| 桌面 | 不适用 |

实现上用 `orientation: portrait/landscape` 媒体查询，**不锁定屏幕方向**（Web 无法可靠锁定，且用户会反感）。

> 横屏手机上「一屏内」的预算会很紧（可用高度常常只有 360px 左右）。
> 此时上述矮屏分档会全部生效（见 §3.6），仍然放不下的部分由 `.learn-page__body`
> 内部滚动兜住 —— **底部的「下一步 / 我念完啦」在任何情况下都不会被顶出屏幕**。

## 四、iPad 专项设计（本产品体验最好的一端）

### 4.1 为什么 iPad 值得单独设计

识字是**手写**与**看大图**的学习行为。iPad 是唯一能同时提供"大尺寸汉字 + 真实笔迹"的设备，且家庭共用的 iPad 在少儿学习场景中渗透率很高。**这是手机 App 结构性做不到的场景。**

### 4.2 Apple Pencil 与手写练习

| 能力 | 技术 | 说明 |
| --- | --- | --- |
| 手写笔迹采集 | **Pointer Events**（`pointerdown/move/up` + `getCoalescedEvents()`） | 比 `touchstart` 精度高，可拿到高频采样点 |
| 压感与倾斜 | `event.pressure` / `event.tiltX/tiltY` | 笔迹粗细、笔锋表现（Safari 支持） |
| 手掌防误触 | `touch-action: none` + 只处理 `pointerType === 'pen'` | 落笔时忽略 `touch` 类型事件 |
| 笔迹保真 | 压力曲线 → 线宽映射 + 平滑算法（Catmull-Rom / 贝塞尔拟合） | 避免锯齿，儿童书写抖动大，过拟合反而难看 |
| 判分 | 笔顺序列比对（`stroke_order_ref` 的笔顺数据）+ 轨迹相似度 | **不做字迹美观打分**，只判笔顺正确性与大致结构 |
| 橡皮擦 | iPadOS 上 Apple Pencil 2+ 的"轻点两下"可映射为擦除 | 可选增强 |

```ts
// composables/useHandwriting.ts —— 要点
// 1. 只接受 pointerType === 'pen' | 'mouse'，忽略 touch（防手掌误触）
// 2. 用 getCoalescedEvents() 取同一帧内的全部采样点，避免高速书写丢点
// 3. 采样点先做 5px 网格吸附 + 时间戳，便于后续笔顺判定与回放
// 4. Canvas 用 devicePixelRatio 缩放，避免 iPad Retina 上笔迹发虚
```

> ⚠️ **不要在 iPad 上强推手写**：触屏手写（非笔）识别体验差，会打击信心。策略是**检测到 `pointerType === 'pen'` 时开启手写练习入口**，否则默认走"描红跟写"的宽容模式。

### 4.3 大屏信息密度增量

在 iPad 上相对手机**额外呈现**的内容（手机端折叠进二级页）：

| 模块 | iPad 增量 |
| --- | --- |
| 字卡 | 同屏显示：拼音 + 释义 + 组词 + 部首笔画 + 笔顺动画 |
| 学习地图 | 显示单元进度环形图与本周学习曲线 |
| 答题 | 答错时右侧同屏显示字卡对比（手机需跳转） |
| 古诗 | 竖排版式 + 逐句注释 + 创作背景，同屏阅读 |
| 家长报告 | 双图表并排 + 明细表 |

### 4.4 家庭共用与多档案切换

iPad 常为家庭共用设备，这是**手机端没有的使用模式**：

- 平板断点下，档案切换入口提升到一级（顶部头像 + 长按快速切换），手机端收在设置里
- 支持"学习结束自动切回档案选择页"，避免下一个孩子接着上一个人的进度
- 每个档案有独立主题色，避免混淆（视觉身份标识）

### 4.5 分屏与台前调度

iPadOS 的 Split View / Stage Manager 会让视口变窄且比例异常。应对：

- 不依赖固定宽高比做布局，全部用流式 Grid/Flex
- `@media (min-width: 768px)` 判定后，**再叠加容器宽度判断**（container query），避免"分屏后仍是平板布局但空间只有 500px"的挤出
- 横屏分屏时若宽度 < 600px，**降级为手机布局**（形态按可用宽度定，不按设备定）

| 项 | 设计 |
| --- | --- |
| 布局 | 三列：侧边导航（240px）+ 主内容（`--content-max` 居中）+ 辅助面板（可选） |
| 快捷键 | 数字键 `1–4` 选答案、`空格` 重播读音、`←/→` 切换字卡、`Esc` 退出关卡 |

| 教师端（远期） | 班级看板、批量导出，桌面独占 |
| 演示模式 | 一键全屏，隐藏非必要 UI，适配投屏教学 |

## 六、手机专项设计

| 项 | 设计 |
| --- | --- |
| 单手可达 | 主要操作放屏幕**下 1/3**；顶部只放标题与返回 |
| 底部导航 | 4–5 项，含安全区内边距；字卡/答题等沉浸页**隐藏导航** |
| 沉浸式学习 | 进入关卡后全屏，隐藏状态栏区域（`100dvh` + 深色延展） |
| 弱网优化 | 预取下一单元、音频降码率（单声道 64kbps 足够）、骨架屏 |
| 微信内置浏览器 | 需适配 X5/WKWebView 差异；分享落地页在此打开，**首屏必须 1.5s 内可用** |
| 音频播放 | `speechSynthesis` 为兜底，真实音频走 `Audio` + 预加载；**首次交互后才能播放**（autoplay 限制） |
| 亮度与护眼 | 尊重系统深色模式仅做轻微调整（儿童端视觉不宜大改），提供舒眼背景切换 |

> ⚠️ **微信内置浏览器是多端里最容易被忽略的一环**：分享落地页从这里打开。它不支持 PWA 安装提示，且缓存策略独立，**首屏包体必须比 PWA 模式更激进地瘦身**。

## 七、能力分级与降级

### 7.1 能力矩阵

| 能力 | Web（PWA） | App（uni-app） | 微信小程序 |
| --- | --- | --- | --- |
| **声调 F0 检测**（核心差异化） | ✅ 实时 | ✅ 录后分析 | ✅ 录后分析 |
| **本地 ASR 模型**（20–60MB） | ✅ 需下载 | ✅ | ❌ **包体积不允许** |
| 手写轨迹采集 | ✅ Pointer Events + 压感 | ✅ | ⚠️ 仅 touch，无压感 |
| 离线学习闭环 | ✅ SW + IndexedDB | ✅ 本地存储 | ⚠️ Storage 上限低，靠分包预下载 |
| PWA 安装到桌面 | ✅ | — | — |
| 消息推送 | ⚠️ iOS 上受限 | ✅ | ✅ 订阅消息（一次性，需用户主动订阅） |
| 社交分享/裂变 | ⚠️ 截图分享 | ✅ | ✅ **最强（会话/朋友圈卡片）** |
| 录音采集 | ✅ getUserMedia | ✅ | ✅ RecorderManager（16kHz 单声道） |
| 音频实时流分析 | ✅ AudioWorklet | ✅ | ⚠️ onFrameRecorded（兼容性需实测） |
| 后台长时任务 | ❌ | ⚠️ 系统限制 | ❌ |

### 7.2 三档能力定义

| 档位 | 端 | 定义 |
| --- | --- | --- |
| **Full** | Web / PWA、iOS / Android App | 全部功能可用，含本地模型、离线闭环、手写压感 |
| **Lite** | 微信小程序 | 保留核心学习闭环与声调检测；砍掉本地大模型与重资产能力；以"按需分包 + 云端补充"实现 |

### 7.3 运行时能力探测（关键实现）

**不要用 `if (isMiniProgram)` 散落在业务代码里。** 统一在启动时探测一次，产出能力对象，注入到 core：

```ts
// packages/core/platform/types.ts —— 平台能力接口（core 只认这个接口）
export interface PlatformCapabilities {
  runtime: 'web' | 'miniprogram' | 'app';
  form: 'phone' | 'tablet' | 'desktop';   // 形态按可用宽度判定，不按设备
  canRecord: boolean;
  canLocalAsr: boolean;          // 小程序为 false
  canRealtimeAudioAnalysis: boolean;
  canHandwritingPressure: boolean;
  canPush: boolean;
  canInstallPwa: boolean;
  storageQuotaMB: number;
}
```

```ts
// apps/web/src/platform/web.ts  /  apps/mobile/src/platform/uni.ts
// 每个外壳只实现一份适配器，core 通过依赖注入拿到它
```

**能力探测必须附带降级行为**，只报能力不给方案等于没做：

| 能力缺失 | 降级行为 | 用户感知 |
| --- | --- | --- |
| 无本地 ASR（小程序） | 走云端 ASR / 直接跳过"内容判定"，只做声调判定 | 功能变少但不报错，不显示禁用按钮 |
| 无法实时音频分析 | 改为"录 2 秒 → 停止 → 分析 → 出结果" | 交互多一步，结果一致 |
| 无 Web Audio 可视化 | 用静态波形图代替实时频谱 | 视觉简化 |
| 存储配额低（小程序） | 只缓存当前单元 + 下一单元，其余按需拉取 | 离线范围变小，需在 UI 说明 |
| 无 PWA 安装 | 隐藏"添加到主屏幕"引导 | 静默隐藏，不做替代引导 |
| iOS 无推送 | 引导开启 Web App 通知或邮件提醒 | — |

> ⚠️ **降级不等于隐藏**：能降级实现的功能要降级实现（如声调用录后分析），只有当降级也无法实现时才隐藏入口。**大面积隐藏按钮会让小程序端显得像个残次品**，直接影响获取成本最低那条渠道的转化。

### 7.4 能力矩阵的维护

能力矩阵是**单一事实来源**，新增功能时必须回答"三端分别怎么表现"，否则不允许进入开发。

## 八、分端性能预算

| 指标 | 手机（4G） | iPad（WiFi） | 桌面 | 小程序 | App |
| --- | --- | --- | --- | --- | --- |
| 首屏可交互 | < 2s | < 1.5s | < 1.5s | < 1.5s | < 1.5s |
| 首屏 JS（gzip） | < 150KB | < 200KB | < 200KB | **主包 < 1.2MB**（留余量） | < 200KB |
| 主包 / 入口包 | — | — | — | **主包 ≤ 2MB（硬限）** | — |
| 字卡切换 | < 100ms | < 100ms | < 100ms | < 150ms | < 100ms |
| 声调评测出结果 | < 300ms | < 300ms | < 300ms | < 500ms | < 300ms |
| 内存占用峰值 | < 150MB | < 250MB | < 400MB | < 120MB | < 200MB |
| 离线可用范围 | 已缓存单元 | 已缓存单元 | 已缓存单元 | 当前 + 下一单元 | 已缓存单元 |

**大资源加载策略（三端一致）**：

| 资源 | 体积 | 策略 |
| --- | --- | --- |
| F0 提取算法（纯 JS/WASM） | 几十 KB | **内联进主包**（这是核心能力，不能延后） |
| 声调模板数据 | < 50KB | 随主包或首次进入评测时拉取 |
| 本地 ASR 模型 | 20–60MB | **首屏绝不加载**；用户首次进入跟读功能时后台下载，进度条可见，成功后写 Cache Storage |
| 音频素材 | 单条 20–60KB | 进入单元时预取，LRU 淘汰 |
| 笔顺数据 | 单字 2–5KB | 进入字卡时拉取 |

> ⚠️ 小程序端不存在"后台下载大模型"这条路（无长时任务 + 包体积限制）。**这是小程序必须做 Lite 版的根本原因**，不是策略选择。

## 九、多端测试矩阵与验收

### 9.1 必须真机验证的设备

| 优先级 | 设备 | 验证重点 |
| --- | --- | --- |
| P0 | iPhone（含刘海机型）SE 或 13+ | 安全区、底部导航、录音权限弹窗 |
| P0 | Android 中端机（骁龙 6/7 系，2–3 年前机型） | **性能下限**、WebView 差异、低端机录音质量 |
| P0 | iPad 10 代或 Air（**含 Apple Pencil 至少 1 台**） | 横竖屏、双栏布局、手写笔迹、分屏 |
| P0 | 微信内置浏览器（iOS + Android 各一） | 分享落地页首屏、音频播放授权 |
| P1 | 桌面 Chrome / Safari | 快捷键、三栏布局、报告导出 |
| P1 | 微信小程序（开发者工具 + 至少 2 台真机，iOS/Android 各一） | 分包加载、录音、包体积实测 |
| P2 | iPad Pro 12.9"（iPad 档大屏临界） | 断点临界表现 |

### 9.2 必须真机才能发现的问题清单

- 音频录制在**降噪/回声消除**开启时的实际音质（影响声调判定准确率）
- 低端 Android WebView 上 Web Audio 的延迟与丢帧
- iPad 手写笔迹在 **60Hz / 120Hz ProMotion** 下的采样差异
- 弱网（3G / 高丢包）下的离线队列补报
- 小程序 `onFrameRecorded` 在各机型上的帧回调稳定性
- 系统字体放大（无障碍设置）后的布局溢出

### 9.3 验收标准

一个功能视为"多端完成"，需同时满足：

- [ ] 手机（<768）、iPad（768–1279）、桌面（≥1280）三档布局都无溢出、无遮挡、无错位
- [ ] 触屏与鼠标两种交互方式都可用（含 `hover` 隔离）
- [ ] 竖屏与横屏都验证（iPad 与手机横屏）
- [ ] 系统字体放大 1.3× 后不破版
- [ ] 安全区在刘海机型上不遮挡
- [ ] 能力缺失时走降级路径，不出现禁用按钮或报错
- [ ] 在能力矩阵中登记了三端表现
- [ ] 弱网（限速 3G）下首屏可交互达标
